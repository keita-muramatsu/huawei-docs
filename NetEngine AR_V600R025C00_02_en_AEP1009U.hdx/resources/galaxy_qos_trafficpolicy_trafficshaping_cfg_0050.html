Configuring Traffic Shaping to Implement Interface-based Rate Limiting

Context

When a large amount of traffic is sent from the downstream device to its upstream device, to prevent congestion or packet loss, configure traffic shaping on the outbound interface of the device. Traffic shaping adjusts the rate of outgoing traffic on the interface to reduce traffic bursts so that outgoing packets can be transmitted at a stable rate. With traffic shaping, packets exceeding the rate limit enter the buffer queue, and are only sent out at an even rate when there are sufficient tokens in the token bucket. In addition, if the buffer queue is full, the system discards new packets.

If packets are encapsulated through VPN tunnels, the calculated packet length during rate limiting or traffic statistics collection on a WAN-side interface includes the lengths of link-layer and physical-layer packet headers and the lengths of tunnel protocol encapsulation headers. As a result, the actual user bandwidth calculated using this method is smaller than the expected value. To minimize the difference between the actual bandwidth and the expected bandwidth, you can disable the device from counting the inter-frame gaps and preambles when it calculates the packet length, and configure the function of excluding the tunnel encapsulation length of packets on the tunnel interface. In this way, the calculated packet length excludes the lengths of the physical-layer packet header and tunnel protocol encapsulation header.

Currently, traffic shaping can only be used to rate-limit outgoing traffic on an interface.

The system will generate an alarm when the rate of outgoing traffic on an interface exceeds the alarm threshold for rate-limiting outgoing traffic.

Procedure

  1. Enter the system view.

    system-view

  2. (Optional) Configure the method of calculating the packet length when the device calculates the traffic shaping rate.

    qos overhead layer link

    By default, the device counts the physical-layer and link-layer compensation information of packets when calculating the traffic shaping rate in the outbound direction or the traffic policing rate for interface-based rate limiting in the inbound direction.

    After rate limiting is configured for traffic shaping in the outbound direction or traffic policing for interface-based rate limiting in the inbound direction, the device counts the inter-frame gaps and preambles of packets when calculating the traffic shaping rate in the outbound direction or the traffic policing rate for interface-based rate limiting in the inbound direction. As a result, the calculated rate is inaccurate. After this command is configured, the device does not count the inter-frame gaps and preambles when calculating the rate. This ensures the accuracy of the rate limit for traffic shaping in the outbound direction or traffic policing for interface-based rate limiting in the inbound direction.

    The AR8700 series, AR6710-L26T2X4, AR6710-L26T2X4-T, AR6710-L50T2X4, and AR6710-L50T2X4-T do not support this command. Therefore, the device counts the inter-frame gaps and preambles when calculating the traffic shaping rate in the outbound direction or the traffic policing rate for interface-based rate limiting in the inbound direction. By default, the inter-frame gap is 12 bytes and the preamble is 8 bytes.

  3. (Optional) Enter the interface view.

    interface { interface-type interface-number | interface-name }

  4. (Optional) Enable the queue capability on the interface.

    qos queue-scheduling enable

    By default, the queue capability is disabled on an interface.

    After the queue capability is enabled on an Eth-Trunk interface or a tunnel interface, the loopback function is enabled by default.

    For other physical interfaces, when the queue capability is enabled on an interface, it is not enabled on a sub-interface of the interface. If the queue capability also needs to be used on a sub-interface, enable it in the sub-interface view.

    • Queue resources are not allocated to physical and logical interfaces by default for the AR5700 series, AR6710-L14T2X4, AR6710-L8T3TS1X2, and AR6710-L8T3TS1X2-T. This command can be configured on physical and logical interfaces. For other models, queue resources are allocated to physical interfaces, but are not allocated to logical interfaces by default. Therefore, this command can be configured only on logical interfaces.
    • This command cannot be configured on an MP-group interface or on a serial interface created on an E1 card. If queue resources are insufficient, creating these two types of interfaces will cause queue-related functions on the interfaces to become invalid. In this case, you need to create the interfaces again when queue resources are sufficient.

  5. (Optional) Configure the tunnel encapsulation length of packets on the tunnel interface.

    qos overhead encap-length encap-length-value
quit

    By default, no tunnel encapsulation length of packets is configured on a tunnel interface.

    Only the AR8100 series, AR5700 series, AR6700-H series, AR6710-L14T2X4, AR6710-L8T3TS1X2, and AR6710-L8T3TS1X2-T support this function.

  6. Enter the interface view.

    interface { interface-type interface-number | interface-name }

  7. Configure the rate limit for outgoing traffic on the interface.

    qos lr cir cir-value [ kbps | mbps | gbps ] [ cbs cbs-value [ bytes | kbytes | mbytes ] ] [ outbound ]

    By default, the rate limit on an interface is the maximum bandwidth of the interface.
