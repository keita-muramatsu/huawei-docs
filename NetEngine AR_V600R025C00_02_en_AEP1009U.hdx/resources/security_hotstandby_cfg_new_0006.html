Device Priority and Fault Monitoring

The device priority in hot standby reflects a device's comprehensive capabilities. A device with a higher priority better suited to carry services. Device priority is determined by indicators in Table 1 and cannot be configured.

For ARs, they work in load sharing mode under normal conditions. If a device restarts after a fault, it temporarily enters the Standby state. If the cost of dynamic routes is adjusted based on the active/standby status, services are handled by the other device. Once the restarted device completes data backup, both devices return to load balancing mode.

Table 1 Indicators determining the device priority

Indicator

Meaning

Impact on the Priority

Calculation Method

Fault indicator

Indicates the severity of a fault that occurs on a device. In hot standby mode, a device with a higher fault indicator has a more severe fault, and is not suitable for carrying services.

A device with a lower fault indicator has a higher priority.

If the fault indicators are different, the robustness indicators are not compared.

The initial value of the fault indicator is 0. The value is determined based on the following monitored items (for the calculation formula, see the following table):

  • Status of the monitored interface
  • Status of the monitored link

Robustness indicator

Indicates the working capability of a device. In hot standby mode, a device with a higher robustness indicator has a stronger processing capability and is suitable for carrying services.

If the fault indicators are the same, the device with a higher robustness indicator has a higher priority.

Robustness indicator = Number of operational CPUs x 2

Table 2 describes the impact of faults on the indicators.

Table 2 Impact of faults on the indicators

Fault

Impact on the Fault Indicator

Impact on the Robustness Indicator

CPU fault

The CPU status does not affect the fault indicator.

Faulty CPUs refer to those that are not registered, have core failures, or have anomalies in key processes. The robustness indicator is recalculated based on the number of CPUs that are running properly.

Interface fault

A device has many interfaces, some of which may be unused or carry less important services. The fault indicator is affected only when the physical status (not protocol status) of a monitored interface is down. The interface fault affects the fault indicator in the following cases:

  • When monitored physical interfaces are down, the fault indicator increases by 2 x Number of faulty interfaces.

  • If an Eth-Trunk interface is monitored, the device also monitors all its member interfaces (you can disable this behavior if required). If member interfaces go down, the fault indicator increases by 2 x Number of faulty member interfaces. If Eth-Trunk interfaces go down, the fault indicator increases by 2 x Number of faulty Eth-Trunk interfaces. If member interfaces are also monitored, the fault indicator does not additionally increase.

NOTE:

If you want the device priority to remain unchanged when a member interface of a trunk interface fails, you can disable the HRP module from monitoring the status of trunk member interfaces. To do so, run the undo hrp track trunk-member enable command.

The interface fault does not affect the robustness indicator.

Link fault

A device can monitor specific BFD sessions to determine the link status. When monitored sessions go down, the fault indicator increases by 2 x Number of down sessions.

The link fault does not affect the robustness indicator.
