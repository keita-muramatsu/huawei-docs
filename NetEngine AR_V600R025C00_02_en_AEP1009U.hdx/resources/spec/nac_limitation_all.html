Precautions

  • NAC authentication mode:

    Currently, the device supports the following authentication modes: 802.1X authentication, MAC address authentication, Portal authentication

    Currently, the device supports the following multi-mode authentication modes: MAC address authentication and 802.1X authentication, MAC address-prioritized Portal authentication, MAC address bypass authentication

  • NAC support on different interfaces:
    • MAC address authentication is supported on Layer 2 physical interfaces, VLANIF interfaces, and Eth-Trunk interfaces.
    • 802.1X authentication is supported on Layer 2 physical interfaces and Eth-Trunk interfaces.
    • Different types of interfaces support different Portal authentication modes.Layer 2 physical interfaces support only Layer 2 Portal authentication, and VLANIF interfaces support both Layer 2 and Layer 3 Portal authentication.
    • NAC authentication should not be enabled on both a Layer 2 physical interface and the VLANIF interface corresponding to the VLAN to which the physical interface belongs. Otherwise, users have no network access rights after going online.
    • When Portal authentication or MAC address authentication is configured on a VLANIF interface, it is not recommended that the authentication server and terminals be on the same network segment.
    • When NAC is configured on a main interface, service functions on its sub-interfaces will be affected.
    • You are advised to configure wireless user authentication in a VAP profile instead of on a VLANIF interface.
  • When users go online or are re-authenticated through an inter-board Eth-Trunk interface, resetting one of the boards may disconnect the users.
  • Users who have static MAC address entries configured can obtain network access rights without authentication. If these users need to be authenticated, you need to delete their static MAC address entries.
  • The number of NAC users cannot exceed the maximum number of MAC address entries supported by the device.

MAC Address Authentication

Application limitations in MAC address authentication scenarios:

1. MAC address authentication supports AD/LDAP authentication. By default, the device uses PAP authentication, and AD/LDAP authentication is available on the device without the need to modify the configuration.

2. When the device connects to a ClearPass or an ISE server for MAC address authentication, service-type needs to be set to 10 and the calling-station-id format needs to be set to XX-XX-XX-XX-XX-XX in the RADIUS server template on the device.

3. When the number of MAC address authentication users exceeds the upper limit or users are authorized, for example, users are authorized with ACLs or upstream/downstream CAR, you are advised to manually adjust the CPCAR value for packets triggering MAC address authentication to prevent user login failures or user logouts due to re-authentication.

4. You are advised not to configure authorized VLANs during MAC address authentication. This is because it will prevent static users (such as dumb terminals) from obtaining IP addresses after their VLANs are changed.

5. When MAC address authentication is configured on a VLANIF interface, the authentication server, DHCP server, DNS server, and terminal cannot be on the same network segment. If they are on the same network segment, an authentication-free rule needs to be configured to permit the server source IP address.

802.1X authentication

802.1X application limitations in different scenarios:

1. If the 802.1X client uses MD5 encryption, the user authentication mode on the device can be set to EAP or CHAP.

2. If the 802.1X client uses PEAP authentication, the authentication mode on the device can be set to EAP.

3. The authentication mode for 802.1X users can be set to EAP relay only when RADIUS authentication or local EAP authentication is used.

4. When AAA local authentication is used, the authentication mode for 802.1X users can only be set to EAP termination.

5. When AD or LDAP authentication is used, the authentication mode for 802.1X users must be set to PAP.

6. Terminals such as laptops support EAP termination only after third-party clients are installed.

7. When the account information of 802.1X users is stored on the AD/LDAP server, it is recommended that the device be connected to the RADIUS server and that the RADIUS server be connected to the AD/LDAP server and authenticate terminals through PAP (non-plaintext, RADIUS shared key for encrypted transmission), MS-CHAPv2, or EAP TLS.

8. When the number of 802.1X users exceeds the upper limit or users are authorized, for example, ACLs and upstream and downstream CAR are authorized, you are advised to manually adjust the CPCAR value for 802.1X packets to prevent user login failures or user logouts due to re-authentication.

9. When an 802.1X user is online on an interface, changing the user authentication mode in the 802.1X access profile bound to the interface will disconnect the online 802.1X user.

10. If a Layer 2 switch exists between the device and users, Layer 2 protocol tunneling needs to be enabled on the Layer 2 switch so that 802.1X authentication packets can be transparently transmitted. Otherwise, users cannot be authenticated.

802.1X authentication

For the AR8000 series, AR6700 series, AR5710-H8T2TS1-T, AR5710-S8T2X-LTE4EA, AR5710-S8T2X, AR5710-H2T4PN2X-NRGL, AR5710-S8P2X, AR5710-S8T2S, AR5710-H4T4N2X, AR5710-S10T1X2, AR5710-S8TWDSE-LTE4EA, AR5710-H4T4N2X-LTE4EA, AR5710-H8T2TS1, AR5710-S8P1XDSE-2LTE4EA, AR5710-S8T1XWE-NRGL, AR5710-S8T2XE-LTE4EA-T, AR5710-H2T4N2X-NRGL, AR5710-S8T1XWE, AR5710-S8T2XE:

Application limitations in 802.1X wireless authentication scenarios:

1. When 802.1X+local authentication, 802.1X+AD authentication, or 802.1X+LDAP authentication is performed on a terminal, because the terminal does not support EAP termination authentication (PAP or CHAP), a third-party client (such as H3C iNode client) that supports PAP or CHAP must be used for access authentication. In addition, the security policy of the device must be set to open authentication.

2. If WPA, WPA2, or WPA3 authentication is configured in a security policy template, 802.1X authentication does not support pre-authentication authorization.

3. In 802.1X authentication scenarios, EAP packets are control packets and need to be transmitted to the AC through a CAPWAP tunnel. Therefore, service VLANs must be created on the AC regardless of direct forwarding or tunnel forwarding.

Portal Authentication

Limitations on wired Portal authentication:

1. IPv4 redirect ACLs and IPv6 redirect ACLs cannot be authorized to users using the multi-share authentication mode.

2. In Portal authentication scenarios, users may forge IP addresses for authentication. You are advised to configure attack defense functions such as IP source guard and DHCP snooping to avoid security risks.

3. When Portal authentication is configured on a VLANIF interface, the authentication server, DHCP server, DNS server, and terminal cannot be on the same network segment. If they need to be on the same network segment, an authentication-free rule needs to be configured to permit the server source IP address.

4. When the device has a non-Huawei AC and APs connected (APs and wireless users associate with the AC) and wired Portal authentication is performed for wireless access users, the URL configured using the url-parameter command in the URL template view cannot carry the AC's CAPWAP gateway address (device-ip), AC's MAC address (device-mac), AP's IP address (ap-ip), AP's MAC address (ap-mac), or SSID associated with users (ssid).

5. VLANs cannot be authorized to Portal users after they are successfully authenticated.

Portal Authentication

Limitations on IPv6 Portal access authentication:

1. Layer 3 Portal authentication cannot be performed for IPv6 users.

2. HTTP/HTTPS-based Portal authentication cannot be performed for IPv6 users.

3. Layer 2 Portal authentication using the Portal protocol can be performed using IPv6 addresses.

4. An IPv6 address can be configured for the Portal server, but an IPv4 address must also be specified because the device cannot exchange IPv6 Portal packets with the Portal server.

Portal Authentication

Limitations on Portal authentication in VPN scenarios:

1. HTTP/HTTPS-based Portal authentication cannot be performed in VPN scenarios.

2. 802.1X authentication, MAC address authentication, and external Portal authentication can be performed for users in a VPN but not for users who are in different VPNs but have the same IP address.

3. In a Portal authentication scenario, if a Layer 3 interface is bound to a VPN and a terminal accesses the network from the VPN, the device needs to learn the ARP entry of the terminal. Otherwise, the authentication fails.

Portal Authentication

Limitations on Portal authentication in wireless scenarios:

1. If an ACL is authorized to a wireless Portal user, the ACL is delivered to an AP and takes effect, and the rule deny ip command is configured, then you need to configure the permit rule in the ACL to permit the IP address of the Portal server. Otherwise, the Portal user cannot access the Portal server after being authenticated successfully.

2. VLANs cannot be authorized to Portal users after they are successfully authenticated.

User Management

1. Authentication triggered by any packet has the following limitations:

(1) This function applies only to access devices to reduce device pressure and risks. You are advised not to configure this function on the aggregation device or gateway.

(2) You are advised to limit the number of users on each interface. The recommended value is 10. This prevents attack users on an interface from occupying too many entries on the device.

(3) The scenario with a single MAC address and multiple IP addresses is not supported.

(4) VLANIF access cannot be performed.

(5) MAC address migration cannot be performed.

(6) For the types of packets that cannot trigger authentication, see the description of the specific device model.

2. Limitations on no check of IP address conflicts:

(1) When a static resource group is configured, incorrect matching may occur.

(2) When the command that does not check IP address conflicts is enabled on one template but disabled on the other template, two users with the same IP address can go online through the two templates respectively but their permissions may be incorrectly matched.

3. In user traffic detection and MAC address aging scenarios, ARP probe packets may be incorrectly sent.

4. If an interface is added to or removed from a VLAN due to the configuration change, it is normal that the user is disconnected due to the removal of the interface from the VLAN.

5. Functions including downstream CAR authorization, UCL authorization, ACL authorization, and downlink priority authorization take effect only for known and unknown unicast packets.

6. After a user goes offline, the learned user ARP entry cannot be cleared accordingly.

7. When authentication is configured on a VLANIF interface, MAC address learning in the VLAN is not limited, and dynamic MAC addresses may be learned.

8. When a static MAC address entry is configured for a user, the priority of the static MAC address entry is higher than that of authentication. In this case, the static MAC address entry of the user needs to be deleted.

9. If a user's authentication packet carries a VLAN ID, other VLANs cannot be authorized after the user goes online.

10. NAC users' pre-connection authentication permissions are controlled based on uplink traffic but not downlink traffic.

11. If a user fails the authentication, the user cannot manage the lower-layer devices of the authentication device. In this case, you need to run the free-rule command to configure an authentication-free management VLAN.

12. If the destination IP address accessed by a user is on the same network segment as the user's IP address or is an IP address of the device, redirection may not be triggered.

13. If authorization information (such as ACL, UCL group, VLAN, and redirection ACL group) is not configured on the authorization device, user authorization fails.

14. If the authorization information to be authorized to a user is not supported by the user, the user will be authorized successfully, but the user entry for the unsupported authorization information is not displayed. The function is not supported.

1. Authentication triggered by any packet: STP, VBST, DLDP, GVRP, and Smart Link packets cannot trigger authentication, but other packets can trigger authentication.

2. When authentication is configured on a VLANIF interface, if no user entry exists (the authentication fails or no pre-connection is established), the device permits ARP, DHCP, and ND packets.

3. After a user goes online through an interface, when traffic is sent from a non-authentication interface, the ENP chip does not learn the source MAC address. Layer 3 unicast traffic can be forwarded, but Layer 2 traffic cannot be forwarded.

User Management

Limitations on association between NAC access and DHCP (IPv4/IPv6)

1. The DHCP-assigned addresses will not be released automatically following user logouts (normal or abnormal logouts) (applicable to access through physical interfaces, trunk interfaces, and VLANIF interfaces).

2. In the VLANIF access scenario, DHCP packets are sent only to the DHCP module, which triggers IP address allocation. This is not associated with the NAC authentication result triggered by gratuitous ARP packets sent by users.

3. In the VLANIF access scenario, if the user MAC address entry cannot be learned, traffic cannot be forwarded and no address is allocated.

4. If DHCP and NAC authentication are enabled but triggering through DHCP packets is disabled, DHCP packets are sent to the DHCP module, triggering address allocation.

User Management

VLAN authorization limitations:

1. The following limitations apply to VLAN authorization of users in MAC-base mode:

(1) VLAN authorization can be performed on hybrid interfaces but not on access and trunk interfaces.

(2) If a user packet carries a VLAN tag, the VLAN ID must be the same as the PVID of the interface so that the server can dynamically authorize the VLAN to the user.

2. The following limitations apply to VLAN authorization of users in port-base mode: VLAN authorization can be performed on hybrid and trunk interfaces but not on access interfaces.

3. When STP multi-instance is configured, the authorized VLAN and PVID must be in the same instance. Otherwise, service traffic cannot be forwarded.

4. When the STP mode is set to VBST, the stp edged-port enable command must be run on the authentication interface. Otherwise, the interface is blocked during VBST recalculation after the VLAN is changed, and packets fail to be sent.

5. VLAN authorization cannot be performed for users with double VLAN tagged packets.

6. If an authorized VLAN is manually configured and then an interface is added to the VLAN in tagged mode, the interface is added to the authorized VLAN in tagged mode. If an interface is added to a VLAN in tagged mode and then the VLAN is authorized after a user goes online, the interface is added to the VLAN in untagged mode.

7. You are advised to configure the authorized VLAN on access devices because lower-layer devices cannot dynamically detect the VLAN and allow packets from the VLAN to pass through when the authorized VLAN is configured on aggregation and core devices.

8. When the VLAN from which a user goes online is the same as the authorized VLAN on the interface through which the user goes online, the user can go online successfully. However, when the interface is removed from the authorized VLAN, the user is logged out.

9. If a user terminal obtains an IP address through DHCP, after a VLAN is successfully authorized or the authorized VLAN is changed through CoA, DHCP needs to be manually triggered to apply for an IP address again. The device can enable the terminal to re-apply for an IP address by intermittently disconnecting the authentication interface.

VLAN authorization cannot be performed on a VLANIF interface configured with authentication.

Limitations on the idle-cut function:

The idle-cut function can be configured for wireless users. Because idle duration backup between FAPs and HAPs is not available, after a user roams within an AC or between cloud APs, the user cannot be disconnected based on the configured idle duration.

User Management

Limitations on the multi-share mode:

1. The multi-share mode cannot be configured on a VLANIF interface.

2. In multi-share mode, if the first access user fails to be authenticated and establishes a pre-connection, subsequent access users cannot be authenticated. If the first user may fail to be authenticated, you are advised to disable the pre-connection function (using the undo authentication pre-authen-access enable command) when 802.1X authentication or MAC address authentication is used.

3. In multi-share mode, UCL authorization cannot be performed.

4. In multi-share mode, voice VLAN authorization cannot be performed.

5. In multi-share mode, CAR authorization cannot be performed.

6. In multi-share mode, DSCP authorization and 802.1p authorization cannot be performed.

7. In multi-share mode, user traffic statistics collection cannot be performed.

8. In multi-share mode, redirect ACL authorization cannot be performed.

9. In multi-share mode, idle-cut authorization cannot be performed.

User Management

NAC access authentication has the following limitations:

1. QinQ access cannot be performed.

2. Dot1q access cannot be performed.

3. VLAN mapping access cannot be performed.

4. VLAN stacking access cannot be performed.

5. NAC authentication cannot be enabled on both a Layer 2 Ethernet interface and the VLANIF interface of the VLAN to which the Layer 2 Ethernet interface belongs.

6. Users with the same IPv6 address but from different VPNs cannot all go online.

7. Different values configured using the access-limit user-name max-num command cannot be authorized to the same account.

8. Authentication cannot be triggered by packets carrying three or more VLAN tags.

9. Interface binding authentication is mutually exclusive with the following configurations:

(1) ip-subnet-vlan enable

(2) mac-vlan enable

(3) mac-address limit

(4) mac-address learning disable

10. If NAC authentication is enabled on a physical interface or trunk interface but authentication triggered through DHCPv4/v6 packets is disabled, DHCP packets are sent to the DHCP module. If authentication triggered through ARP packets is disabled, the device still learns ARP entries.

11. ARP and ND learning cannot be triggered when ARP/ND request packets are sent for user aging detection and ARP/ND reply packets are sent from terminals.

12. When a user updates IPv6 addresses and there are 10 addresses, the link-local address is preferentially updated when the user updates IPv6 addresses again.

13. When the MAC address of a user is a virtual MAC address, static MAC address, blackhole MAC address, or multicast MAC address, the user cannot be authenticated.

14. The ARP packets with the source address 0.0.0.0 can trigger authentication, but the IP address in the user table is empty because 0.0.0.0 is an invalid address.

15. During LNP negotiation, NAC users cannot go online before the link type of their connected interface is determined. If the link type of the interface is negotiated again and the negotiation result changes, the NAC users are disconnected.

16. User access through tunnels, such as VXLAN and IPsec tunnels, is not supported.

1. Packets whose destination MAC address is a blackhole MAC address can trigger authentication.

2. This function cannot be used together with the MUX VLAN function.

User Management

Limitations on authorizing ACLs:

1. The ACL ID ranges from 3000 to 3999 (3000 to 3031 for wireless users).

2. The time range and logging configured in ACLs cannot be used to match traffic when IPv4 ACLs and IPv6 ACLs are authorized.

3. The source IP addresses configured in ACLs cannot be used to match traffic when ACLs (IPv4 and IPv6 ACLs) or DACL groups are authorized.

4. Standard ACLs (IPv4 and IPv6 ACLs) take precedence over DACL groups.

1. During IPv6 ACL authorization, when protocol is delivered, only the TCP, UDP, GRE, OSPF, and ICMPv6 protocols can be used to match against packets (for IPv6).

2. During IPv6 ACL authorization, dscp, vpn, tcp-flag, fragment, source-ip, time-range, and logging cannot be used to match against packets.

User Management

Downlink traffic control limitations:

1. When a device functions as a pure Layer 2 edge device, a maximum of one IP phone and one PC can be connected to an interface, and only MAC address authentication and 802.1X authentication are supported.

2. When users have authentication event entries, downlink traffic control does not take effect. You are advised not to configure network access rights for users in each phase before user authentication succeeds.

3. It is recommended that ports be configured as STP edge ports and the number of VLANs to which a port is added not exceed 4 (including authorized VLANs).

4. Downlink traffic control cannot be performed on VLANIF interfaces and routed main interfaces.

5. If bidirectional traffic control is configured, the VBST mode is recommended. After a user goes online, STP is switched to another mode, and traffic is interrupted for a short period of time.

6. Before configuring bidirectional traffic control in MSTP or STP mode, you need to run the stp region-configuration command to specify different VLANs in different instances.

7. Control VLANs of ring networks such as an ERPS ring cannot be used as user VLANs to control downlink traffic.

8. After downlink traffic control is configured, user authentication triggered by any packet does not take effect.

User Management

CAR authorization limitations

The upstream CAR is not limited by ACL resources, but the downstream CAR is limited by ACL resources.

User Management

Limitations on the SSL policy used by NAC:

When an SSL policy is used for NAC services (for example, an SSL policy needs to be referenced for HTTPS-based Portal authentication), nist is automatically added to the elliptic curve parameter of the ECDHE algorithm.
