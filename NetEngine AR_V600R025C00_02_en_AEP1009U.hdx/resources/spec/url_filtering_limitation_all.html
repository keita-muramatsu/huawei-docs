Configuration Precautions for URL filtering

Licensing Requirements

The remote URL query function is controlled by the URL remote query license, but the other functions of URL filtering are not. If the license control item is not activated, the remote URL query service will be unavailable. After the license control item is activated, remote query can be performed. After the remote URL query license expires, the remote URL query service will be unavailable.

URL filtering

If the browser has cached the website home page, the browser will not send access requests to the web server within a short period of time. Instead, the browser uses the locally cached information. In this way, URL filtering may not take effect. Therefore, you are advised to clear the browser cache before using the URL filtering function.

The following lists the common steps for clearing the cache of browsers:

Chrome:

(1) Click the menu button in the upper right corner of the Google Chrome browser.

(2) Click "Delete browsing data".

(3) Select "Time range", select "Browsing history", "Cookies and other site data", and "Cached images and files", and click "Delete data".

(4) Click "Delete data".

Firefox browser:

(1) Click the menu button in the upper right corner of the Mozilla Firefox browser to open the menu, and click "Settings".

(2) Click "Privacy & Security" and scroll down to the "Cookies and Site Data" section.

(3) Click "Clear data" and select "Cached Web content".

(4) Click "Clear". (Optional: Clear cookies or other data.)

Microsoft Edge:

(1) Open Microsoft Edge, click the menu button in the upper right corner of the browser to open the menu, and click "Settings".

(2) In the navigation pane, click "Privacy, search, and services".

(3) In the "Clear browsing data" section, click "Choose what to clear".

(4) Select "Cached images and files". (Other options, such as "Cookies and other site data" and "Browsing history", can be selected as required.)

(5) Select "Time range". ("All time" is recommended for thorough clearing.)

(6) Click "Clear now".

URL filtering

If a session contains multiple URLs, the device performs URL filtering on each URL and blocks the entire session if any one of the URLs is blocked.

URL filtering

The number sign (#) in a URL is used to identify a specific part of a page and provide direct access to a specific location or information fragment. This improves user experience in most cases, especially when users need to quickly jump to a specific part of a web page. The character # takes effect only on the client and is not sent to the server.

If a URL rule contains a number sign (#), the sign itself and the string following it do not take effect during the matching process. Similarly, if a user attempts to access a URL that contains the number sign, the sign itself and the string following it will not be sent to the URL filtering module for URL matching.

URL filtering

Currently, URL filtering cannot filter online-proxied URL requests.

URL filtering

When the incoming and outgoing paths of packets are inconsistent, the device cannot receive all packets of a data flow, and the URL filtering function is unavailable.

URL filtering

For HTTP traffic, URL filtering can extract only the URI and host fields for filtering. When you search for keywords on some websites (such as YouTube), the keywords are not in the URI and host fields but in the Referer field. In this case, the search keyword-based URL filtering function does not take effect.

URL filtering

When the device uses the URL filtering function to perform content security detection on traffic, the performance of the device is affected. Therefore, you need to configure the URL filtering function as required.

URL filtering

To prevent log storms, the content security detection engine merges URL filtering logs by default. Information such as the source port number in the merged logs may be 0.

URL filtering

The product ensures network connectivity based on the service priority principle. As a function component, URL filtering is affected by multiple factors and cannot ensure 100% URL filtering effect. The factors include but are not limited to device performance overload (traffic burst and traffic threshold crossing), resource insufficiency (CPU, memory, and queue channel), performance priority mode, and escape mechanism in resilience scenarios (bypass upon integrated policy timeout, bypass upon protocol decoder exception, and impact of encrypted protocols).

If a single product cannot ensure 100% filtering effect in URL control scenarios (such as monitoring), consider and select a proper end-to-end solution from the perspective of the entire solution.

URL filtering

The encrypted traffic filtering function of URL filtering can process only TLS 1.0 and later versions.

URL filtering supports HTTP and HTTPS. To filter HTTPS URL requests, you also need to configure encrypted traffic filtering. The encrypted traffic filtering function implements URL filtering based on domain names. The domain names of the websites that users access is obtained from the Server Name Indication (SNI) field in the client's Client Hello packets and the Common Name (CN) fields in the server's Certificate packets. Before using the encrypted traffic filtering function to implement HTTPS URL filtering, read the following restrictions:

- In the scenario where a browser proxy exists, when a user accesses some websites, the website domain names extracted by the device from the SNI field in the client's Client Hello packet and the CN field in the server's Certificate packet may not match the actual website domain names. As a result, the URL filtering function does not take effect. For example, when a user uses the UC browser to access the Youku website, the URL filtering function does not take effect due to the cloud acceleration proxy of the UC browser. To solve this issue, you can disable the cloud acceleration function of the UC browser.

- If some browsers transmit data in encryption mode, the URL filtering function may not take effect. For example, Google Chrome uses QUIC by default for data transmission. You can configure a security policy to block QUIC applications.

- The SNI and CN may be different. If only one of them is configured in the whitelist, the whitelist filtering function may not take effect. In this case, you need to add both of them to the whitelist.

- The encrypted traffic filtering function implements URL filtering through SSL handshake packets. The client has not initiated an HTTP request. Therefore, the URL push information cannot be sent.

- If the secure DNS option is enabled in the user browser, the ECH extension option may be used in the SSL handshake phase. In this case, the domain name extracted by the device from the SNI is inconsistent with the actual domain name accessed by the user. As a result, the URL filtering function does not take effect. You need to disable the secure DNS option on the browser or use a security policy on the device to block encrypted DNS traffic and applications.

- URL filtering for encrypted traffic in non-decryption mode does not take effect when Client Hello packets are fragmented in TLS 1.3.

With the development of Internet technologies, more URLs that cannot be accurately filtered using the encrypted traffic filtering function may emerge. The preceding lists only some typical restrictions.

URL filtering

The default HTTP port number is 80, and the default HTTPS port number is 443. If the web server uses the default port, you do not need to configure the port number in an exact URL filtering rule. If the server uses a non-default port, the port number must be specified in the URL filtering rule.

For example, if you want to forbid access to http://www.example.com:8080, set the URL filtering rule to add blacklist url www.example.com:8080.

URL filtering

The host name in the URL accessed by a user is an IP address. In this case, if the IP address does not match any local URL category but perform the remote URL query, the query result is Others because the cloud query server does not classify the IP address. For example, if the URL is http://1.1.1.1/, the cloud query server returns Others.

URL filtering

When the URL remote query function is used, it is recommended that the outbound interface of the route from the device to the remote query server be a service interface. The management interface is used only for management.

URL filtering whitelist control scenarios include:

- Allowing users to access only websites of specified categories or whitelisted URLs

- Whitelist-based URL filtering scenarios

In the preceding scenarios, only the requests to access the URLs that fall into the specified URL category or whitelist are permitted and the requests to access other URLs are all blocked.

When a user accesses a specified URL from a browser, the browser requests to access multiple URLs during web page loading. Not all these requested URLs can match the specified URL category or whitelist. Requests to access the unmatched URLs are blocked. As a result, the web page loaded by the browser may not be completely displayed.

To load the web page completely, you need to add the domain name or URL related to the URL access to the URL whitelist.

URL filtering

During URL category filtering, the device first queries the local cache for the category to which a URL belongs. If no matching category is found, the device queries the remote query server for the URL category, saves the remote query result to the local cache, and records the timestamp of the cache. If the URL category on the remote query server (on the cloud) changes, the device updates the category in the local cache at least 24 hours later.

If you want to update the category immediately, run the undo url-filter cache add all command in the diagnostic view to delete the local cache. Subsequently, the device will query the URL category on the cloud.
