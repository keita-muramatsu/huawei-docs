OSPF loop detection depends on the Opaque capability of OSPF in a process. If the Opaque capability is not enabled, OSPF loop detection does not take effect. In this case, you need to manually enable the Opaque capability of OSPF.

The network types of the interfaces on both ends of an OSPF neighbor relationship must be the same so that the interfaces can learn routes after the neighbor relationship is established. Otherwise, the neighbor relationship cannot be established and routes cannot be calculated.

You are advised to use the same network type at both ends.

OSPF advertises default routes to a stub area only when a neighbor in the Full state exists in the backbone area.

After the device is restarted, if the BFD session status of the local device or neighbor is Admin Down, the OSPF status is not affected. When the BFD session is renegotiated, if the BFD session reports that the detection status is Down but the previously reported detection status is Up, the OSPF sets the neighbor status to Down. In other cases, the OSPF status is not affected.

Constraints on the association between BFD and cost values of OSPF broadcast links

(1) When there is only one neighbor, the neighbor is not deleted when BFD goes Down, and the OSPF LSDB component is notified that the neighbor enters the BFD-associated cost state.

(2) This function is not supported when there are multiple neighbors.

When the number of neighbors changes from one to multiple, the neighbor in the BFD Down state is deleted and the OSPF LSDB component is notified that the neighbor is deleted.

It is recommended that only one neighbor relationship be established on an OSPF broadcast network.

When a device in an NSSA generates an NSSA LSA based on an imported external route, the device preferentially uses the IP address of a loopback interface in the NSSA as the forwarding address (FA). If no loopback interface exists in the NSSA, the device selects the IP address of a non-loopback interface as the FA. As a result, if links have the same cost value, the downstream device will fail to implement load balancing between routes corresponding to the links.

In OSPF loop detection scenarios, incorrect detection may be triggered when a router ID conflict occurs, including intra-AS router ID conflict and inter-AS router ID conflict.

OSPF advertises default routes to an NSSA only when neighbor relationships in the Full state exist in the backbone area or default routes of another protocol or of another OSPF process exist in the same VPN instance, and the nssa default-route-advertise command is run. If the default-route-advertise command is run in an OSPF NSSA, the default LSA is advertised only when the active default route that does not belong to the current OSPF process exists in the IP routing table. If OSPF advertises a default route first, the device does not calculate the default routes from other devices. If OSPF learns a default route first and the route is active, OSPF does not advertise its own default routes. If the current OSPF process does not need to learn default routes from other devices, you need to configure a route-policy to filter out the default routes. If the current OSPF process needs to learn default routes from other devices as backup paths, the priorities of the default routes (required by advertisement of default LSAs) in the IP routing table must be higher than those of OSPF routes. Otherwise, when the device restarts or route flapping occurs, the sequence in which OSPF learns default routes and advertises them may change, which may cause a failure of OSPF in advertising default LSAs or lead to a routing loop.
