Basic OSPFv3 Functions

OSPFv3 advertises default routes to an NSSA only when neighbor relationships in the Full state exist in the backbone area or default routes of another protocol or of another OSPFv3 process exist in the same VPN instance, and the nssa default-route-advertise command is run. If the default-route-advertise command is run in an OSPFv3 NSSA, the default LSA is advertised only when the active default route that does not belong to the current OSPFv3 process exists in the IPv6 routing table. If OSPFv3 advertises a default route first, the device does not calculate the default routes from other devices. If OSPFv3 learns a default route first and the route is active, OSPFv3 does not advertise its own default routes. If the current OSPFv3 process does not need to learn default routes from other devices, you need to configure a route-policy to filter out the default routes. If the current OSPFv3 process needs to learn default routes from other devices as backup paths, the priorities of the default routes (required by advertisement of default LSAs) in the IPv6 routing table must be higher than those of OSPFv3 routes. Otherwise, when the device restarts or route flapping occurs, the sequence in which OSPFv3 learns default routes and advertises them may change, which may cause a failure of OSPFv3 in advertising default LSAs or lead to a routing loop.

Basic OSPFv3 Functions

The network types of the interfaces on both ends of an OSPFv3 neighbor relationship must be the same so that the interfaces can learn routes after the neighbor relationship is established. Otherwise, the neighbor relationship cannot be established and routes cannot be calculated.

You are advised to use the same network type at both ends.

Basic OSPFv3 Functions

1. Loop detection can be implemented for a maximum of 100,000 routes. If the number of LSAs advertised after routes are imported exceeds the upper limit, the LSAs are not advertised.

2. Routes cannot be imported to NSSAs.

3. Summary routes cannot advertise redistribute information.

4. After a routing loop is removed, the device cannot automatically exit the routing loop state. To exit the routing loop state and clear the alarm, you need to run a command.

5. If the redistribute IDs of different devices conflict, a loop alarm may be falsely reported.

6. Loop detection is not supported in the scenario where more than two re-advertisement nodes are configured.

7. Loops may fail to be detected in scenarios where a loop route and a non-loop route advertised by multiple nodes form load balancing in a process.

8. Self-healing is not supported when the original route source is withdrawn and a loop is triggered.

9. Route import between public and private networks is not supported.

10. When detecting a routing loop, a re-advertisement node increases the cost of the route to be re-advertised to eliminate the loop. This may cause the traffic direction to be different from the expected path.

11. When the maximum cost is advertised after a routing loop is detected, the apply cost configuration in a route-policy does not take effect.

12. After this function is enabled, LSAs need to be added for each prefix to advertise extended TLVs, which greatly increases memory usage.

Basic OSPFv3 Functions

If the OSPFv3 neighbor timeout period is too short, the neighbor relationship may easily go Down due to timeout, affecting services.

You are advised to use the default hello timer and dead timer. Alternatively, you can change the value of the dead timer to a value greater than or equal to 40s.

Basic OSPFv3 Functions

OSPFv3 advertises default routes to a stub area only when a neighbor in the Full state exists in the backbone area.

Basic OSPFv3 Functions

After the device is restarted, if the BFD session status of the local device or neighbor is Admin Down, the OSPFv3 status is not affected. When the BFD session is renegotiated, if the BFD session reports that the detection status is Down but the previously reported detection status is Up, the OSPFv3 sets the neighbor status to Down. In other cases, the OSPFv3 status is not affected.
