Feature Requirements

Table 2 Feature requirements

Feature

Feature Requirements

IPv6 IPsec

IPsec 6 over 6 is available in both tunnel and transport modes. IPsec 4 over 6 and IPsec 6 over 4 are available only in tunnel mode.

IPv6 IPsec

IPsec 6 over 6 and IPsec 4 over 6 do not have NAT traversal. IPsec 6 over 4 has NAT traversal, but only ESP can be used for packet encapsulation.

IPsec reliability

In scenarios requiring high IPsec service reliability, such as LTE, you are advised to enable DPD on devices at both ends of an IPsec tunnel in order to rapidly detect and rectify tunnel failures of the remote device. When DPD is enabled on a device and a large number of IPsec tunnels exist on the network, DPD packets are frequently sent and received, which consumes significant CPU resources and leads to deteriorating device performance. To address this issue, run the ike dpd or dpd command to set an appropriate DPD idle time for IKE peers.

- If there are less than 10,000 tunnels, retain the default DPD idle time (30s).

- If there are 10,000 to 20,000 tunnels, you are advised to set the DPD idle time to 45s.

- If there are more than 20,000 tunnels, you are advised to set the DPD idle time to 60s.

IPsec reliability

It is recommended that the MTU of the interface to which an IPsec policy group is applied be greater than or equal to 256 bytes. As IP packets become longer after IPsec processing, a small MTU results in the interface dividing a large IP packet into multiple fragments, which may not be properly received or processed by the remote device.

IPsec reliability

In AH encapsulation mode, the DF bit of an inner packet is inherited to the outer packet and used together with the DF flag bit of the outer packet to calculate the checksum of the packet. If the remote end of the tunnel removes the DF bit from the outer packet and then calculates the checksum, the checksum on both ends of the tunnel will be inconsistent, resulting in both ends being unable to communicate with each other. To prevent this problem, run the ipsec df-bit clear command to ensure that the checksums on both ends of the tunnel are the same.

IPsec reliability

Fragmentation before encryption is not supported when the IPsec encapsulation mode is transport.

IPsec profile

In the DSVPN over IPsec scenario, multiple mGRE tunnel interfaces on a spoke or the hub cannot be configured with the same source interface or address. Otherwise, only one tunnel can be established.

IPsec profile

After an IPsec profile is bound to a tunnel, modifying the source or destination address of the tunnel will unbind the IPsec profile from the tunnel.

IKE negotiation

Digital envelope authentication of Chinese cryptographic algorithms is defined by State Cryptography Administration of China and can be used only for IKEv1 negotiation in main mode. It cannot be used for IKEv1 negotiation in aggressive mode or for IKEv2 negotiation.

IKE negotiation

SM3 and SM4 can be used only in IKEv1 negotiation.

IKE negotiation

By default, the device does not support SA negotiation through IKEv1. To use IKEv1 functions, you need to load the IKEv1 feature package. Log in to Huawei technical support website, search for the corresponding product and version in the software download area, and download IKEV1_V600R0XXCXX.ccx. For details about how to install the plug-in, see "Configuring the Feature Software Package" in "Upgrade Maintenance Configuration" in Configuration Guide > System Management Configuration.

IKE negotiation

The DH group value affects the IKE negotiation performance (such as the tunnel setup rate). A larger DH group value results in a greater impact on the IKE negotiation performance (for example, the tunnel setup rate decreases significantly).

IKE negotiation

If IKE uses certificates for negotiation, it is not recommended that the key usage of the local certificate support certificate signing. If certificate signing is supported, the following requirements must be met. Otherwise, the negotiation will fail.

1. If the certificate contains the Basic Constraints extension, the Subject Type of the extension cannot be CA.

2. If the certificate does not contain the Basic Constraints extension, the certificate cannot be a self-signed root certificate of V1 or contain the special CA flag of Netscape.

IPsec deployment

The QoS function is not recommended in IPsec scenarios because IPsec negotiation may be interrupted.

IPsec deployment

IPsec is not recommended on networks where the source or destination address of a plaintext packet is the device's address and the forward and return paths are asymmetric. The encryption tunnel for forward packets is different from the decryption tunnel for reverse packets, which may cause packet loss.

IPsec deployment

The use of the SHA2-384 or SHA2-512 algorithm will deteriorate IPsec performance.

IPsec deployment

After the device is switched to the FIPS mode, weak security algorithms cannot be used even if the weak security algorithm/protocol feature package WEAKEA is installed.

IPsec deployment

When configuring IPsec data flows to be encrypted, configure refined ACL rules (but not loose ACL rules) based on services to prevent service interruptions caused by unnecessary data flows entering the encryption tunnel.

IPsec deployment

In IPv6 scenarios, to encrypt packets sent by the local device using IPsec, run the route inject nexthop command to set the next hop to the IPv6 address of the interface directly connected to the local device.

IPsec deployment

In transport mode, the flow information generated after IPsec negotiation must be consistent with an IPsec tunnel address, which is a 32-bit host address.

IPsec deployment

IPv6 IPsec cannot provide the following functions:

- IPsec transparent mode

- IPsec fragmentation before encryption

- IPsec using IPv6 IPsec profiles

- Invalid SPI recovery for IPsec

- Network resource push

- Detection of overlapping IPsec flows

IPsec deployment

An IPsec policy cannot be applied to a tunnel interface configured with both IPv4 and IPv6 addresses, as an IPsec tunnel cannot be established on such an interface. As such, ensure that only an IPv6 address is configured for the tunnel interface before applying an IPv6 IPsec policy to the interface. If an incorrect configuration is delivered and causes both IPv4 and IPv6 addresses to be configured on the tunnel interface, you need to delete the IPv4 address and IPv6 IPsec policy from the tunnel interface and then reapply the IPv6 IPsec policy to the tunnel interface. The interval between deleting the IPv6 IPsec policy and reapplying the IPv6 IPsec policy must be longer than 5s. Otherwise, the IPv6 IPsec policy does not take effect.

IPsec deployment

If a NAT device is deployed on an IPsec tunnel, NAT traversal cannot be disabled and only ESP can be used as the security protocol.

IPsec deployment

To establish multiple tunnels between two devices, use different tunnel source addresses to prevent these tunnels from flapping.

IPsec deployment

If the device establishes an IPsec tunnel with the remote gateway based on an IPsec policy template, it is recommended that the IPsec SA aging time configured on the device be 15% longer than that on the remote end. If the IPsec SA aging time configured on the device is shorter than that on the remote end, the IPsec SA on the device expires first, triggering the negotiation of the new IPsec SA on the device. If a new IPsec SA cannot be negotiated within a certain period, the device deletes the old IPsec SA, disconnecting the IPsec tunnel and leading to service forwarding failures.

IPsec deployment

In route injection scenarios, if the destination IP address of a non-IPsec-protected data flow matches the OPR route injected by IPsec, run the route inject nexthop command to specify the next hop of the route. Otherwise, the data flow may be discarded.

IPsec deployment

When the number of IPsec tunnels on the device is greater than 50% of the maximum, running the undo ipsec policy or undo ipsec profile command may cause a high CPU usage alarm on the device for a short period. After all SAs are deleted, CPU usage returns to the normal range.

IPsec deployment

It is not recommended that IPsec be deployed on both tunnel interfaces and other interfaces. When IPsec is deployed on both a tunnel interface and another interface and the device functions as the negotiation responder, it first matches encrypted data flows against the IPsec configuration on the tunnel interface. If the match fails, the device matches encrypted data flows against the IPsec configuration on the other interface.

IPsec deployment

It is recommended that original packets not exceed 1500 bytes before entering an IPsec tunnel, as jumbo packets may fail to enter an IPsec tunnel for encrypted transmission.

IPsec deployment

In an IPsec scenario, if the device needs to return an ICMP error packet in response to a packet from the initiator, the source IP address of the ICMP error packet is not the destination IP address of the initiator's packet, and is instead the interface IP address of the device, then an ACL needs to be configured for the ICMP error packet so that the packet can enter the IPsec tunnel. For example, in a scenario where a base station connects to the device, if the length of an IPv6 service packet after IPsec tunnel decryption is greater than the IPv6 MTU of the outbound interface, the device needs to send an ICMP error packet to the base station. In this case, you need to configure an ACL (with the source address being the IP address of the outbound interface) for the ICMP error packet, in order for the packet to enter the IPsec tunnel. If no ACL is configured for the ICMP error packet, the packet cannot be transmitted to the base station through the tunnel, leading to a service exception.

IPsec deployment

The parameter settings of the security protocol, authentication algorithm, encryption algorithm, and packet encapsulation mode on devices at both ends of an IPsec tunnel must be the same during the configuration of an IPsec proposal. Otherwise, tunnel negotiation will fail. If the PFS algorithm is configured, ensure that both devices use the same PFS algorithm. Otherwise, tunnel negotiation will fail.

IPsec deployment

In IPsec tunneling scenarios, the IP addresses configured using the remote-address and acl rule destination commands cannot be the same. Otherwise, tunnel negotiation or service traffic encryption and decryption may be abnormal due to incorrect route selection.

IPsec deployment

The protocol types defined in the ACL rules on both ends of an IPsec tunnel must be consistent. For example, if one end uses the IP protocol, the other end must also use the IP protocol.

IPsec deployment

If multiple IPsec policy groups are bound to different tunnel interfaces and these tunnel interfaces borrow the IP address of the same physical interface, two devices can perform IPsec negotiation successfully only when the policies in the first bound IPsec policy group are used for the negotiation.

IPsec deployment

On an IPv6 network, when packets such as detection and monitoring packets of an IPsec tunnel need to be transmitted over the tunnel, the corresponding ACLs need to be configured for these packets.

IPsec deployment

When an IPsec profile is configured on a tunnel interface, negotiation can be initiated normally even if the tunnel interface goes down. If the interface is brought down due to the shutdown or Keepalive configuration, negotiation can still be initiated. This prevents an interface from being brought down due to peer unreachability detected by Keepalive packets in GRE over IPsec scenarios.

IPsec deployment

In IKEv1 scenarios, it is not recommended that one end use an ISAKMP IPsec policy and the other end use an IPsec profile for negotiation.

This is because, in IKEv1 scenarios, the data flows to be protected by IPsec on one end must either mirror those on the other end or be a subset of those defined by the responder. When one end uses an ISAKMP IPsec policy, an ACL must be configured to define the data flows to be protected. However, if the other end uses an IPsec profile, no ACL is needed, meaning that this end protects all data flows using IPsec.

Consequently, if the end using an IPsec profile initiates the negotiation first, the protected data flow range of the initiator may not be a subset of that of the responder, leading to tunnel negotiation failure.

In this scenario, ensure that the source and destination addresses in the ACL configured in the ISAKMP IPsec policy are all any.

IPsec NAT traversal

IKE negotiation packets are preferentially forwarded when the device is overloaded. In NAT traversal scenarios, if the port number used for IPsec NAT traversal is set to a user-defined port number (not 4500), the forwarding priority of IKE negotiation packets cannot be guaranteed. You are advised to use the default port number (4500) for IPsec NAT traversal.

Tunnel overlapping

Only unicast protocol packets (such as GRE, NHRP, and BGP packets) forwarded by the CPU can be forwarded through IPsec tunnels. Multicast and broadcast packets (such as IS-IS, OSPFv3, RIP, and RIPng packets) and all unicast protocol packets that are not forwarded by the CPU cannot be forwarded through IPsec tunnels.

Tunnel overlapping

In a DSVPN over IPsec scenario, if a NAT device is deployed, you are advised to set the IPsec encapsulation mode to transport. If two spokes are situated behind different NAT devices or the hub is situated behind a NAT device, the IPsec encapsulation mode can only be transport.

IPsec policy

When an IPsec policy references an ACL, rules must be configured in the ACL view, and the number of ACL rules configured for all IPsec policies in a single IPsec policy group cannot exceed 5,000. Otherwise, the IPsec policy cannot reference the ACL. In addition, when a large number of rules are configured in the ACL and service traffic is transmitted over the tunnel, modifying the last several rules will temporarily increase CPU usage. As such, you are advised to modify ACL configurations during off-peak hours.

IPsec policy

An IPsec policy group cannot reference both ACLs and ACL6s.

IPsec policy

Only one IPv6 address can be configured for the tunnel interface to which an IPv6 IPsec policy is applied.

IPsec policy

If the source and destination addresses in an ACL rule are specified using address pools (source-pool and destination-pool), the ACL cannot be referenced in an IPsec policy or IPsec policy template if the number of addresses or address segments (ip-address) in the address pools exceeds 32. If an ACL has been referenced by IPsec, addresses can be added to the address pool referenced by the ACL rule. If the number of addresses or address segments (ip-address) in the address pool exceeds 32, the excess addresses or address segments cannot be matched.

IPsec policy

If the packets received by the interface to which an IPsec policy group is applied match destination NAT, the IPsec configuration may not take effect because the device performs NAT-related configurations first. You can solve the problem in the following cases:

- If only IPsec but not NAT needs to be performed on the packets, you need to create a NAT policy, set the destination IP address in the matching condition of the NAT policy to the destination IP address in the ACL rule referenced by the IPsec policy, and set the action to no-nat.

- If only NAT but not IPsec needs to be performed on the packets, do not set the destination IP address in the ACL rule referenced by the IPsec policy to a post-NAT IP address.

- If both IPsec and NAT need to be performed on the packets, set the destination IP address in the ACL rule referenced by the IPsec policy to a post-NAT IP address.

IPsec policy

It is not recommended that the same 5-tuple be configured for branches and that the branches be distinguished only based on their DSCP priorities. This is because return traffic cannot be forwarded from the headquarters to the branches under such a configuration.

IPsec policy

The ACLs referenced by IPsec policies in an IPsec policy group cannot contain the same rules, and rules cannot overlap. Rules with overlapping address segments may affect each other, which can cause data flows to incorrectly match rules or lead to IPsec tunnel flapping.

IPsec policy

The remote addresses configured in all IPsec policies in an IPsec policy group applied to an interface cannot overlap. If the remote addresses overlap, only the IPsec policy with the smallest sequence number takes effect.

IPsec policy

If multiple IPv6 addresses are configured on an interface bound to an IPsec policy and no local IP address of the IPsec tunnel is specified in the IPsec policy using the tunnel local command, the device uses the lowest IPv6 address configured on the interface for tunnel negotiation.

IPsec security

For security purposes, you are advised not to use the weak security algorithm or weak security protocol provided by this feature. If necessary, run the install feature-software WEAKEA command to install the weak security algorithm or protocol feature package WEAKEA.

IPsec security

Only SAs dynamically negotiated using IKE support the anti-replay function.

IPsec security

If IPsec check is configured, the device checks whether the IP header of the decrypted IPsec packet is in the range defined by a specific ACL. If the decrypted IPsec packet matches the permit clause in the ACL, the device continues to process the packet. Otherwise, the device discards the IPsec packet.
