Feature Requirements

Feature

Feature Requirements

IFIT by Insertion Head

When a device enabled with IFIT globally receives a large number of invalid IFIT packets, the generation of dynamic IFIT instances may be affected, but the IFIT instances that have been dynamically created are not affected.

IFIT by Insertion Head

Application-level IFIT and tunnel-level IFIT cannot be both configured for the same packet. If tunnel-level measurement and application-level measurement are configured on the same device, application-level measurement takes precedence over tunnel-level measurement. If tunnel-level measurement and application-level measurement are configured on different devices, the measurement type carried in the outer IFIT header takes effect. Application-level measurement flows are not displayed in tunnel-level IFIT measurement results.

IFIT by Insertion Head

Since the IFIT measurement solution depends on timer sampling, the actual measurement time is different from the specified measurement interval. Therefore, when the IFIT measurement data is used to calculate the flow rate, the average rate of packets within a measurement interval is inaccurate.

IFIT by Insertion Head

The sum of the forwarding delay and processing delay of IFIT packets varies on each node, causing the start time of IFIT statistics on the ingress node to be different from that on other devices. As a result, the first period of IFIT statistics on the egress node may be the second period of IFIT statistics on the ingress node, causing the third period of E2E IFIT statistics to be inaccurate. In the first two periods of each instance, error information is reported to iMaster NCE or MCP for data filtering. The third period of the ingress node, however, corresponds to the second period of the egress node. Therefore, data collected during the third period is filtered out by iMaster NCE or MCP due to error information reported by the egress node. Services need to be planned properly. Otherwise, the third period of E2E IFIT statistics is inaccurate and is filtered out on iMaster NCE or MCP.

IFIT by Insertion Head

IFIT does not support hop-by-hop measurement in SD-WAN/SRv6-over-other-tunnel scenarios. In these scenarios, IFIT headers can be encapsulated normally, but no hop-by-hop measurement data is available for the tunnel-over-tunnel segment (including SRv6 over GRE, SRv6 over IPsec, and SD-WAN over IPsec scenarios), which is considered as one hop.

IFIT by Insertion Head

When the tunnel on the public network is an SRv6 tunnel, penultimate segment pop of the SRH (PSP) is configured, packet carry the IFIT header, and IFIT measurement is enabled on the device, the PSP does not take effect and the USP action is performed by default.

IFIT by Insertion Head

When an SRv6 tunnel is configured as the public network tunnel, PSP is configured, and the penultimate hop device is a non-Huawei device, a Huawei device with no IFIT configured, or a Huawei IFIT-capable device with IFIT disabled, IFIT statistics on the egress node are not collected.

IFIT by Insertion Head

In the upstream instance of the IFIT ingress node, statistics about packets discarded due to invalid entries, for example, interface entries, before the IFIT measurement process starts cannot be collected. The configurations need to be properly planned.

IFIT by Insertion Head

In IFIT delay measurement, only one packet is colored in each interval. When packet loss occurs, there is a possibility that packets for delay measurement are discarded. As a result, there is no delay measurement data.

IFIT by Insertion Head

The aging time of IFIT dynamic instances can be set to 10 minutes (if the measurement interval is 2s, 10s, 30s, and 1 minute) and 50 minutes (if the measurement interval is 5 minutes). After the multiplier is configured, the aging time is the multiplier multiplied by the measurement interval. Dynamic flows on the ingress, transit, and egress nodes need to be aged after a period of time. If the number of dynamic instances reaches the upper limit, resources may not be obtained for a new instance before dynamic instances are automatically aged. As a result, no new dynamic flow instance can be generated.

IFIT by Insertion Head

If a packet needs to be fragmented, IFIT measures only the first fragment. Therefore, the number of packets is accurate, but the number of bytes may be inaccurate. If packets on transit and egress nodes are discarded, the IFIT packet loss measurement is normal. However, the actual traffic statistics show that packet loss occurs and the failure point cannot be located.

IFIT by Insertion Head

When the configuration in an IFIT instance changes or the ingress node restarts, the data in several periods may be inaccurate or no measurement data is obtained. The details are as follows:

1. For static instances, the measurement period or mode is changed and the flow ID remains unchanged.

2. The measurement period or mode for the whitelist corresponding to dynamic 5-tuple instances is changed, the dynamic 5-tuple instances are deleted and then created, and the flow ID changes.

3. For dynamic 5-tuple instances, the measurement period or mode is changed and the flow ID remains unchanged.

You need to properly plan service networking configurations to prevent inaccurate IFIT measurement.

IFIT by Insertion Head

Flow characteristics cannot conflict on the IFIT ingress node. If flow characteristics conflict (for example, the characteristics of one measurement instance include or overlap those of another measurement instance), the IFIT measurement results may be inaccurate. Avoid this scenario during service planning.

IFIT by Insertion Head

When IFIT interworks with native-IP IFIT, ensure that clocks of all involved devices are synchronized, intervals for IFIT and native-IP IFIT are the same, and the global color bits configure for native-IP IFIT are the same.

IFIT by Insertion Head

If the forwarding path changes (for example, FRR or hard convergence occurs) during IFIT measurement, the measurement data within one or two intervals after the switchover is inaccurate.

IFIT by Insertion Head

IFIT measurement supports SRv6 policy, SRv6 BE, and SD-WAN tunnels, but does not support other types of tunnels. (For tunnels that are not supported, no extension header is added and statistics are not collected after IFIT is configured.) Services need to be planned properly. Otherwise, no IFIT measurement result is displayed.

IFIT by Insertion Head

When an IFIT header is added on the ingress node but removed on the egress node, statistics on terminated packets (including but not limited to BFD, NQA, and other packets sent to the CPU) cannot be collected on the outbound interface of the egress node. As a result, IFIT packet loss statistics are incorrect.

IFIT by Insertion Head

NTP needs to be configured for IFIT measurement, and one-way delay measurement is unavailable if common-precision NTP is configured. A clock source (without an upstream device) cannot be configured on an IFIT device. During clock switchover, IFIT measurement result is inaccurate. Services need to be planned properly; otherwise, IFIT measurement result is inaccurate.

IFIT by Insertion Head

When SRv6 BE tunnels are used as public network tunnels and IFIT is configured, the paths for load balancing change due to protocol encapsulation changes. The load balancing effect is not affected.

IFIT by Insertion Head

When ACLs are added or deleted using the ACL-based IFIT function, the static 5-tuple IFIT measurement instances on the ingress node and the whitelist function become unavailable for a period of time. This is because the ACL mechanism of the product does not support the function of dynamically adding rules. You need to delete all existing ACL rules and deliver them again. Operations that may cause IFIT ACL changes include but are not limited to the following: static 5-tuple IFIT configuration change, whitelist rule change, and change of trunk member interfaces bound to the whitelist. Services need to be properly planned to ensure that the IFIT function is available.

IFIT by Insertion Head

In a scenario where IFIT monitors an SRv6 policy list, IFIT measurement cannot be performed for locally sent packets on the tunnel ingress through the upper-layer protocol.

IFIT by Insertion Head

IFIT measurement instances support only Eth-Trunk member interfaces, VLANIF member interfaces, and physical main interfaces as inbound and outbound interfaces. Static instances on the in-point node can be restricted using commands, but those on the mid-point and out-point nodes cannot be restricted using commands. During the measurement, if an unsupported interface is bound or traffic passes through an unsupported interface, no IFIT instances or statistics are generated. IFIT instances and statistics on a sub-interface are generated based on its main interface. Services need to be planned properly. Otherwise, no IFIT measurement statistics are displayed.

IFIT by Insertion Head

If the hub and spoke devices are the ingress and egress PEs of an SRv6 TE Policy, the SIPv6 address obtained on the egress node is the IP address of the ingress node of the SRv6 TE Policy. If the Policy tunnel is only one segment of the public network tunnel, the SIPv6 address obtained from the packet is not the IP address of the ingress node. In this case, the MCP local path calculation function cannot be used. For example, for the PE1--P2--P3--PE4 path, if the Policy tunnel is established between P2 and P3, the MCP local path calculation function cannot be used, and the function can be used only when the tunnel is established between PE1 and PE4.

IFIT by Insertion Head

IFIT cannot correctly collect statistics on ICMP tracert packets. Tracert uses TTL-exceeded packet discarding as the trigger source, and some packets do not leave the IFIT network. Therefore, when tracert packets enter the IFIT network, the number of packets counted by the egress PE is less than the number of packets counted by the ingress PE. As a result, packet loss due to incorrect statistics collection occurs.

IFIT by Insertion Head

When IFIT interworks with native-IP IFIT, the interworking configuration on the egress node is based on interfaces, regardless of whether the instances on the ingress node are statically configured or dynamically generated. That is, the interworking action is performed for all IPv4 traffic passing through the interface on the IFIT egress node configured with the interworking function. In addition, IPv4 instances of the interworking type on the egress node are displayed. Services need be properly planned to ensure that the IFIT measurement instances on the interface of the IFIT egress node configured with the interworking function belong to services requiring the interworking function.

IFIT by Insertion Head

IFIT does not support broadcast and multicast traffic statistics collection. In multicast scenarios, multiple copies of traffic statistics are collected, causing excess packets or inaccurate statistics. The multicast and broadcast IP addresses are restricted, and IFIT measurement traffic cannot be copied for broadcast. Services need to be properly planned. Otherwise, IFIT measurement is inaccurate.

IFIT by Insertion Head

For an IP 5-tuple IFIT measurement instance over an SD-WAN tunnel, if the egress node does not support IFIT for the SD-WAN tunnel, the IFIT function does not take effect. Properly deploy services and ensure that the egress node must be a device that supports IFIT for SD-WAN tunnels.

IFIT by Insertion Head

The IFIT statistics are inaccurate during DDR isolation, which last for one or two measurement intervals.

Basic IFIT Functions

The port range cannot be configured for the 5-tuple of a static IFIT instance.

Basic IFIT Functions

The following limitations apply to scenarios where IFIT is deployed to measure the quality of an SRv6 TE Policy:

1. If the encapsulation source-address ipv6-address configuration in the SRv6 view changes, the involved tunnel-level IFIT instance is deleted and reestablished, regardless of whether an MCP is configured.

2. If no encapsulation source-address ipv6-address configuration is available in the SRv6 view or the configured address is unreachable, MCP calculation cannot be used.

3. IFITMCP calculation is supported only when IFIT instances are generated on the ingress and egress of a tunnel.

4. If an SRv6 TE Policy is unidirectional, IFIT does not send the calculation result to the SRv6 TE Policy.

5. In scenarios where a large number of IFIT instances are deployed, only ow-performance boards do not support 2s measurement.

6. When the CPU usage exceeds the threshold, SLA calculation is not performed.

Basic IFIT Functions

1. IFIT does not allow MCP-based calculation to be performed for BFD packets in BFD For EVPN VPWS over SRv6 scenarios.

2. In MCP-based computation for U-BFD for SRv6 tunnel scenarios, the TE IPv6 router ID configured using the te ipv6-router-id command must be the same as the source address configured using the encapsulation source-address ipv6-address command. Otherwise, the MCP cannot compute the SLA result of BFD packets.

Typical configuration:

[HUAWEI] display this

te ipv6-router-id 2001:DB8:1::1

[HUAWEI-segment-routing-ipv6] display this

segment-routing ipv6

encapsulation source-address 2001:DB8:2::2

3. In the scenario where IFIT is used to monitor an SRv6 TE Policy list and the MCP is used for statistics collection, if the insert encapsulation mode is used for the SRv6 TE Policy and the source IPv6 address of the traffic is not the address of the ingress of the tunnel, MCP calculation is incorrect.

Typical configuration:

[HUAWEI-segment-routing-ipv6-policy-policy1] display this

encapsulation-mode insert

[HUAWEI-segment-routing-ipv6] display this

segment-routing ipv6

encapsulation source-address 2001:DB8:2::2

The source address of traffic is 2001:DB8:1::1.

4. In the scenario where U-BFD return packets are forwarded over a tunnel, if the egress timestamp and ingress timestamp are on the same device, the return delay of the instance is used as the two-way delay of the two-way instance, and the return delay divided by 2 is used as the one-way delay of the two-way instance. If no two-way instance exists, this processing is not performed.

5. In the scenario where U-BFD return packets are forwarded over a tunnel and no background traffic exists, the calculation depends on timeout. Due to the precision problem of the timer, the jitter in some periods may fail to be calculated in the 2-second measurement instance. The period is not notified to the Policy, which does not affect the switchover.

6. In the scenario where only U-BFD return packets are forwarded over a tunnel, the calculation starts only after no packet loss occurs for the first time.

7. When the egress has an interface board without IFIT Policy measurement capabilities, the MCP cannot calculate statistics.

Basic IFIT Functions

When IFIT measurement is performed for an SRv6 TE Policy list, if the list stack contains up to the penultimate hop End.X SID for public network traffic (including BFD packets for the SRv6 TE Policy list), the SRH is removed because the SL value is 0. As a result, an IFIT egress instance is generated on the penultimate hop. MCP statistics calculation is not supported in this scenario.
