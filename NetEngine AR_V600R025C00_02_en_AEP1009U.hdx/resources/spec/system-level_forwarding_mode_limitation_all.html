Hardware-based Routing and Forwarding

For the AR5710-H4T4N2X, AR5710-H8T2TS1-T, AR6710-L8T3TS1X2, AR6710-L8T3TS1X2-T, AR5710-H2T4PN2X-NRGL, AR5710-H4T4N2X-LTE4EA, AR5710-H8T2TS1, AR5710-H2T4N2X-NRGL:

1. After the hardware route-forwarding qos enable command is configured, only some IPv4 QoS services in traditional scenarios can be accelerated by hardware (IPv6 QoS services and tunnel-related QoS services cannot be accelerated by hardware).

2. After hardware-based QoS acceleration is enabled, hardware queues, ACLs, and WRED profiles are used. The number of these resources is less than that used for software-based forwarding. The configuration that require excess hardware resources will not take effect. In addition, software-based forwarding is performed for services that do not support hardware-based routing. HQoS, traffic shaping, congestion avoidance, and congestion management still use hardware resources.

3. After hardware-based QoS acceleration is enabled, the precision of hardware-based traffic management is 3%.

4. If an HQoS (including CBQ) policy is applied to an interface, the sum of CIRs of user queues must be less than or equal to the interface bandwidth. Otherwise, the CIR of each user queue cannot be ensured.

5. When the hardware QoS acceleration function is enabled or disabled, a small number of packets are lost. If queue statistics collection is enabled, the queue statistics will be affected.

6. Traffic of MQC services is forwarded based on software in the following sequence: traffic statistics collection, re-marking, flow mirroring, packet filtering, traffic queue or user queue reference, sub-policy, traffic policing, and redirection. The order in which sub-policies are executed is the same as that of parent policies. Services take effect immediately (except for the processing of referenced flow queues or user queues).

Hardware-based forwarding applies to MQC services in the inbound direction in the following sequence: flow mirroring (only matching), re-marking, traffic statistics collection, traffic policing, flow queue or user queue reference, packet filtering or redirection, and sub-policy.

Hardware-based forwarding applies to MQC services in the outbound direction in the following sequence: traffic statistics collection, traffic policing, flow mirroring (only matching), re-marking, flow queue or user queue reference, packet filtering, and sub-policy. Sub-policies are executed in the same sequence as that in the outbound direction. The flow mirroring service is executed after all services are executed.

The main differences between software-based and hardware-based MQC are as follows:

(1) If both the parent and child policies are configured with mirroring, the child policy takes effect in hardware-based forwarding scenarios, and both the parent and child policies take effect in software-based forwarding scenarios. Two copies of packets are replicated.

(2) If flow mirroring, redirection, and packet filtering are configured, in hardware-based forwarding scenarios, mirroring takes effect only in the inbound direction; in software-based forwarding scenarios, mirroring takes effect in both inbound and outbound directions.

(3) If flow mirroring and traffic policing are both configured, all packets are mirrored in software-based forwarding scenarios, and the packets after traffic policing are mirrored in hardware-based forwarding scenarios.

(4) If MQC is configured on both the inbound physical and logical interfaces, the software-based forwarding process executes MQC on the physical interface first and then on the logical interface, whereas the hardware-based forwarding process executes MQC on the logical interface first and then on the physical interface. The execution results are different.

(5) Hardware-based forwarding supports redirection only in the inbound direction.

(6) If fragmentation is configured for the outbound interface, and MQC-based traffic statistics collection, traffic policing, or interface-based traffic policing is configured in the outbound direction at the same time, the collected MQC-based traffic statistics are the packet length and number of packets before fragmentation, and traffic policing is performed based on the packet length and number of packets before fragmentation.

(7) In hardware-based forwarding scenarios, if an MQC policy based on Layer 4 information (such as the port number and TCP flag) is configured and packets are fragmented on the network, the MQC policy does not take effect. This is because packet fragments other than the first fragment do not carry port information. To apply an MQC policy to all packet fragments, you are advised to configure an IP address-based MQC policy.

7. Hardware-based acceleration is not supported for the following QoS functions: priority mapping, intelligent policy-based routing, SaaS traffic steering, MPLS QoS, IPv6, and tunnel QoS. Hardware-based acceleration is not supported for the following QoS functions in IPv4:

MQC:

- Traffic classifier: matching conditions including the inbound interface, application type, application group type, and TTL-based ACL (the traffic behavior does not take effect after this condition is configured)

- Traffic policy: specifying a traffic policy as the preferential policy (specifying the first process parameter)

- Traffic behavior: specifying the percentage of the CIR to the interface bandwidth (the car cir pct command) and redirection in the outbound direction

Traffic policing: hierarchical traffic policing, traffic policing based on IP addresses, and CAR after decapsulation

Traffic shaping and traffic policing: configuring a device not to add the interpacket gap and preamble lengths in rate calculation in traffic policing and interface rate limiting, configuring QoS profiles, and configuring loopback after traffic shaping

HQoS: hierarchical CAR HQoS

Congestion management: configuring the scheduling mode of interface queues and configuring the drop mode for a WRED drop profile

8. The following QoS services are supported:

(1) MQC services:

Traffic classifier: matching conditions including link-layer rules (Layer 2 rules), network-layer rules (Layer 3 rules), transport-layer rules (Layer 4 rules), ACL rules, and the rule for matching all packets

Traffic behavior: packet filtering, traffic statistics collection, packet redirection, packet re-marking, traffic policing, and flow mirroring

Traffic policy: pre-processing policies on Ethernet physical interfaces, Ethernet sub-interfaces, Eth-Trunk interfaces, Eth-Trunk sub-interfaces, cellular interfaces, dialer interfaces, VLANIF interfaces, VDSL interfaces, and VDSL sub-interfaces

(2) Packet redirection

- Redirection to a specific next hop (inbound) and redirection to primary and secondary next hops (inbound)

- Associating NQA, VRRP, or routing with next-hop redirection

- Redirection to a dialer or cellular interface

(3) Traffic policing and traffic shaping

- Supports srTCM and trTCM CAR algorithms.

- Supports traffic policing on Ethernet physical interfaces, Ethernet sub-interfaces, Eth-Trunk interfaces, Eth-Trunk sub-interfaces, VLANIF interfaces, cellular interfaces, dialer interfaces, VDSL interfaces, and VDSL sub-interfaces.

- Supports queue shaping, interface rate limiting, and traffic statistics collection on Ethernet physical interfaces, Ethernet sub-interfaces, Eth-Trunk interfaces, Eth-Trunk sub-interfaces, cellular interfaces, dialer interfaces, VDSL interfaces, and VDSL sub-interfaces.

- Supports link-layer rate limit compensation for packets.

(4) Congestion avoidance and congestion management

- Supports tail drop.

- Supports the configuration of WRED profiles and queue buffer sizes on Ethernet physical interfaces, Ethernet sub-interfaces, Eth-Trunk interfaces, Eth-Trunk sub-interfaces, cellular interfaces, dialer interfaces, VDSL interfaces, and VDSL sub-interfaces.

(5) HQoS

- Supports the configuration of CBQ and HQoS policies on Ethernet physical interfaces, Ethernet sub-interfaces, Eth-Trunk interfaces, Eth-Trunk sub-interfaces, cellular interfaces, dialer interfaces, VDSL interfaces, and VDSL sub-interfaces.

- Supports the configuration of flow queues, user queue profiles, and QoS parameters for flow queues and user queues.

- Supports the configuration of scheduling modes between user queues and flow queues.

- Supports the configuration of an HQoS sub-policy in a traffic behavior.

- Supports the configuration of a flow queue profile and a user queue profile in a traffic behavior.

- Supports scheduling between flow queues and user queues.

(6) Priority mapping

- Supports the configuration of port priorities.

Hardware-based Routing and Forwarding

For the AR5710-H4T4N2X, AR5710-H8T2TS1-T, AR6710-L8T3TS1X2, AR6710-L8T3TS1X2-T, AR5710-H2T4PN2X-NRGL, AR5710-H4T4N2X-LTE4EA, AR5710-H8T2TS1, AR5710-H2T4N2X-NRGL:

1. If NAT is enabled on an interface, the interface will occupy a session table entry even if it has no traffic matching the NAT policy.

2. After NAT ALG is enabled, hardware acceleration forwarding is not performed on multi-channel protocol service traffic transmitted over control channels.

3. Hardware acceleration forwarding is not performed for ICMP Error Report messages.

Hardware-based Routing and Forwarding

For the AR5700 series, AR6700 series, AR8700-8:

1. When there are multiple VPNs or the high-order bits of IP addresses change discretely, the number of routes cannot reach the upper limit.

2. When route-based load balancing is configured, the software forwarding algorithm is different from the hardware forwarding algorithm. As a result, the load balancing effect may be different.

3. When per-packet load balancing is configured in hardware routing mode, load balancing is still performed based on the source and destination IP addresses.

4. In hardware route forwarding mode, the ipv6 load-balance command does not take effect. You can run the ip load-balance command to control load balancing for both IPv4 and IPv6 traffic.

For the AR5710-H8T2TS1-T, AR5710-H4T4N2X, AR6710-L8T3TS1X2, AR6710-L8T3TS1X2-T, AR5710-H2T4PN2X-NRGL, AR5710-H4T4N2X-LTE4EA, AR5710-H8T2TS1, AR5710-H2T4N2X-NRGL:

After the hardware-based routing function is configured and the forwarding mode is switched back to software-based forwarding, the forwarding performance is 15% lower than that when hardware-based routing is not configured.

Hardware-based Routing and Forwarding

For the AR5710-H4T4N2X, AR5710-H8T2TS1-T, AR6710-L8T3TS1X2, AR6710-L8T3TS1X2-T, AR5710-H2T4PN2X-NRGL, AR5710-H4T4N2X-LTE4EA, AR5710-H8T2TS1, AR5710-H2T4N2X-NRGL:

When the outbound interface fragments packets, the collected outbound traffic statistics are the packet length and number of packets before fragmentation.
