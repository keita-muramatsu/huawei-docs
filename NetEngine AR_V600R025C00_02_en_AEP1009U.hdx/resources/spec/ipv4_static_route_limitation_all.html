If recursion depth-based static route selection is configured, the number of static routes for load balancing may decrease. As a result, static routes may fail to implement load balancing.

Before you associate a static route with a BFD session, the session must have been created.

When static routes are deployed, the following features are mutually exclusive and cannot be deployed together:

1. BFD for static route

2. NQA for static route

3. Permanent advertisement of static routes

Determine which feature to use based on your requirements:

- BFD for static routes can be deployed to bind a static route to a BFD session. The BFD session can be used to detect the link status of the static route and determine whether to activate the static route.

- NQA for static routes uses an NQA test instance to detect the link status of a static route and determines whether to activate the static route based on the NQA test result. In some special scenarios, for example, BFD is not configured to detect links between ISPs or a segment of a link, you can deploy NQA for static routes.

- Deploy permanent advertisement of static routes. If the customer wants to determine the forwarding path of service traffic and does not switch the path even if a link fault occurs, deploy permanent advertisement of static routes.

The outbound interface and next-hop IP address specified when binding an IPv4 static route to a BFD session must be the same as those in the template used to bind the IPv4 static route to the BFD session.

Properly plan and configure the outbound interface and next hop of the route.

The static routes to participate in FRR must have different priorities configured.

When the number of configured static routes for load balancing exceeds the product specification limit, the preferred static route may change after the active preferred route is modified or the active/standby switchover is performed twice.
