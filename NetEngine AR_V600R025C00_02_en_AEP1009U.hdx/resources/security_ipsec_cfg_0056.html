Configuring the Function of Sending the INITIAL_CONTACT Notification Payload

Prerequisites

  • The function of sending the INITIAL_CONTACT notification payload takes effect only for IKEv2 negotiation.
  • The function of sending the INITIAL_CONTACT notification payload takes effect only for the following IPsec types:
    • ACL-based IPsec (involving ISAKMP IPsec policies and template IPsec policies)
    • Route-based IPsec (involving IPsec profiles)

Context

The INITIAL_CONTACT notification payload is used to maintain IKE SAs between a pair of IKE peers and ensures that there is only one active IKE SA between a pair of IKE peers.

By default, the device can automatically delete outdated IKE SAs after IKE SA negotiation succeeds without depending on the INITIAL_CONTACT notification payload. If the remote device deletes an outdated IKE SA based on the INITIAL_CONTACT notification payload, you need to configure the function of sending the INITIAL_CONTACT notification payload on the local device. The local device then sends the INITIAL_CONTACT notification payload in the first IKE_AUTH request message. If the local device restarts or wants to use the current IKE SA as the unique SA to establish an IPsec tunnel, you can also configure this function on the local device to instruct the remote device to delete the remaining SA.

Procedure

  1. Enter the system view.

    system-view

  2. Configure the function of sending the INITIAL_CONTACT notification payload.

    ikev2 initial-contact enable

    By default, the function of sending the INITIAL_CONTACT notification payload is disabled.
