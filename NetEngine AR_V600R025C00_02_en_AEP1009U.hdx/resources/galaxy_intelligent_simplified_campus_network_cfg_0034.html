RU Traffic Forwarding Exception

Symptom

RU traffic is not forwarded as expected. For example, the central device cannot receive traffic from terminals connected to the RU, or terminals connected to the RU cannot receive traffic.

Possible Causes

  • The traffic forwarding path fails, or an uplink or downlink interface of the RU fails.
  • The PHY chip on the RU is faulty.
  • The forwarding chip of the RU does not work properly.
  • The upstream link of the RU is incorrectly connected.

Procedure

  1. Check the status and packet statistics of the downlink interface, uplink interface, and interconnection interface based on the traffic forwarding path to locate the failure point.

    1. For example, if traffic is forwarded from the central device to the RU, check the status of the interface connecting the central device and RU and check the statistics of incoming and outgoing packets on this interface. The following example uses Eth-Trunk 1 as the interconnection interface.

    Determine the interface with abnormal traffic based on the command output. For example, in normal cases, the incoming traffic volume of the central device's interconnection interface is equal to the outgoing traffic volume of the RU's uplink interface. If not, find out where packets are lost based on the traffic statistics in the command output and determine the faulty interface.

  2. View FMEA-related alarms on the central device to check whether the RU's PHY chip is faulty.

    RUMNG/2/RuPhyStatAbnormal:OID [oid] Remote unit PHY chip is abnormal. (RemoteUnitEsn=[OCTET]) indicates that the RU's PHY chip is abnormal. For details about the alarm information, see hwRuPhyStatAbnormal.

    1. If the interface that uses the abnormal PHY chip is in Up state, the device automatically restarts. After the restart, check whether the interface can send and receive packets properly. If not, the PHY chip is faulty. In this case, replace the device.
      # Display information brief about the RU interface and check the PHY status of the interface. As shown in the following example, port 3 is connected to a terminal and its PHY status is Up. If the alarm hwRuPhyStatAbnormal is generated on the central device, the central device automatically restarts. After the restart, check whether the interface can send and receive packets properly.

    2. If the interface that uses the abnormal PHY chip is in Down state, the device will not automatically restart. If this interface is not used, no further action is required. If this interface needs to be used, run the reboot command to restart the device. After the restart, check whether the interface can send and receive packets properly.

  3. Perform internal loopback on the RU's downlink interface, and restart the interface to rectify the fault.

    1. Perform an internal loopback test on the RU interfaces.
      # Perform an internal loopback test on port 2 of RU 0 to check whether the internal forwarding chip of the RU works properly. If "Error: Failed to set loopback test, error message:***" is displayed after the loopbacktest internal port command is delivered, the internal loopback test failed and the interface is faulty. In this case, information needs to be collected for fault locating. If "Info: Setting the internal loopback test on the port of the remote unit succeeded." is displayed, the internal loopback test is successful and the internal forwarding chip works properly.
      <HUAWEI> system-view 
[HUAWEI] remote-unit 0 
[HUAWEI-remote-unit-0] loopbacktest internal port 2
    2. Restart interfaces on the RU.

      # If the status or statistics of port 1 on RU 0 is abnormal, restart the port to rectify the fault.

      [HUAWEI-remote-unit-0] restart port 1 
[HUAWEI-remote-unit-0] quit

  4. Check whether the uplink interfaces are correctly connected.

    1. The uplink interfaces of an RU are added to the Eth-Trunk by default. Check whether the uplink interfaces are connected to the same central device. If they are connected to two central devices, traffic forwarding will be abnormal.
    2. An RU is connected to the central device through two uplinks. Check whether the two downlink interfaces of the central device are added to the same Eth-Trunk interface. If not, a link exception alarm is generated and the interfaces go Error-Down.

    In dual-link scenarios, the central device may not set up an Eth-Trunk or the two links may connect to different central devices. In these cases, the central device will automatically detect the fault, triggering an alarm and Error-Down event.

    # If an interface is in Error-Down state, run the restart command to restart the interface or set the automatic recovery time of the interface. Run the error-down auto-recovery cause remote-unit-link interval command to set the automatic recovery time for the interfaces connecting the central device to RUs if the interfaces go Error-Down due to link faults. Run the error-down auto-recovery cause remote-unit-misconfig interval command to set the automatic recovery time for the interfaces connecting the central device to RUs if the interfaces go Error-Down due to incorrect configuration.

    [HUAWEI] error-down auto-recovery cause remote-unit-link interval 30
[HUAWEI] error-down auto-recovery cause remote-unit-misconfig interval 30

  5. Collect log and configuration information and contact technical support personnel. You can run the display diagnostic-information command to collect diagnostic information.
