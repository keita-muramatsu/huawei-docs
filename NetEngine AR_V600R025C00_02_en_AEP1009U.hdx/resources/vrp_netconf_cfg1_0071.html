(Optional) Enabling Proactive NETCONF Registration

Context

If an NMS does not support automatic device discovery, it cannot manage devices as soon as they go online. To address this problem, you can configure proactive NETCONF registration. This enables a device to send a NETCONF connection request to the NMS when the device goes online, allowing the NMS to manage the device.

Procedure

  1. Enter the system view.

    system-view

  2. Enter the NETCONF user interface view.

    netconf

  3. Create a callhome template and enter the callhome template view.

    callhome callhome-name

  4. Configure the interval at which the device sends NETCONF connection requests to the NMS.

    reconnection interval interval

    By default, a device sends a NETCONF connection request to the NMS at an interval of 5s.

  5. (Optional) When multiple NETCONF connection instances are configured, configure the selection mode of the NETCONF connection instances as required.

    • Select a NETCONF connection instance based on the configuration delivery sequence to establish a connection.

      Configure the default mode for the NETCONF connection instance.

      work-endpoint select-mode default

      By default, a NETCONF connection instance uses the default mode.

    • Select a NETCONF connection instance based on the priority to establish a connection.
      1. Configure the priority mode for the NETCONF connection instance.
        work-endpoint select-mode priority

        By default, a NETCONF connection instance uses the default mode.

      2. Configure an interval for initiating a round of link detection.
        link-detect interval interval-val

        By default, the device initiates a round of link detection at an interval of 5 minutes.

      In priority mode, the device initiates TCP link detection for all NETCONF connection instances. After the device successfully connects to the NMS, if it detects that an available NETCONF connection instance with a higher priority than the currently connected instance exists, the device switches to that instance with a higher priority.

  6. Create a NETCONF connection instance and enter the NETCONF connection instance view.

    endpoint endpoint-name

    A device supports 20 IPv4 NETCONF connection instances and 20 IPv6 NETCONF connection instances, but only one NETCONF connection instance can be used for connection. If a connection fails, the device connects to the NMS through the next NETCONF connection instance. If the service disable command is configured, the device does not connect to the NMS through the next NETCONF connection instance.

  7. Configure a callhome keepalive interval.

    keepalive-interval intervalTime

  8. Configure the number of callhome keepalive times.

    keepalive-maxcount maxcount

  9. Configure the IP address and TCP port number of the NMS that establishes a NETCONF connection with the device, as well as the device's source IP address and VPN instance.

    { peer-ip ip-address | peer { peerName ipv6 | peerName } port port-number { [ [ local-address source-ip ] | [ vpn-instance vpn-instance | public-net ] ] * | [ source-interface { interface-name | interface-type interface-num } ] }

  10. (Optional) Configure a priority for the NETCONF connection instance.

    priority priority-val

    By default, no priority is configured for a NETCONF connection instance.

    Before running this command, ensure that the work-endpoint select-mode priority command has been run in the callhome view to configure the priority mode for the NETCONF connection instance. Otherwise, this command fails to be executed.

  11. (Optional) Disable a device from proactively sending a NETCONF connection request to the NMS and establishing a NETCONF connection with the NMS.

    service disable

    By default, a device proactively sends a NETCONF connection request to the NMS and establishes a NETCONF connection with the NMS.

Follow-up Procedure

After proactive NETCONF registration is configured during deployment, you can perform the following operations to check the registration status and offline reasons of a device to facilitate deployment.

  • Run the display controller connect-status command to check the registration status of the device with the NMS.
  • Run the display controller register-fail-record command to check records about device registration failures. This allows you to determine the failure cause as well as date and time when the device failed to register with the NMS.
  • Run the display controller offline-record command to check the reason why the device went offline from the NMS.
  • Run the reset controller register-fail-record command to clear records about device registration failures. This enables the device to re-collect statistics about registration failures with the NMS.
  • Run the reset controller offline-record command to clear records about the reasons why the device went offline from the NMS.
