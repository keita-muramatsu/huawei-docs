Understanding DSVPN NAT Traversal

In Figure 1, the private networks of spokes are situated behind NAT devices. In this case, when spokes want to set up VPN tunnels with the hub or with each other, traffic must traverse the NAT devices. DSVPN supports NAT traversal to implement direct communication between spokes.

Figure 1 DSVPN NAT traversal
The following describes the implementation of NAT traversal on a DSVPN network:
  1. A spoke sends an NHRP Registration Request message with its original public address to the hub.
  2. The NHRP module of the hub detects whether the spoke is behind a NAT device. If so, the hub sends an NHRP Registration Reply message to the spoke. The reply includes the post-NAT address of the spoke.
  3. The source spoke sends an NHRP Resolution Request message with its pre- and post-NAT public addresses to the destination spoke.
  4. The destination spoke sends an NHRP Resolution Reply message with its pre- and post-NAT public addresses to the source spoke.
  5. The source and destination spokes now know each other's pre- and post-NAT public addresses. They then establish a tunnel for direct communication based on their post-NAT addresses.
  • DSVPN does not support NAT traversal if two spokes are behind the same NAT device and have the same post-NAT IP address.
  • DSVPN does not support NAT traversal if two spokes are behind different NAT devices with Port Address Translation (PAT) configured.
  • To enable spoke-to-spoke communication, the NAT devices must have NAT Server or static NAT configured. NAT traversal cannot be implemented on a DSVPN network if outbound NAT is configured on the NAT devices.
  • In a DSVPN over IPsec scenario, if a NAT device is deployed, you are advised to set the IPsec encapsulation mode to transport. If two spokes are situated behind different NAT devices or the hub is situated behind a NAT device, the IPsec encapsulation mode can only be transport.
