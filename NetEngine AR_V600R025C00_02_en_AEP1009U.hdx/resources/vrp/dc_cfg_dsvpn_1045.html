Spoke Subnets Cannot Communicate Directly in a Non-Shortcut Scenario

Fault Symptom

On a DSVPN network deployed in non-shortcut mode, spoke subnets cannot communicate with each other.

Procedure

  1. Check whether there are reachable routes between hub and spoke subnets as well as between spoke subnets, and whether the next hop of these routes is the tunnel address of the peer end.

    Run the display ip routing-table command on a spoke to check whether it has routes to the peer spoke, and run the display ip routing-table command on the hub to check whether it has routes to spoke subnets.

    • If there is no reachable route between hub and spoke subnets as well as between spoke subnets, configure such routes. For details, see CLI Configuration Guide > IP Routing Configuration.
    • If there are reachable routes between hub and spoke subnets as well as between spoke subnets, but their next hop is not the tunnel address of the peer end, change the next hop to the peer end's tunnel address. For details, see CLI Configuration Guide > IP Routing Configuration.
    • If there are such routes and their next hop is the tunnel address of the peer end, go to step 2.

  2. Check whether the hub and a spoke generate an NHRP mapping entry for the peer spoke.

    Run the display nhrp peer command on the hub and spokes to check NHRP mapping entries.

    If the hub does not generate NHRP mapping entries for the spokes, rectify the fault by referring to Spoke Registration Fails.
