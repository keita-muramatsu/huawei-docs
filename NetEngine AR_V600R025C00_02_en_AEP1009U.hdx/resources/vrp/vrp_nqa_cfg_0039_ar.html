Configuring an LSP Trace Test

Context

An NQA LSP trace test is used to detect the forwarding path of an LSP and collect statistics about each device along the forwarding path. Figure 1 shows a network on which an NQA LSP trace test is performed. The LSP trace test process is as follows:

  1. The client (PE-A) constructs a UDP MPLS Echo Request packet whose destination IP address in the IP header is on the network segment 127.0.0.0/8, and searches for the corresponding LSP. This MPLS Echo Request packet contains the downstream mapping TLV, which carries downstream information (such as the next hop address and outgoing label) about the LSP on the current node. The TTL of the first MPLS Echo Request packet is 1.

  2. The MPLS Echo Request packet is forwarded through the specified LSP in the MPLS domain. Upon receiving this packet, the first-hop device determines that the TTL expires and returns an MPLS Echo reply packet.

  3. The client continues to send MPLS Echo Request packets, with the TTL value increasing by 1 each time a new packet is sent. This process is repeated until all label switching routers (LSRs) along the LSP respond to the MPLS Echo Request packets.

  4. Based on the MPLS Echo reply packets received from each LSR along the LSP, the client collects information about the LSP from itself to the destination and statistics about each LSR.

Procedure

  1. Enter the system view.

    system-view

  2. Create an NQA test instance and set the test instance type to LSP trace.
    1. Create an NQA test instance and enter its view.

      nqa test-instance admin-name test-name

    2. Set the NQA test instance type to LSP trace.

      test-type lsptrace

    3. (Optional) Configure a description for the NQA test instance.

      description description

  3. (Optional) Enable MPLS packet fragmentation for an NQA test instance.

    fragment enable

    If the MPLS packet length of an NQA test instance is greater than the MTU of a specified MPLS tunnel, MPLS packets fail to pass through the tunnel.

  4. Set the LSP type for the NQA test instance.

    lsp-type ipv4

  5. Set the destination IP address for NQA test packets, that is, the IP address of the NQA server.

    destination-address ipv4 destAddress [ { lsp-masklen maskLen } | { lsp-loopback loopbackAddress } ] *

  6. (Optional) Set the next-hop IP address for load balancing.

    lsp-nexthop nexthop-ip-address

    When load balancing is enabled on an ingress node, you can run this command to configure an IP address for the next hop.

  7. (Optional) Set parameters as required for an NQA test instance to simulate packet transmission.
    1. Set the LSP EXP value for the NQA test instance.

      lsp-exp exp

    2. Set the mode in which LSPs are returned for the NQA test instance.

      lsp-replymode { no-reply | udp }

    3. Set the number of probes in a test.

      probe-count number

    4. Set the source IP address for NQA test packets. Use the IP address of the NQA client.

      source-address ipv4 srcAddress

    5. Set the TTL of test packets.

      tracert-livetime first-ttl first-ttl max-ttl max-ttl

    6. Configure the aging time for the NQA test instance.

      agetime ageTimeValue

  8. (Optional) Configure test failure conditions.
    1. Set the timeout interval for response packets.

      timeout time

    2. Set the maximum number of hop failures for NQA test packets.

      tracert-hopfailtimes hopFailTimes

  9. (Optional) Set the maximum number of historical test records and test results that can be saved for the NQA test instance.

    records { history history-number | result result-number }

  10. Schedule the NQA test instance.
    1. (Optional) Set the interval for performing an NQA test instance.

      frequency frequencyValue

    2. Start the NQA test instance.

      You can start an NQA test instance immediately, at a specified time, after a delay, or periodically.

      • Start the test instance immediately.
        start now [ end { at [ yyyy/mm/dd ] hh:mm:ss | delay { seconds second | hh:mm:ss } | lifetime { seconds second | hh:mm:ss } } ]
      • Start the test instance at a specified time.
        start at [ yyyy/mm/dd ] hh:mm:ss [ end { at [ yyyy/mm/dd ] hh:mm:ss | delay { seconds second | hh:mm:ss } | lifetime { seconds second | hh:mm:ss } } ]

      • Start the test instance after a specified delay.

        start delay { seconds second | hh:mm:ss } [ end { at [ yyyy/mm/dd ] hh:mm:ss | delay { seconds second | hh:mm:ss } | lifetime { seconds second | hh:mm:ss } } ]

      • Start the test instance at a specified time every day.

        start daily hh:mm:ss to hh:mm:ss [ begin yyyy/mm/dd ] [ end yyyy/mm/dd ]
