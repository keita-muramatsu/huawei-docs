IFIT Packet Format

Figure 1 shows the structure of an IFIT packet header on an SRv6 network. Table 1 describes the fields in the IFIT packet header.

Figure 1 IFIT packet header structure
Table 1 Fields in an IFIT packet header

Field

Description

Guiding label
  • Type: 130, indicating the start of the IFIT packet header.
  • Length: indicates the total length of the IFIT packet header.
  • Rsv: indicates bits reserved for future extension.

Basic header
  • Flow ID/Flow ID Ext: uniquely identifies a service flow on the entire network in a measurement domain.
  • L: loss flag, indicating packet loss measurement.
  • D: delay flag, indicating delay measurement. The default value is 0. If this field is set to 1, timestamp information needs to be reported to the analyzer.
  • S/R: If the guiding label is the bottommost label, R is carried and is set to 1. If the guiding label is not the bottommost label, S is carried and is set to 0. The default value is 1. Currently, the value of this field can only be set to 1.
  • NextHeader: indicates whether an extension header is carried. Currently, only 0x09 (data-plane protocol extension) is supported.
  • E: indicates the measurement mode, including the hop-by-hop mode and E2E mode. The value 1 indicates the E2E mode.
    NOTE:

    Only the E2E mode is supported in an IFIT tunnel-level quality measurement scenario.

  • P: used for IPv4 encapsulation to prevent incorrect matching of Probe Marker. The value 1 indicates incorrect matching. In this case, measurement is not performed. (Currently, this field is not supported.)
  • F: indicates the forward flow flag. The value 1 indicates the forward flow.
  • Len: indicates the extended length. The 16-bit Trace Type field is reserved in the Len field and consists of 15 metadata fields and one control field. The Len value is expressed in 4 bytes. The Len value is 1 if there is no metadata field.
  • R/Rsv: indicates bits reserved for future extension.
  • Trace Type (bitmap): metadata indication bit, which is represented by a bitmap. A maximum of 16 types of extension are supported, such as Sequence and control fields.

Extension header
  • Bit0: It is used to measure the packet-by-packet delay. If it is set to 1, the timestamp is valid and occupies 6 bytes. The first 2 bytes indicate second, and the last 4 bytes indicate nanosecond. (This field is not supported currently.)
  • Bit1: control field, which is used to carry control information such as backward flow creation and synchronization period.
    • DIP/SIP Mask: indicates the mask length of an IPv4 or IPv6 address. (This field is not supported currently.)
    • Proto/Ports: indicates the protocol number, source port number at the transport layer, and destination port number at the transport layer. The value 1 indicates that the corresponding bit is valid. For example, the value 0b101 indicates that an ACL rule needs to be created for the backward flow that matches the destination port number and protocol number. (This field is not supported currently.)
    • V: indicates whether a backward flow needs to be created. The value 1 indicates that a backward flow needs to be created. (This field is not supported currently.)
    • DSCP: indicates whether the measurement flow is determined based on DSCP.
    • Tunnel: indicates whether IFIT tunnel-level quality measurement is used.
    • Period (s): indicates the synchronization report period, in seconds.
  • Bit2: used for out-of-order detection. The value 1 indicates that the sequence is valid. The length of this field is 4 bytes. (This field is not supported currently.)
  • Bit3: used to implement packet modification detection by checking the checksum. The value 1 indicates that the checksum is valid. The length of this field is 4 bytes. (This field is not supported currently.)
The above information describes the packet format of application-level IFIT measurement. In a scenario where native-IP IFIT and application-level IFIT measurement domains are interconnected, you need to configure color bit switching on the device that functions as the border node. Figure 2 shows the packet format of native-IP IFIT measurement to better illustrate the switching between native-IP IFIT and application-level IFIT measurement modes. Native-IP IFIT measurement is implemented by coloring IP headers. Bits in the Type of Service (ToS) or Flags field of an IP header can be used as color bits, and are configurable.
Figure 2 IPv4 header structure

  • ToS field

    The ToS field contains eight bits. The leftmost three bits (bits 0 to 2) constitute the Precedence field that identifies the IP packet priority. Bits 3 to 7 are rarely used. If bits 3 to 7 are not used, one of them can be used as the color bit to uniquely identify service packets with a specific characteristic.

  • Flags field

    The Flags field determines whether a packet can be fragmented. It contains three bits, bits 0 to 2, of which bit 0 is reserved and can be used as the color bit to uniquely identify service packets with a specific characteristic.
