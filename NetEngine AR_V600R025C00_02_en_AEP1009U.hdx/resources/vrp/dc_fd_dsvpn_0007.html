Understanding Dual-Hub DSVPN

On a typical DSVPN network, all spokes connect to a hub. If the hub fails, spokes cannot establish tunnels for direct communication. To improve DSVPN reliability, two hubs can be deployed for active/standby backup.

As shown in Figure 1, Hub1 and Hub2 are deployed at the HQ. Routing policies are deployed on spokes so that routes to Hub1 have a higher priority than those to Hub2. In this way, Hub1 serves as the active hub and Hub2 as the standby hub.

Dual-hub redundancy is applicable to DSVPN only in a shortcut scenario.

Figure 1 Dual-hub DSVPN
The two hubs deployed for redundancy on a DSVPN network work as follows:
  1. All spokes simultaneously send NHRP Registration Request messages to Hub1 (active) and Hub2 (standby), and establish active and standby static mGRE tunnels with Hub1 and Hub2, respectively.
  2. When a spoke wants to set up an mGRE tunnel with another spoke, it sends an NHRP Resolution Request message to one of the hubs:
    • When both Hub1 and Hub2 are functioning properly, the NHRP Resolution Request message is sent to Hub1 over the active static mGRE tunnel because the route from the source spoke to Hub1 has a higher preference. Hub1 then forwards the NHRP Resolution Request message to the destination spoke.
    • If Hub1 fails, the preference of the route to Hub1 becomes lower than that to Hub2. As such, the source spoke sends the NHRP Resolution Request message to Hub2 over the standby static mGRE tunnel. Hub2 then forwards the NHRP Resolution Request message to the destination spoke.
    • After Hub1 recovers, the route to Hub1 once again has a higher preference than that to Hub2, and so the source spoke reverts to transmitting the NHRP Resolution Request message to Hub1.
  3. The destination spoke sends an NHRP Resolution Reply message to the source spoke. After that, they set up a dynamic mGRE tunnel.
  4. When connected with a dynamic mGRE tunnel, spokes can directly communicate, and whether the hubs are functioning properly has no impact on service flows between the spokes. If the dynamic mGRE tunnel between two spokes is torn down because it has had no traffic to forward for a long period of time, the spokes need to re-establish a dynamic mGRE tunnel when they want to communicate. In this case, they determine the hub to which NHRP Resolution Request messages are sent based on the route preference.
