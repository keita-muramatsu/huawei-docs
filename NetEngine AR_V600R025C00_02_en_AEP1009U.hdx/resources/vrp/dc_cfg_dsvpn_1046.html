Spoke Subnets Cannot Directly Communicate in a Shortcut Scenario

Fault Symptom

On a DSVPN network deployed in shortcut mode, spoke subnets cannot communicate with each other.

Procedure

  1. Check whether there are reachable routes between spoke subnets as well as between hub and spoke subnets.

    Run the display ip routing-table command on a spoke to check whether it has routes to the peer spoke's subnet, and run the display ip routing-table command on the hub to check whether it has routes to spoke subnets.

    • If there is no reachable route between hub and spoke subnets as well as between spoke subnets, configure such routes. For details, see CLI Configuration Guide > IP Routing Configuration.
    • If there are such routes, go to step 2.

  2. Check whether the next hop of the route from a spoke to the peer spoke's subnet is the hub's tunnel address.

    Run the display ip routing-table command on a spoke to check whether it has a route to the peer spoke's subnet.

    • If the spoke has such a route but the next hop is not the hub's tunnel address, change the next hop to the hub's tunnel address. For details, see CLI Configuration Guide > IP Routing Configuration.
    • If the spoke has such a route and the route uses the hub's tunnel address as the next hop, go to step 3.

  3. Check whether the hub and a spoke generate an NHRP mapping entry for the peer spoke.

    Run the display nhrp peer command on the hub and spokes to check NHRP mapping entries.

    If the hub does not generate NHRP mapping entries for the spokes, rectify the fault by referring to Spoke Registration Fails. -
