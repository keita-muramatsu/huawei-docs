Configuring an IKE Peer

Prerequisites

  • An IKE proposal has been configured, which will be referenced by the IKE peer to be configured.
  • If Rivest-Shamir-Adleman (RSA) signature authentication is used, determine the public key infrastructure (PKI) realm to which the IKE peer belongs, and ensure that the local certificate and CA root certificate have been imported to the authenticated device and the CA root certificate has been imported to the authenticating device.

Context

An IKE peer needs to be referenced when an IPsec tunnel is established in IKE negotiation mode. When configuring an IKE peer, pay attention to the following points:
  • IKE peers on both ends must use the same IKE version.
  • The IKE peers that use IKEv1 must use the same negotiation mode.
  • Identity authentication parameters of the two IKE peers must match.

Procedure

  1. Enter the system view.

    system-view

  2. Create an IKE peer and enter the IKE peer view.

    ike peer peer-name

    By default, no IKE peer is created in the system.

  3. Configure the IKE protocol version used by IKE peers.

    version { 1 | 2 }

    By default, the device does not support this command, that is, SA negotiation through IKEv1 is not supported. To use this command, install the IKEv1 feature package.

    Before running this command, load the IKEv1 feature package. By default, the IKEv1 feature package is not installed on the device. As such, only IKEv2 is enabled for IKE peers and SA negotiation through IKEv1 is not supported. After the IKEv1 feature package is loaded, both IKEv1 and IKEv2 are enabled for IKE peers by default.

  4. Optional: Configure the negotiation mode in IKEv1 phase 1.

    exchange-mode { main | aggressive | auto }

    By default, the main mode is used in IKEv1 phase 1.

    auto indicates that the negotiation mode of IKEv1 phase 1 is auto-sensing mode. In auto-sensing mode, the device uses the main mode if it serves as the IKE negotiation initiator. If it serves as the responder, it can use either the main or aggressive mode.

  5. Configure the IKE peer to reference the configured IKE proposal.

    ike-proposal proposal-number

    By default, an IKE peer does not reference an IKE proposal.

    proposal-number specifies the number of a created IKE proposal.

  6. Configure the local ID type.

    local-id-type { dn | ip [ ip-configurable ] | user-fqdn | fqdn | esn }

    By default, the local ID type is an IP address.

    In PSK authentication mode, the local ID type cannot be set to dn and must be the same as that displayed in the display pki certificate command output.

  7. Optional: Configure a local ID.

    local-id id

    You need to configure a local ID when the local ID type of an IKE peer is an FQDN or a user FQDN. The local ID configured on the local end must be the same as the remote ID configured on the remote end.

    • In a PSK authentication scenario, if the local ID type is an IP address, by default, the device uses the IP address of the interface on which the device establishes an IPsec tunnel as the local ID. If multiple IP addresses are configured for the interface, the device uses the IP address configured using the tunnel local { ip-address | applied-interface } command as the local ID.

      If the local ID type is an IP address, you can also specify the ip-configurable parameter and then run the local-id command to configure another IP address as the local ID as needed.

    • If the local ID type is a DN, FQDN, or user FQDN, you can run the ike local-name local-name command in the system view to configure a global local ID for IKE negotiation. After the configuration, all IKE peers on the device use this ID as the local ID for identity authentication. The local ID configured using the local-id id command takes precedence over that configured using the ike local-name local-name command.
    • If the local ID type is an ESN, the device uses its own ESN as the local ID, and the local-id configuration does not take effect.

  8. Configure the authentication mode and authentication parameters.

    The device supports the following identity authentication modes: PSK authentication, RSA digital signature certificate authentication, and SM digital envelope authentication.

    PSK authentication

    In PSK authentication mode, the same ID and PSK can be configured for one or more peers (in single key mode), and different IDs and PSKs can be configured for multiple peers using an IKE user table (in multi-key mode). An IKE user table is used in a template IPsec policy to configure different IDs and PSKs for different peers. This table effectively prevents the disclosure of the ID and PSK of a specific peer from posing security risks to other peers. When both the single key mode and multi-key mode are configured, the PSK configured using the IKE user table is preferred.

    • In single key mode, you can directly configure authentication parameters such as a PSK and a remote ID.
      1. Configure a PSK.
        pre-shared-key [ key ]

        The PSKs of IKE peers on both ends must be the same.

        If the key parameter is not specified in the command, the command is used to enter the PSK in interactive mode.

        For security purposes, you are advised to periodically change the key on both ends.

      2. Configure the remote ID type.
        remote-id-type { any | dn | esn | fqdn | ip | user-fqdn | none }

        By default, no remote ID type is configured.

        The remote ID type configured on the local end must be the same as the local ID type configured on the remote end. Table 2 describes the relationship between the remote ID types and remote IDs in PSK authentication mode.

      3. Configure a remote ID.
        remote-id id

        In PSK authentication, if both the local ID type and the remote ID type are IP addresses, the local ID configured on the local end does not need to be the same as the remote ID configured on the peer end.

    • In multi-key mode, you need to create an IKE user table, create an IKE user in the IKE user table, and configure authentication parameters for the IKE user.
      1. In the system view, create an IKE user table and enter the IKE user table view.
        ike user-table user-table-id
      2. Create an IKE user and enter the IKE user view.
        user user-name
      3. Configure a description for the IKE user.
        description description

        By default, no description is configured for an IKE user.

      4. Configure a PSK for the IKE user.
        pre-shared-key [ key ]

        By default, no PSK is configured for an IKE user.

        If the key parameter is not specified in the command, the command is used to enter the PSK in interactive mode.

      5. Configure the ID type and ID for the IKE user.
        id-type { any any-id | esn esn-number | fqdn remote-fqdn | ip { ipv4-address | ipv6-address } | user-fqdn remote-user-fqdn }
quit

        By default, no ID type or ID is configured for an IKE user.

        In IKEv1 main mode, the ID type of an IKE user can only be set to ip; in NAT traversal scenarios, ip-address must be set to a post-NAT address.

      6. Return to the system view.
        quit
      7. Enter the IKE peer view.
        ike peer peer-name
      8. Configure the IKE peer to reference a specified IKE user table.
        user-table user-table-id

      remote-id-type { any | dn | esn | fqdn | ip | user-fqdn | none }

      By default, no remote ID type is configured.

      The remote ID type configured on the local end must be the same as the local ID type configured on the remote end. Table 3 describes the relationship between the remote ID types and remote IDs in RSA signature authentication mode.

    2. Optional: Configure a remote ID.
      remote-id id

      The remote ID configured on the local end must be the same as the local ID configured on the remote end.

      If the local ID type is set to FQDN or user FQDN, the remote ID specified in this command will be used for IKEv1 negotiation. In IKEv2 negotiation, the value of the DNS field (if the local ID type is FQDN) or E-mail field (if the local ID type is user FQDN) in the certificate is preferred as the remote ID. If the value of the DNS or E-mail field is blank, the remote ID specified in this command will be used for IKEv2 negotiation.

    3. Set the padding mode for an RSA signature.
      rsa signature-padding { pkcs1 | pss [ sha2-256 ] }

      If you run the rsa signature-padding pss command to set the padding mode of an RSA signature to pss, the PSS mode of the SHA2-256 algorithm is used if the sha2-256 parameter is specified, and the PSS mode of the Huawei algorithm is used if the sha2-256 parameter is not specified. When the device functions as the tunnel initiator, the PSS padding hash algorithm used by the device must be compatible with that used by the peer end. Otherwise, tunnel negotiation may fail.

    4. Specify a digital certificate for the local end.

      In RSA signature authentication, the local ID indicated by an IP address, a DN, a common name (CN), or a user FQDN, is contained in a local certificate. The digital certificate used by the local end can be specified offline. Alternatively, the PKI realm to which the digital certificate belongs can be specified so that the digital certificate of the local end can be obtained based on the configuration of the PKI realm.

      • Specify the digital certificate for the local end offline.
        certificate local-filename filename
      • Specify the PKI realm to which the digital certificate belongs.
        pki realm realm-name

        A PKI realm is a set of identity information required by a PKI entity to enroll a certificate.

        The specified PKI realm must exist, and the CA certificate and local certificate have been imported to the PKI realm. IKE peers can obtain the local CA certificate and local certificate based on the configuration of the PKI realm.

      If the digital certificate used by the local end is specified using both the preceding methods and a CA certificate has been imported to the PKI realm, the device uses the digital certificate specified offline during certificate negotiation, and uses the CA certificate in the PKI realm to verify the peer certificate. You are advised to use only one method to specify the digital certificate used by the local end.

    5. Optional: Configure the certificate signature algorithm used by IKEv2.
      ikev2 authentication sign-hash { md5 | sha1 | sha2-256 | sha2-384 | sha2-512 }

      By default, the certificate signature algorithm used by IKEv2 is SHA2-256.

    6. Optional: Configure the device to preferentially use the local ID specified by a specific field in the local certificate during IKE certificate negotiation.
      local-id-preference certificate enable

      By default, the device preferentially uses the local ID specified by a specific field in the local certificate during IKE certificate negotiation. If no local ID is obtained in the local certificate, the device uses the local ID configured locally.

      In IKE certificate negotiation, the device can use the local ID specified by a specific field in the local certificate, removing the need to configure the local ID for the device.

    7. Optional: Configure the remote ID contained in the IKE packets sent by the initiator as the local ID of the responder in IKEv2 negotiation.
      local-id-reflect enable

      By default, the remote ID contained in the IKE packets sent by the initiator is used as the local ID of the responder in IKEv2 negotiation.

      When the device functions as the responder to perform IKEv2 negotiation, run this command if the device does not know the remote ID configured on the initiator. This command takes effect only when the ID type is IP, ESN, FQDN, or user FQDN. When the responder receives an IKE packet from the initiator, the responder uses the IDr payload (indicating a remote ID) in the packet as its local ID. If the responder does not obtain the IDr payload, it uses the local ID configured locally. If both the local-id-reflect enable and local-id-preference certificate enable commands are run, the local-id-reflect enable command takes precedence over the local-id-preference certificate enable command.

    SM digital envelope authentication

    1. Configure a PKI encryption realm for an IKE peer.

      encryption-certificate pki realm realm-name

      The encryption certificate used for SM digital envelope authentication needs to be imported to the device using the pki import-certificate local realm realm-name { der | pkcs12 | pem } filename filename no-check-same-name command. The no-check-same-name parameter can be specified to allow the device to import the encryption certificate and signature certificate with the same issuer and subject names.

    2. Configure a PKI signature realm for the IKE peer.

      signature-certificate pki realm realm-name

      The signature certificate used for SM digital envelope authentication needs to be imported to the device using the pki import-certificate local realm realm-name { der | pkcs12 | pem } filename filename no-check-same-name command. The no-check-same-name parameter can be specified to allow the device to import the encryption certificate and signature certificate with the same issuer and subject names.

  9. Optional: Configure the responder to accept the IKE proposal of the initiator.

    ike negotiate compatible

    By default, the responder does not accept the IKE proposal of the initiator.

    During IPsec negotiation between IKE peers, if the responder does not know the initiator's negotiation parameters (such as the IKE negotiation mode, algorithm in an IKE proposal, or security protocol, algorithm, and encapsulation mode in an IPsec proposal), perform this step to enable the responder to use the IPsec proposal of the initiator for IPsec negotiation. This configuration ensures successful IPsec negotiation.

    After this command is executed, the default IPsec SA aging time is 604,800 seconds and no traffic is aged by default (that is, the traffic timeout function is disabled) on the responder. In this case, the responder cannot initiate IPsec SA renegotiation.

  10. Optional: Configure the remote IP address, an address segment, or a domain name used in IKE negotiation.

    remote-address { [ vpn-instance vpn-instance-name ] { { start-ip-address [ end-ip-address ] | start-ipv6-address [ end-ipv6-address ] } | host-name host-name } | authentication-address start-ip-address [ end-ip-address ] }

    By default, no remote IP address, address segment, or domain name used in IKE negotiation is configured.

    The following describes the parameters in this command:
    • start-ip-address [ end-ip-address ]: If the remote device uses a fixed IP address, the remote address can be set to this fixed IP address. Otherwise, the remote address needs to be set to an IP address segment.
    • host-name host-name: specifies the domain name of the remote device if the remote device does not have a fixed IP address but has a fixed domain name. In this case, Dynamic Domain Name Service (DDNS) needs to be configured on the remote device to bind the domain name to the dynamic IP address, and DNS needs to be configured on the local device for domain name resolution.
    • authentication-address start-ip-address [ end-ip-address ]: In IPsec NAT traversal scenarios, if both ends use IKEv2 and IP addresses need to be used for authentication, you need to specify the pre-NAT IP address or address segment as the remote authentication address. The IP address of the remote device needs to be set to a post-NAT IP address.

  11. Optional: Set the IKEv2 re-authentication interval.

    re-authentication interval interval

    By default, IKEv2 does not perform re-authentication.

    In remote access scenarios, IKEv2 peers periodically perform re-authentication with each other, which reduces potential risks of attacks and improves IPsec tunnel security.

Verifying the Configuration

  • In the user view, run the display ike peer [ brief | name peer-name ] [ slot slot-id cpu cpu-id ] command to check the IKE peer configuration.
  • If an IKE user table is configured, run the display ike [ slot slot-id cpu cpu-id ] user-table [ number user-table-id [ user-name user-name ] ] command in the user view to check the IKE user table configuration.

Follow-up Procedure

A configured IKE peer can be referenced in an IPsec policy or IPsec profile. For details, see Configuring an IPsec Policy or Configuring an IPsec Profile.
