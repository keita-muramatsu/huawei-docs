Security Policy Matching Process

The device matches traffic against a security policy only when the inbound and outbound interfaces of the traffic are both Layer 3 interfaces added to security zones. Layer 2 packets are not matched against a security policy. To control traffic forwarding, you can create a security policy. Generally, a device has multiple security policies configured for different service traffic. The following describes the rules for matching multiple security policies.

Rules for Matching Security Policies

Figure 1 illustrates the rules for matching security policies. Each security policy contains multiple matching conditions, and the relationship between these matching conditions is AND. That is, a packet matches a security policy only when the packet matches all the matching conditions in the security policy. Multiple values can be configured for a matching condition and these values are ORed. That is, a packet matches a condition as long as the packet matches any value of this condition.

Figure 1 Rules for matching security policies

When multiple security policies are configured, they are sorted in a list by configuration sequence by default. A security policy configured earlier is displayed in the upper part of the list and has a higher priority. The device matches traffic against security policies one by one from the top of the policy list until a matched security policy is found. Therefore, the sequence of configuring security policies is important. To ensure more effective traffic control based on security policies, you need to configure policies with accurate conditions first, and then policies with general conditions. If a specific security policy is placed after a general security policy, it may never be matched. Applying a new security policy will not cause service unavailability or existing connection interruption. For example:

An enterprise has an FTP server (10.1.1.1) deployed. To allow all PCs excluding two temporary ones (10.2.1.1 and 10.2.1.2) on subnet 10.2.1.0/24 to access the FTP server, you need to configure two policies, first policy1 and then policy2.

Of the two security policies, policy1 has more specific conditions than policy2. If policy2 is configured first, policy1 will never be matched. As a result, two temporary PCs (10.2.1.1 and 10.2.1.2) can still access the FTP server.

General policies usually come before exceptions but the required configuration sequence is opposite. During the initial planning, first list all the policies and then configure exceptions before general policies. However, more exceptions may be added in the maintenance phase. Therefore, you need to adjust the sequence after the configuration.

If none of the configured policies is matched, the default security policy is matched. The default security policy is located at the bottom of the policy list and has the lowest priority. In the default security policy, all matching conditions are Any and the default action is Permit. The default action of the default security policy can be modified. There is an exception. The traffic in the same security zone is by default not controlled by the default security policy, and the default forwarding action for such traffic is Permit. You can modify the settings to allow the default security policy to control intra-zone traffic.

Security Policy Filtering Mechanism

For the same data flow, you only need to configure a security policy for traffic on the forward path (that is, in the direction in which access is initiated); no security policy is required for traffic on the return path. That is, the first packet matches the security policy and a session entry is created. Subsequent packets directly match the session table without matching the security policy, improving service processing efficiency. The following uses the access from a client PC to the web server as an example to describe the filtering mechanism of security policies:

Figure 2 shows the process of the client PC accessing the web server. When the traffic reaches the device, the device matches the first packet against security policies. After a matching security policy is found, the device permits the packet to pass through and sets up a session. The session contains information about the packet sent by the PC, such as the source and destination addresses and source and destination port numbers. When the response packet returned by the web server arrives at the device, the device compares packet information with session information in the session table. If the packet matches the session and complies with the subsequent packet definition in the related protocol, the device considers the packet as the response packet from the web server to the PC and permits the packet.
