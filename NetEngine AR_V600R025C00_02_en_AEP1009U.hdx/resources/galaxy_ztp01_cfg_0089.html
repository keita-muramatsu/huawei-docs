Understanding Registration Query Center-based Deployment

During registration query center-based deployment, the device interacts with the DHCP server, registration query center, iMaster NCE-Campus, and bootstrap server. Figure 1 shows the deployment process.

Figure 1 Registration query center-based deployment process
  1. Configuring network deployment parameters and interconnecting with the registration query center

    The network administrator configures global parameters and ZTP on iMaster NCE-Campus controller, and configures the controller to connect to the registration query center. The functions of the controller and registration query center are as follows:

    • iMaster NCE-Campus: establishes NETCONF connections with the device to deliver deployment configurations to the device.
    • Registration query center: provides information such as the address and port number of the bootstrap server and the address and port number of the controller.
  2. Configuring the DHCP server and bootstrap server
    The network administrator deploys the DHCP server. The network administrator can also deploy the DHCP relay agent, bootstrap server, DNS server, and Syslog server as required. The functions of each device are as follows:
    • DHCP relay agent: relays DHCP packets between the device and the DHCP server when they are located on different network segments.
    • DHCP server: assigns a temporary management IP address, default gateway address, DNS server address, and Syslog server address to the device.
    • Bootstrap server: stores CA certificates applied by users. For security purposes, no initial certificate is available on iMaster NCE-Campus. In this case, a device needs to download a CA certificate from the bootstrap server so that two-way authentication for establishing a NETCONF connection between the device and iMaster NCE-Campus can be successfully performed. Currently, iMaster NCE-Campus has integrated the bootstrap server function.

    • DNS server: provides mappings between domain names and IP addresses, and resolves the domain names of the registration query center and bootstrap server to IP addresses.

    • Syslog server: records important information in user logs during ZTP deployment and uploads the logs to the NMS.

  3. Powering on the device

    The deployment person powers on and starts the device. The device starts with a configuration file if one is available. Otherwise, the device automatically starts the ZTP process.

  4. Obtaining DHCP information

    1. The device sends DHCP request packets through its Layer 3 physical interface.
    2. The DHCP server sends a DHCP reply packet to the device. The Option parameters in the packet specify the information that the device needs to obtain from the DHCP server, including the temporary management IP address allocated to the device, default gateway address, DNS server address, and Syslog server address. The device connects to the DNS server based on the server address to resolve the preconfigured domain name of the registration query center.

      If the device fails to obtain the preceding information from the DHCP server through a physical interface, it obtains information such as the device IP address and DNS server address through automatic dial-up configured on the 5G network interface.

  5. Obtaining registration query center information

    The device accesses the registration query center through the preconfigured domain name of the registration query center, obtains the controller's address and port number based on the device ESN or MAC address, and obtains the IP address and port number of the bootstrap server.

  6. (Optional) Obtaining the CA certificate

    This phase is mandatory when no initial certificate is available on the controller.

    The process of obtaining the CA certificate from the bootstrap server is as follows:

    1. The device establishes an HTTPS connection with the bootstrap server based on the obtained address and port number of the bootstrap server.
    2. The device sends a request packet to the bootstrap server to download a CA certificate. The request packet carries the device ESN or the IP address of the bootstrap server.
      • If the Option parameter specifies the certificate verification mode as ESN, the request packet carries the device ESN.
      • If the Option parameter specifies the certificate verification mode as DOMAIN_IP, the request packet carries the IP address of the bootstrap server. The CA certificate can be obtained only after being successfully verified.
    3. The bootstrap server searches for the CA certificate based on the ESN or IP address in the request packet and sends a response packet carrying the CA certificate to the device. The response packet also carries the device ESN or the IP address of the bootstrap server.
    4. After receiving the response packet from the bootstrap server, the device terminates the HTTPS connection with the bootstrap server, parses the response packet, and verifies the validity of the certificate.

      If the CA certificate sent by the bootstrap server has been signed, the device verifies the signature of the certificate. After the signature verification is successful, the device verifies the certificate. If the CA certificate sent by the bootstrap server has not been signed, the device determines whether to trust the certificate based on the Option parameter setting. If the Option parameter specifies that the certificate can be trusted, the device verifies the certificate. Otherwise, the device verifies the signature first. In this case, signature verification will fail.

      The device verifies the certificate based on the certificate verification mode specified by an Option parameter. If the certificate verification mode is ESN, the device verifies the certificate based on the device ESN. If the certificate authentication mode is DOMAIN_IP, the device verifies the certificate based on the IP address of the bootstrap server. If the verification fails, the device fails to obtain a CA certificate.

    5. The device imports the obtained CA certificate to the PKI realm named default to establish a NETCONF connection with the controller.
  7. (Optional) Starting the Syslog server

    The device obtains the address of the Syslog server from the DHCP reply packet and enables the Syslog server function. Information about important phases during device deployment is recorded in user logs, which the Syslog server will upload to the NMS.

  8. Registering with the controller

    After receiving a packet carrying the controller address from the registration query center, the device enables proactive NETCONF registration, and creates an SSH user (huawei). The device then establishes a NETCONF connection with the controller based on the obtained address and port number of the controller. The controller delivers deployment configurations to the device, which then completes automatic deployment.

  • When deploying an unconfigured device, you are advised not to manually deliver the same configurations as those delivered during ZTP. Doing so will cause the configurations to be deleted if the deployment fails.
  • ZTP depends on OPS. You can run the display ops process current command to obtain the task ID, which indicates the ZTP process ID, and then run the ops stop process process-id command to stop the ongoing ZTP process. This operation, however, may cause the configurations that have been delivered during ZTP to be retained on the device.
