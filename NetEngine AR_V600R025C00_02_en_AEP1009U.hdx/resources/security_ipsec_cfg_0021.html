Creating an Advanced ACL

Context

IPsec can protect one or more data flows. ACL-based IPsec uses advanced ACLs to define data flows to be protected by IPsec. In real-world applications, you need to configure an advanced ACL to define the data flow to be protected and then reference the ACL in an IPsec policy to protect the data flow. During the configuration of a template IPsec policy, defining protected data flows on the responder is optional. If protected data flows are not defined on the responder, the responder accepts the range of protected data flows defined on the initiator. If protected data flows are defined on the responder, the ACLs configured on the responder to define protected data flows must mirror or include the ACLs configured on the initiator.

Only one ACL can be referenced in an IPsec policy. Note the following points when configuring ACLs:

  • To protect data flows with different security requirements, create different ACLs and IPsec policies.

  • To protect data flows with the same security requirements, configure multiple rules in an ACL to protect these data flows.

In an ACL, a permit rule defines a data flow that needs to be protected by IPsec, whereas a deny rule defines a data flow that does not need to be protected by IPsec. An ACL can contain multiple rules. A data flow is processed according to the first matched rule.
  • In the outbound direction of an SA, the packets that match the permit rule of an ACL will be encrypted by IPsec before being forwarded. If a packet matches a deny rule or does not match any permit rule, the packet will be directly forwarded without IPsec protection. If a data flow transmitted between two peers matches a permit rule, the data flow needs to be protected and a pair of SAs will be created.
  • In the inbound direction of an SA, IPsec-protected packets are decrypted before being forwarded, whereas non-IPsec-protected packets are forwarded without IPsec protection.

Procedure

  1. Enter the system view.

    system-view

  2. Create an advanced ACL with acl-number in the range from 3000 to 3999 and enter the advanced ACL view.

    acl [ number ] advance-acl-number

  3. Configure ACL rules based on service requirements.

    For details, see "Configuring an Advanced ACL" in CLI Configuration Guide > IP Addresses and Services Configuration > ACL Configuration > Configuring an ACL.

    If ACL rules on both ends of an IPsec tunnel mirror each other, an SA can be successfully established when any end initiates negotiation. If ACL rules on both ends do not mirror each other, an SA can be successfully established only when the address range defined in the ACL rule of the initiator is included in that of the responder or when there are overlapping address ranges in the ACL rules on both ends. It is recommended that ACL rules on both ends mirror each other. That is, the source and destination addresses in an ACL rule on one end are the destination and source addresses in an ACL rule on the other end. To be specific,

    • In IKEv1, an SA can be successfully established as long as the address range specified in the ACL rules configured on the initiator is included in that of the responder. The two ends use overlapping address ranges as the negotiation result. However, IKEv1 does not support the matching of the port number range in ACL rules. Only the start port number in the port number range is used for IPsec tunnel negotiation.

    • In IKEv2, an SA can be successfully established as long as there are overlapping address ranges in the ACL rules on both ends. The two ends use overlapping address ranges as the negotiation result.

      When ACL rules on both ends are defined by the ACL address pool (using the acl ip-pool pool-name command), pay attention to the following points:

      • If the IPsec tunnel is triggered by traffic, ensure that the address pools referenced by the ACL rules that match the traffic on the initiator and responder overlap. Otherwise, the IPsec tunnel fails to be established.

      • If the IPsec tunnel is automatically triggered, ensure that the address pools referenced by each ACL rule of the initiator and responder overlap. Otherwise, the IPsec tunnel fails to be established.

      Only IKEv2 supports the configuration of an ACL address pool, and a maximum of 15 IP addresses can be configured in an ACL address pool.

  4. Return to the system view.

    quit

  5. Optional: Enable flow check on the IKE negotiation initiator.

    undo ike initiator flow-check disable

    By default, flow check is enabled on the IKE negotiation initiator.

    After flow check is enabled on the initiator, the initiator sends the ACL that defines the traffic flows to be protected to the remote end during IKE negotiation. Upon receiving the negotiation response, the initiator compares the protected traffic flow range returned by the remote end with its own configured ACL to verify that the negotiation result is correct.

    If flow check is disabled on the IKE negotiation initiator, the initiator does not check the negotiation result.

Verifying the Configuration

Run the display acl { acl-number | all } command to check the ACL configuration.

Follow-up Procedure

Reference the configured ACL in an IPsec policy. For details, see Configuring an IPsec Policy.
