STUN Implementation

Typical STUN Networking

Figure 1 illustrates a typical STUN network where STUN clients on a private network are located behind NAT devices and the STUN server is located on a public network. STUN clients send requests to the STUN server for NAT detection if this is required by services, and will then receive responses from the STUN server. After successful detection, STUN clients send information about their transport network ports (TNPs) to the route reflector (RR), and obtain the TNP information (including the IP addresses and port numbers before and after NAT) of other STUN clients through the RR. When STUN clients need to communicate with each other, they will send BGP packets to instruct the peer end to perform hole punching and send STUN messages based on their TNP information to establish a data channel.

NAT detection

  1. Each STUN client sends a binding request to the STUN server.

    When a service requires NAT detection (for example, NAT detection needs to be enabled prior to TNP advertisement), the STUN clients (STUN client1 and STUN client2 in this example) send binding requests to the STUN server.

  2. After the STUN server receives the binding requests, if authentication is configured, the STUN server performs authentication and message integrity check, as follows. Otherwise, the STUN server proceeds to Step 3.
    1. The STUN server searches for the password associated with the username carried in the USERNAME attribute of each STUN message.
    2. The STUN server uses the password (HMAC key) and the STUN message (including the message header and attributes preceding the MESSAGE-INTEGRITY attribute) as the input to calculate the HMAC value.
    3. The STUN server obtains the HMAC value from the MESSAGE-INTEGRITY attribute of the STUN message and compares it with the HMAC value calculated in b. If they are the same, authentication and message integrity check succeed, and the STUN server proceeds to Step 3. Otherwise, the STUN server returns an error code to the corresponding STUN client and records a log.
  3. The STUN server sends a binding response to each STUN client.

    The STUN server obtains the source IP address and port number from the binding request and sends a binding response to each STUN client. The binding response message carries the MAPPED-ADDRESS, XOR-MAPPED-ADDRESS, and RESPONSE-ORIGIN attributes. If authentication is enabled, the MESSAGE-INTEGRITY attribute is also carried in the message for authentication and message integrity check after the STUN client receives the binding response.

  4. Each STUN client confirms the NAT detection result and sends the result to the service module that requires NAT detection (such as the TNP module).

    After receiving the binding response, each STUN client performs authentication and message integrity check according to Step 2 and then notifies the service module of the NAT detection result, if authentication is configured. Otherwise, the STUN clients just confirm the NAT detection result as follows and notify the service module of the result. The STUN client obtains an IP address and port number from the MAPPED-ADDRESS or XOR-MAPPED-ADDRESS attribute in the binding response, and compares the obtained IP address and port number with the source IP address and port number carried in the binding request. If they are different, a NAT device is used in front of the STUN client. After confirming the NAT detection result, each STUN client notifies the service module of the result.

Hole punching

Hole punching is a technique for establishing a direct connection between P2P communicating parties behind NAT devices. Specifically, it sets up a data channel between P2P STUN clients across intermediate devices (such as RRs and servers) by creating NAT session entries on NAT devices. The process of STUN hole punching is as follows:

  1. A STUN client obtains the TNP information (including IP addresses and port numbers before and after NAT) of other STUN clients from an RR through BGP. When STUN client1 needs to communicate with STUN client2, it sends BGP packets to notify STUN client2 that hole punching is required to establish a data channel.

    In the following example, the IP address and port number of STUN client1 before NAT are (IP1:Port1) and its post-NAT IP address and port number are (IP1':Port1'). The IP address and port number of STUN client2 before NAT are (IP2:Port2), and its post-NAT IP address and port number are (IP2':Port2').

  2. STUN client1 and STUN client2 send binding requests to each other for hole punching.
    1. STUN client1 sends two binding requests to STUN client2. Specifically, it sends message A containing (IP1, Port1) and (IP2, Port2) and message B containing (IP1, Port1) and (IP2', Port2'). If STUN client1 and STUN client2 are on the same private network (that is, behind the same NAT device), message A can be successfully sent to STUN client2, and the process moves to Step 3. Otherwise, NAT device1 (which is in front of STUN client1) will discard message A.
    2. After STUN client1 sends message B, NAT device1 generates an entry to record the session from STUN client1 to STUN client2. However, since NAT device2 (which is in front of STUN client2) does not have the corresponding session entry, NAT device2 will discard message B. Meanwhile, when STUN client2 is sending binding requests to STUN client1, NAT device2 also generates an entry to record the session from STUN client2 to STUN client1. As NAT device1 does not have the corresponding session entry either, it will discard message B from STUN client2.
    3. The two STUN clients keep sending binding requests to each other. When session entries are generated on both NAT device1 and NAT device2, the two STUN clients can receive binding requests from each other.
  3. After receiving a binding request from STUN client1, STUN client2 sends a binding response to STUN client1. STUN client1 does the same.

After the preceding STUN messages are exchanged, a data channel is established between the STUN clients so that packets can traverse the NAT devices.
