Understanding GRE over IPsec

Generic Routing Encapsulation (GRE) is a tunneling protocol that encapsulates multicast, broadcast, and non-IP packets. GRE provides only simple password authentication but not data encryption, and so cannot ensure data transmission security. IPsec provides high data transmission security but cannot encapsulate multicast, broadcast, or non-IP packets.

GRE over IPsec can be used to transmit multicast, broadcast, and non-IP packets (such as video conferencing messages or dynamic routing protocol messages) over IPsec tunnels. Leveraging advantages of GRE and IPsec, GRE over IPsec encapsulates multicast, broadcast, and non-IP packets into ordinary IP packets and then securely transmits these IP packets through IPsec. Figure 1 GRE over IPsec

In Figure 2, before traffic enters a GRE over IPsec tunnel, it is encapsulated using GRE and then encapsulated using IPsec, ensuring secure and reliable data transmission. GRE over IPsec supports encapsulation in both tunnel and transport modes. A public IP header is added to packets during GRE encapsulation, and another public IP header needs to be added to packets if GRE over IPsec in tunnel mode is used, resulting in longer packets. In this case, packets are more likely to be fragmented. Therefore, GRE over IPsec in transport mode is recommended.

In the IP header added during GRE encapsulation, the source and destination addresses are the source and destination addresses of a GRE tunnel. In the IP header added during IPsec encapsulation in tunnel mode, the source address is the IP address of the local interface to which an IPsec policy is applied and the destination address is the IP address of the remote interface to which an IPsec policy is applied. IPsec protects data flows from the GRE tunnel source to the GRE tunnel destination.

Figure 2 Packet encapsulation and tunnel negotiation in GRE over IPsec

Before configuring GRE over IPsec, you need to perform the following operations:

  • Run the interface tunnel and tunnel-protocol gre commands to create a tunnel interface and set the encapsulation type of the interface to GRE.
  • When running the source { source-ip-address | interface-type interface-number } command to encapsulate IP packets on a tunnel interface, set the source IP address in the header added during GRE encapsulation to the IP address of the outbound interface on the local IPsec gateway.
  • When running the destination dest-ip-address command to encapsulate IP packets on a tunnel interface, set the destination IP address in the header added during GRE encapsulation to the IP address of the outbound interface on the remote IPsec gateway.
  • Configure an IP address for the tunnel interface. The IP address of the tunnel interface can be any idle IP address. When routes with the tunnel interface as the next hop need to be generated through dynamic routing protocols, the IP addresses of the interfaces at both ends of the GRE tunnel must belong to the same network segment.

When a GRE over IPsec tunnel is established based on ACLs, only an ISAKMP IPsec policy can be configured on the gateways at both ends, and the IPsec policy group can be applied only to physical interfaces. IPsec-protected data flows are GRE-encapsulated data flows. The source and destination network segments in ACLs are the source and destination addresses of a GRE tunnel, that is, the interface IP addresses of the IPsec gateways at both ends of the tunnel.

In GRE over IPsec scenarios, if NAT needs to be configured on the device, you need to configure an ACL rule in which the source IP address is the IP address before NAT and the action is permit.
