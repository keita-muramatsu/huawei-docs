Understanding Intermediate File-based Deployment

During intermediate file-based deployment, the device interacts with the DHCP server, intermediate file server, and deployment file server. Figure 1 shows the intermediate file-based deployment process.

Figure 1 Intermediate file-based deployment process
  1. Preparing deployment files and making an intermediate file

    An engineer prepares deployment files and makes an intermediate file on a terminal such as a PC in advance. The intermediate file can be an .ini file (Intermediate File in the INI Format) or Python script (Intermediate File in Python Format).

  2. Deploying the DHCP server, intermediate file server, and deployment file server

    The engineer configures the DHCP server and file server and saves the intermediate file to the intermediate file server and the deployment files to the deployment file server. The engineer can also configure the DHCP relay agent, DNS server, and Syslog server as required. The functions of each device are as follows:

    • DHCP relay agent: relays DHCP packets between the device and the DHCP server when they are located on different network segments.
    • DHCP server: assigns a temporary management IP address, default gateway address, DNS server address, intermediate file server address, and intermediate file name.
    • Intermediate file server: stores the intermediate file required for ZTP deployment. By parsing the intermediate file, the device can obtain information such as the deployment file server address and deployment file name. An intermediate file server must be an SFTP/HTTP/TFTP/FTP file server.

    • Deployment file server: stores the deployment files to be loaded to the device, including the system software, configuration file, and patch file. The deployment file server and intermediate file server can be combined, which must be an SFTP, HTTP, TFTP, or FTP file server.

    • DNS server: provides mappings between domain names and IP addresses, and resolves the file server domain name to an IP address for the device. Based on the resolved IP address, the device can connect to the file server to obtain requested files.
    • Syslog server: records important information in user logs during ZTP deployment and uploads the logs to the NMS.

  3. Powering on the device

    The deployment person powers on and starts the device. The device starts with a configuration file if one is available. Otherwise, the device automatically starts the ZTP process.

  4. Obtaining DHCP information

    1. The device sends DHCP request packets through its Layer 3 physical interface.
    2. The DHCP server sends a DHCP reply packet to the device. The Option parameters in the packet specify the information that the device needs to obtain from the DHCP server.

  5. Obtaining the intermediate file and deployment files

    The device downloads the intermediate file from the intermediate file server according to the information carried in the DHCP reply packet. It then downloads deployment files from the deployment file server according to the intermediate file.

  6. (Optional) Starting the Syslog server

    The device obtains the IP address of the Syslog server from the DHCP reply packet and enables the Syslog server function. Information about important phases during device deployment is recorded in user logs, which the Syslog server will upload to the NMS.

  7. Automatically completing deployment

    The device determines whether to activate each deployment file online based on activation modes defined in the intermediate file or set a deployment file as a system startup file and restart to complete automatic deployment.

  • When deploying an unconfigured device, you are advised not to manually deliver the same configurations as those delivered during ZTP. Doing so will cause the configurations to be deleted if the deployment fails.
  • ZTP depends on OPS. You can run the display ops process current command to obtain the task ID, which indicates the ZTP process ID, and then run the ops stop process process-id command to stop the ongoing ZTP process. This operation, however, may cause the configurations that have been delivered during ZTP to be retained on the device.
