Understanding CAPWAP

CAPWAP Tunnel Establishment

A WAC manages and controls APs through CAPWAP tunnels, which provide the following functions:
  • Maintaining the connectivity state between the WAC and APs
  • Allowing the WAC to manage APs and deliver configurations to them
  • Allowing APs to transmit service data to the WAC for centralized forwarding
Figure 1 Flowchart for establishing a CAPWAP tunnel
Figure 1 shows the process for establishing a CAPWAP tunnel. Specifically, this process involves the following phases:

  1. Discovery phase: A client sends a Discovery Request message to find an available server. The server determines whether to allow the client to access the network. The server does not respond to Discovery Request messages sent by clients that are denied access to the network.

    Clients can discover servers in static or dynamic mode.

    • Static mode

      A static IP address list of servers is preconfigured on clients. When a client goes online, it unicasts a Discovery Request message to each server in the preconfigured IP address list. After receiving the Discovery Request message, the servers respond to the client with a Discovery Response message. The client then selects a server to establish a CAPWAP tunnel.

    • Dynamic mode

      A client can dynamically discover servers in one of these modes: Dynamic Host Configuration Protocol (DHCP), domain name service (DNS), and broadcast. Details on each of the modes are as follows:

      • DHCP mode: A client obtains the IP address of a server through DHCP (by configuring DHCP Offer messages to carry the server IPv4 address list in Option 43 on the DHCP server), and then unicasts a Discovery Request message to the server. After receiving the Discovery Request message, the server responds to the client with a Discovery Response message.

      • DNS mode: A client obtains the server domain name and DNS server IP address through the DHCP service (by configuring the DHCP server to carry the domain name of the server in Option 15 in DHCP Offer messages), and sends a request to the DNS server to obtain the IP address corresponding to the server domain name. Based on the reply from the DNS server, the client unicasts a Discovery Request message to the server. After receiving the Discovery Request message, the server responds to the client with a Discovery Response message.

        After obtaining the domain name of the server from Option 15 in the DHCP Offer message, the automatically adds the fixed prefix huawei-wlan-controller to this domain name. After sending this "prefix + domain name" to the DNS server, the client obtains the IP address of the server. The following example illustrates this mechanism: The domain name ac.test.com of the server is configured on the DHCP server. After obtaining this domain name, the client automatically adds the fixed prefix to it and then sends huawei-wlan-controller.ac.test.com to the DNS server (where the IP address corresponding to huawei-wlan-controller.ac.test.com has been configured) for resolution.

      • Broadcast mode: A client broadcasts a Discovery Request message to discover servers on the same network segment and then selects one to associate with based on the Discovery Response messages returned by the servers. The client and server then start to establish a CAPWAP tunnel. This process varies slightly depending on whether the client has obtained the IP address of the server.
        • Upon a failure to obtain the IP address of any server: The client broadcasts a Discovery Request message. If no server responds to the broadcast message twice, the client determines a failure to discover a server. The client then continues to repeat the preceding operations periodically until it discovers a server.
        • Upon successfully obtaining the IP address of a server: The client unicasts a Discovery Request message to the server. If no response is received after unicasting three Discovery Request messages, the client broadcasts the Discovery Request message. If there is still no response from any server, the client repeats the operations of sending unicast and broadcast messages. If no response is received after the process is completed twice, the client determines a failure to discover a server. The client then continues to repeat the preceding operations periodically until it discovers a server.

    If both static and dynamic modes are configured to specify WACs' IP addresses for an AP, the AP sends a unicast Discovery Request packet to the WAC addresses obtained in both modes.

    After receiving Discovery Response packets from multiple WACs, the AP selects a WAC to set up a link based on WAC information carried in the packets. The WAC selection is determined based on the following priorities in descending order:

    1. Maximum number of access APs supported by a WAC. The AP selects the WAC that supports access of the most APs.
    2. Maximum number of access STAs supported by a WAC. The AP selects the WAC that supports access of the most STAs.
    3. IP address. The AP selects the WAC with the smallest IP address.

  2. CAPWAP tunnel establishment phase:

    CAPWAP tunnels fall into two categories: data tunnel and control tunnel. Whether both types need to be established or only the latter does depends on the data forwarding mode.
    • CAPWAP data tunnel: transmits data packets received by clients to the server for centralized forwarding.
    • CAPWAP control tunnel: transmits control packets between the server and clients. Datagram Transport Layer Security (DTLS) encryption can be enabled for CAPWAP control tunnels to encrypt and decrypt CAPWAP control packets.

DTLS Encryption for CAPWAP Control Tunnels

Extending the protocol architecture of Transport Layer Security (TLS), DTLS ensures the security for UDP packets, which are used by CAPWAP. After DTLS encryption is configured for a CAPWAP control tunnel, packets exchanged over the tunnel are encrypted using DTLS on both ends of the tunnel. This ensures packet integrity and privacy.

DTLS allows a client and a server to establish a session by performing a handshake. During the handshake, the client and server authenticate each other and then negotiate the key and cipher suite for encrypting data to be transmitted.

Figure 2 Handshake process in PSK-based DTLS encryption mode

The following describes the handshake process in DTLS encryption based on the pre-shared key (PSK) demonstrated in Figure 2:

  1. The DTLS client sends a ClientHello message to the DTLS server, carrying the SSL protocol version, encryption algorithm type, generated random number, session ID, and other necessary information for communication between this client and other DTLS servers.
  2. The DTLS server returns a HelloVerifyRequest message to the DTLS client, carrying the cookie value that the DTLS server obtains by hashing the DTLS client's IP address.
  3. The DTLS client sends a ClientHello message to the DTLS server, carrying the cookie value it receives from the DTLS server.
  4. The DTLS server verifies the validity of the ClientHello message based on the received cookie value, selects the highest-priority algorithm it supports, and sends a ServerHello message to the DTLS client. In this step, the DTLS server also sends other associated messages:

    ServerKeyExchange message containing the DTLS server's PSK ID to the DTLS client

    ServerHelloDone message to the DTLS client, indicating that the ServerHello message and associated messages have been sent

  5. After receiving the ServerHello message and associated messages, the DTLS client sends a ClientKeyExchange message to the DTLS server. This message is encrypted using the PSK corresponding to the PSK ID sent by the DTLS server. If the DTLS server successfully decrypts the received message, the DTLS client is successfully authenticated. In this step, the DTLS server also sends other associated messages:

    ChangeCipherSpec message, notifying the DTLS server that the subsequent messages will be encrypted using the latest negotiated encryption algorithm and key

    Finished message, notifying the DTLS server that the handshake is complete

  6. The DTLS server sends a ChangeCipherSpec message to the client, notifying the client that the data to be sent will be encrypted using the latest negotiated algorithm and key.

    The DTLS server sends a Finished message to notify the DTLS client that the handshake is complete.

  7. The DTLS client and DTLS server start data communication.

CAPWAP Tunnel Maintenance

To maintain the state of a CAPWAP tunnel, both ends of the tunnel periodically exchange different packets to detect tunnel connectivity.

  • Keepalive packets for a CAPWAP data tunnel (on the UDP port 5247)
  • Echo packets for a CAPWAP control tunnel (on the UDP port 5246)

CAPWAP Packet Fragmentation

After a CAPWAP packet is encapsulated, the encapsulated device checks whether the packet size exceeds the interface maximum transmission unit (MTU). If so, the device fragments the inner CAPWAP packet. For example, if the interface MTU is 1500 bytes, the maximum payload of a CAPWAP packet is 1456 bytes (1500 – 20 – 8 – 16, where 20 is the length of the IP packet header, 8 is the length of the UDP packet header, and 16 is the length of the CAPWAP packet header). Given this, if the payload of a CAPWAP packet exceeds 1456 bytes, the CAPWAP packet is fragmented.

After the CAPWAP inner fragmentation function is enabled, an AP fragments received user data packets at the IP layer prior to CAPWAP encapsulation, thereby eliminating the need for fragmentation at the CAPWAP layer. As a result, packets arrive at the WAC in order, without being reassembled.
