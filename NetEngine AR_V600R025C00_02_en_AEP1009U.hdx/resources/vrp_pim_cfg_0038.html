Understanding PIM-SM Anycast RP

Anycast rendezvous point (RP) allows you to configure multiple RPs with the same address in a PIM-SM domain and set up peer relationships between RPs. In this way, a multicast source can register to the closest RP, and receivers can join the closest RP. This alleviates burdens on a single RP, implements RP backup, and optimizes forwarding paths.

In a traditional PIM-SM domain, each multicast group can be mapped to only one RP. When the network is overloaded or traffic congestion occurs, the following problems may occur: the RP is overburdened; route convergence is slow after the RP fails; the multicast forwarding path is not optimal. Currently, anycast RP can be implemented in a PIM-SM domain using Multicast Source Discovery Protocol (MSDP) or PIM anycast RP. When deploying a network, you can use either of the two solutions. It is not recommended that you use both solutions simultaneously. In a PIM-SM domain, MSDP and PIM cannot be used together to configure an anycast RP.

If anycast RP is implemented using PIM, you can also configure a device to advertise the data source information obtained from MSDP peers in another domain to peers in the local domain. PIM anycast RP applies to a single PIM-SM domain. To enable an RP to obtain the source and group information in another PIM-SM domain, you can use either of the following schemes:

  • Set up an MSDP peer relationship between every anycast RP member in a PIM-SM domain and an RP in another PIM-SM domain.

  • Set up MSDP peer relationships between some anycast RP members in a PIM-SM domain with the RP in another PIM-SM domain. When the members that have set up MSDP peer relationships receive MSDP SA messages, they convert the messages into Register messages and send them to those that do not set up MSDP peer relationships.

Anycast RP can be implemented in either of the preceding schemes. A receiver and multicast source each select the closest RPs to create RPTs. After receiving multicast data, the receiver DRs determine whether to trigger an SPT switchover. In this way, the optimal RP path and load sharing are implemented. The following describes how anycast RP is implemented using PIM.

Figure 1 Typical networking diagram of implementing anycast RP using PIM
In a PIM-SM domain of the network shown in Figure 1, multicast sources (Source1 and Source2) send multicast data to multicast group G, and Receiver1 and Receiver2 are members of group G. Perform the following operations to use PIM to implement anycast RP in the PIM-SM domain:

  • Configure RP1 and RP2 and assign both the same RP address (address of a loopback interface). Assume that the RP address is 10.10.10.10.

  • Set up a connectionless peer relationship between RP1 and RP2 using unique addresses. Assume that the local address of RP1 is 1.1.1.1 and the local address of RP2 is 2.2.2.2 in the peer relationship.

The process of implementing anycast RP using PIM is as follows:
  1. Receivers send Join messages to the closest RPs and build RPTs.

    • U1 joins the RPT with RP1 as the root, and RP1 creates an (*, G) entry.

    • U2 joins the RPT with RP2 as the root, and RP2 creates an (*, G) entry.

  2. Multicast sources register with the closest RPs.

    • DR1 sends a Register message to RP1, and RP1 creates an (S1, G) entry. Multicast data from S1 reaches U1 along the RPT.

    • DR2 sends a Register message to RP2, and RP2 creates an (S2, G) entry. Multicast data from S2 reaches U2 along the RPT.

  3. After receiving Register messages from the source DRs, the RPs re-encapsulate the Register messages and forward them to peers for multicast source information sharing.

    • After receiving the (S1, G) Register message from DR1, RP1 replaces the source and destination addresses in the Register message with 1.1.1.1 and 2.2.2.2, respectively, and re-encapsulates the message and sends it to RP2. After RP2 receives the Register message, it detects that the message was sent from peer 1.1.1.1. In this case, RP2 processes the message without forwarding it to other peers.

    • After receiving the (S2, G) Register message from DR2, RP2 replaces the source and destination addresses in the Register message with 2.2.2.2 and 1.1.1.1, respectively, and re-encapsulates the message and sends it to RP1. After RP1 receives the Register message, it detects that the message was sent from peer 2.2.2.2. In this case, RP1 processes the message without forwarding it to other peers.

  4. RPs join SPTs with the source DRs as the roots to obtain multicast data.

    • RP1 sends a Join message to S2. Multicast data from S2 first reaches RP1 along the SPT and then reaches U1 along the RPT.

    • RP2 sends a Join message to S1. Multicast data from S1 reaches RP2 along the SPT and then reaches U2 along the RPT.

  5. After receiving multicast data, the receiver DRs determine whether to trigger an SPT switchover.
