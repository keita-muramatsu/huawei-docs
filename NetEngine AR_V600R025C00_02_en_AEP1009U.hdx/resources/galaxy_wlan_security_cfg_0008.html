WPA and WPA2 Security Policies

Wired Equivalent Privacy (WEP) is a security protocol defined in IEEE 802.11 that is used to protect data of authorized STAs from eavesdropping during transmission on a WLAN. WEP uses the shared key authentication mode to encrypt data based on Rivest Cipher 4 (RC4) — a symmetric stream cipher algorithm. This authentication algorithm uses a single shared static key for all users. As such, the encryption mechanism and algorithm are both vulnerable to security threats.

To overcome such drawbacks of WEP, the Wi-Fi Alliance released Wi-Fi Protected Access (WPA) as an interim solution.

In addition to the RC4 algorithm, WPA defines the Temporal Key Integrity Protocol (TKIP) encryption algorithm on the basis of WEP. Following WPA, IEEE 802.11i launched WPA2, which uses a more secure encryption algorithm — Counter Mode with Cipher Block Chaining Message Authentication Code Protocol (CCMP).

A typical WPA/WPA2 security policy involves four phases: link authentication, access authentication, key negotiation, and data encryption. To deliver better compatibility, both WPA and WPA2 support pre-shared key (PSK) authentication in the access authentication phase, and the TKIP or CCMP encryption algorithm in the data encryption phase. They offer almost the same security level, mainly differing in the protocol packet format.

The following details the phases for implementing a security policy.

Link Authentication

Before a STA associates with an AP for WLAN access, link authentication must be performed in open system or shared key mode. For details about link authentication, see "STA Access Process" in CLI Configuration Guide > WLAN Configuration > STA Access Configuration.

WPA and WPA2 support only the open system mode for link authentication.

Access Authentication

In the link authentication phase, open system authentication does not use STAs' identities for authentication. That is, all STAs that request link authentication can associate with APs, which provides no data protection. To ensure security, access authentication is required. During STA access, you can specify the access authentication mode and data encryption algorithm in the association phase. For details about association, see "STA Access Process" in CLI Configuration Guide > WLAN Configuration > STA Access Configuration.

WPA/WPA2-Personal uses the WPA/WPA2-PSK authentication and applies to small networks with relatively low security requirements, such as individual and home networks. Without the need for a dedicated authentication server, WPA/WPA2-Personal only requires the PSK preconfigured on the WLAN node (such as a WLAN server, wireless router, or network adapter). In this way, users only need to enter the correct PSK on the STAs for authentication. The WPA/WPA2-PSK authentication process is as follows:

  1. The PSK is set on the AP.
  2. The user enters the PSK on the STA during STA association.
  3. The AP and STA check whether they have the same PSK during key negotiation.
  4. If key negotiation is successful, this means the PSK entered by the user is valid and STA access authentication is successful. If key negotiation fails, this means STA access authentication fails.

Note that the PSK is used only for identity authentication, not for data encryption.

Key Negotiation

During key negotiation, the PSK is used to generate a pairwise master key (PMK) based on the key hierarchy model defined in 802.11i. The PMK is then used to generate and install the other types of keys through key negotiation.

PMK generation

In PSK authentication, the method for generating a PMK varies depending on the PSK format.
  • If a PSK is in hexadecimal format, it is used as the PMK.
  • If a PSK is a string of characters, the PMK is calculated using the hash algorithm based on the PSK and service set identifier (SSID).

Key type

The 802.11i standard defines two key hierarchy models:
  • Pairwise key hierarchy: protects unicast data exchanged between STAs and APs.
  • Group key hierarchy: protects broadcast or multicast data between STAs and APs.
The PMK can be used to generate the following two types of keys through key negotiation:
  • Pairwise transient key (PTK): encrypts unicast packets.
  • Group temporal key (GTK): encrypts multicast and broadcast packets.

Key negotiation process

As defined in 802.11i, Extensible Authentication Protocol over LAN (EAPOL)-Key frames are used for key negotiation. Key negotiation is supported for unicast and multicast traffic.

  • Key negotiation for unicast traffic

    Key negotiation for unicast traffic is completed through a four-way handshake. In WPA authentication, a PTK is generated and installed during the four-way handshake. In WPA2 authentication, both a PTK and a GTK are generated and installed during the four-way handshake, as shown in Figure 1.
    Figure 1 Flowchart of key negotiation for unicast traffic
    1. The AP sends an EAPOL-Key frame with an authenticator nonce (ANonce), which is a random number, to the STA.
    2. The STA calculates the PTK based on its own MAC address, MAC address of the AP, PMK, ANonce, and supplicant nonce (SNonce). The STA sends an EAPOL-Key frame to the AP. This frame carries the SNonce, robust security network element (RSNE), and message integrity code (MIC). The AP then calculates the PTK and GTK using its own MAC address, MAC address of the STA, PMK, ANonce, and SNonce, and validates the MIC to determine whether the STA's PMK is the same as its own PMK. If they are the same, the third handshake is performed. Otherwise, the validation fails.
    3. The AP sends an EAPOL-Key frame to the STA, requesting the STA to install the PTK and GTK. This frame carries the ANonce, RSNE, MIC, and encrypted GTK. After receiving the EAPOL-Key frame, the STA validates the MIC. If the validation succeeds, the STA starts the fourth handshake.
    4. The STA sends an EAPOL-Key frame to the AP, notifying that the PTK and GTK have been installed and will be used. After receiving the frame, the AP installs the PTK and GTK.

  • Key negotiation for multicast traffic

    Key negotiation for multicast traffic is completed through a two-way handshake, which begins after a PTK is generated and installed through a four-way handshake. In WPA authentication, the GTK is generated and installed during the two-way handshake, as shown in Figure 2. In contrast, this process is not involved in WPA2 authentication.
    Figure 2 Flowchart for group key negotiation
    1. The AP calculates the GTK, uses the unicast key to encrypt the GTK, and sends an EAPOL-Key frame to the STA.
    2. After receiving the EAPOL-Key frame, the STA validates the MIC, decrypts and installs the GTK, and sends an EAPOL-Key ACK frame to the AP. After receiving the EAPOL-Key ACK frame, the AP validates the MIC and installs the GTK.

Data Encryption

WPA and WPA2 support the TKIP and CCMP encryption algorithms.

  • TKIP

    Unlike WEP, which uses a static shared key, TKIP uses a dynamic key negotiation and management mechanism. That is, each STA can obtain an independent key through dynamic negotiation. The key of each STA is calculated using the PTK generated in key negotiation, MAC address of the sender, and packet sequence number. This mechanism helps defend against WEP-specific attacks.

    TKIP leverages the message integrity check mechanism to ensure the integrity of frames received on the receiver and the validity of data on the sender and receiver. The MIC is calculated using the MIC key generated during key negotiation, destination MAC address, source MAC address, and data frame.

  • CCMP

    While WEP and TKIP use a stream cipher algorithm, CCMP uses a block cipher algorithm based on Advanced Encryption Standard (AES). Overcoming defects of the RC4 algorithm, this block cipher algorithm provides higher security.
