Configuring BGP Peer Relationships Between the Controller and Forwarder

Context

Configuring BGP peer relationships between a controller and a forwarder allows the controller to deliver SRv6 TE Policies to the forwarder. This improves the efficiency of automated SRv6 TE Policy deployment.

The process for a controller to deliver an SRv6 TE Policy is as follows:

  1. The controller collects information, such as network topology and SID information, through BGP-LS.

  2. The controller and headend forwarder establish an IPv6 SR Policy address family-specific BGP peer relationship.

  3. The controller computes an SRv6 TE Policy path and delivers it to the headend forwarder through the BGP peer relationship. The headend then generates an SRv6 TE Policy entry.

To implement the preceding operations, you need to establish a BGP-LS peer relationship and a BGP IPv6 SR Policy peer relationship between the controller and the specified forwarder.

Procedure

  1. Configure a BGP-LS peer relationship.

    BGP-LS is used to collect network topology information in a more efficient and easier manner. To ensure that topology information can be reported correctly, you need to configure a BGP-LS peer relationship between the controller and forwarder. This example provides the configuration procedure on the forwarder. The configuration procedure on the controller is similar.

    1. Enter the system view.

      system-view

    2. Enable BGP and enter the BGP view.

      bgp as-number

    3. Create a BGP peer.

      peer { group-name | ipv6-address } as-number { as-number-plain | as-number-dot }

    4. Enable BGP-LS and enter the BGP-LS address family view.

      link-state-family unicast

    5. Enable the device to exchange route information with a specified BGP-LS peer.

      peer { group-name | ipv6-address } enable

  2. Configure a BGP IPv6 SR Policy peer relationship.

    This example provides the configuration procedure on the forwarder. The configuration procedure on the controller is similar.

    1. Enter the system view.

      system-view

    2. Enable BGP and enter the BGP view.

      bgp as-number

    3. Create a BGP peer.

      peer { group-name | ipv6-address } as-number { as-number-plain | as-number-dot }

    4. Enter the BGP IPv6 SR Policy address family view.

      ipv6-family sr-policy

    5. Enable the device to exchange route information with a specified BGP IPv6 SR Policy peer.

      peer { group-name | ipv6-address } enable

    6. (Optional) Configure the device to advertise SRv6 TE Policy routes to EBGP peers.

      advertise ebgp enable

    7. (Optional) Configure router ID filtering.

      router-id filter

      If the RR connection mode is used to reduce the number of required connections, you can configure router ID filtering on non-RRs to discard the traffic optimization policies that are not required by the local device. This prevents a large number of policy nodes from being generated due to the receiving of massive policy-based routes, thereby guaranteeing performance.

    8. (Optional) Configure a mode in which the device processes specified path attributes.

      You can configure attribute-id as required. The sub-attribute-id parameter can be configured only when attribute-id is set to 23, which indicates the tunnel encapsulation attribute.

      peer { peerIpv4Addr | peerIpv6Addr } path-attribute-treat attribute-id { id [ to id2 ] } &<1-255> { discard | withdraw | treat-as-unknown }
Alternatively: peer { peerIpv4Addr | peerIpv6Addr } path-attribute-treat attribute-id id3 sub-attribute-id sub-attribute-id-val treat-as-unknown }

    9. (Optional) Configure a mode in which the device processes the specified incorrect path attribute.

      peer { peerIpv4Addr | peerIpv6Addr } treat-with-error attribute-id id accept-zero-value
