Configuring IPsec Multi-Instance

Context

IPsec multi-instance can isolate traffic on different subnets. To achieve this, an IKE-negotiated IPsec tunnel needs to be bound to a VPN instance on an IKE peer.

Pay attention to the following points when configuring IPsec multi-instance:
  • Before configuring IPsec multi-instance, run the ip vpn-instance vpn-instance-name and route-distinguisher route-distinguisher commands to create a VPN instance and configure a route distinguisher (RD) for the VPN instance.
  • Run the ip binding vpn-instance vpn-instance-name command on an interface to bind the interface to the specified VPN instance according to the network plan. When an IKE-negotiated IPsec tunnel needs to be established and inter-VPN forwarding is implemented through tunnel interfaces, you need to run the ip binding vpn-instance vpn-instance-name command to bind the specified VPN instance to the tunnel interface that has an IPsec policy applied and whose encapsulation mode is IPsec. You are advised to use tunnel interfaces for inter-VPN forwarding.
  • When an advanced ACL is used to define the data flows to be protected, all rules in the ACL must be bound to the same VPN instance.
  • To enable communication between the VPN instance used for service access and the public system, and between VPN instances, run the ip route-static vpn-instance command to configure static routes.

Procedure

  • Binding an IPsec tunnel to a VPN instance based on SAs
    1. Enter the system view.

      system-view

    2. Enter the IKE peer view.

      ike peer peer-name

    3. Configure the VPN instance to which IPsec tunnel traffic belongs.

      sa binding vpn-instance vpn-instance
quit

      By default, the VPN instance to which IPsec tunnel traffic belongs is not configured on an IKE peer.

      The VPN instance specified by vpn-instance must have been created using the ip vpn-instance vpn-instance-name command, and must be the same as the VPN instance bound to the tunnel interface that has a specific IPsec policy applied, and also the VPN instance bound to the ACL rule that is referenced by the IPsec policy.

    4. Optional: Disable the device from checking VPN instance information in data flows during IPsec encryption and decryption.

      1. Enter the IPsec policy view or policy template view.

        # Enter the ISAKMP IPsec policy view.

        ipsec policy policy-name seq-number [ isakmp ]

        # Enter the template IPsec policy view.

        ipsec policy-template template-name seq-number
      2. Disable the device from checking VPN instance information in data flows during IPsec encryption and decryption.
        flow-vrf check disable

        By default, the device checks VPN instance information in data flows during IPsec encryption and decryption.

        In the scenario where branches connect to the headquarters, multiple VPN instances are typically deployed at the headquarters so that the branches access different VPN instances based on services. The IPsec tunnel of the headquarters can be bound to only one VPN instance, and therefore routes need to be imported between VPNs to implement inter-VPN traffic forwarding. To prevent the device from discarding packets of the VPN instance that is different from the VPN instance of the interface that receives these packets, perform this step to disable the function of checking VPN instance information in data flows during IPsec encryption and decryption.

  • Binding an IPsec tunnel to a VPN instance based on an IKE user table

    When an IPsec tunnel is bound to a VPN instance based on an IKE user table, the device determines the VPN instance to which branch traffic passing through an IPsec tunnel belongs based on users. This isolates traffic from different branches. The configuration of binding an IPsec tunnel to a VPN instance based on an IKE user table takes precedence over that based on SAs.

    1. Enter the system view.

      system-view

    2. Enter the IKE user table view.

      ike user-table user-table-id

      The user table specified by user-table-id is an IKE user table that has been created.

    3. Enter the IKE user view.

      user user-name

      The user specified by user-name is an IKE user that has been created.

    4. Configure the VPN instance to which traffic of users in the IKE user table belongs.

      vpn-instance-traffic { public | name vpn-instance-name }
quit

      The VPN instance specified by vpn-instance-name must have been created using the ip vpn-instance vpn-instance-name command, and must be the same as the VPN instance bound to the tunnel interface that has a specific IPsec policy applied, and also the VPN instance bound to the ACL rule that is referenced by the IPsec policy.

    5. Return to the system view.

      quit

    6. Enter the IKE peer view.

      ike peer peer-name

    7. Configure the IKE peer to reference the specified IKE user table.

      user-table user-table-id
quit

    8. Optional: Disable the device from checking VPN instance information in data flows during IPsec encryption and decryption.

      1. Enter the IPsec policy template view.
        ipsec policy-template template-name seq-number
      2. Disable the device from checking VPN instance information in data flows during IPsec encryption and decryption.
        flow-vrf check disable

        By default, the device checks VPN instance information in data flows during IPsec encryption and decryption.

        In the scenario where branches connect to the headquarters, multiple VPN instances are typically deployed at the headquarters so that the branches access different VPN instances based on services. The IPsec tunnel of the headquarters can be bound to only one VPN instance, and therefore routes need to be imported between VPNs to implement inter-VPN traffic forwarding. To prevent the device from discarding packets of the VPN instance that is different from the VPN instance of the interface that receives these packets, perform this step to disable the function of checking VPN instance information in data flows during IPsec encryption and decryption.
