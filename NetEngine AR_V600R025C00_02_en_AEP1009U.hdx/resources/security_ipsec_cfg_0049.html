Configuring Invalid SPI Recovery for IPsec

Prerequisites

Invalid SPI recovery takes effect only for the following IPsec types:

  • ACL-based IPsec (involving ISAKMP IPsec policies)
  • Route-based IPsec (involving IPsec profiles)

Context

If the local device of an IPsec tunnel loses all IPsec SAs but still has IKE SAs, and the remote device still holds the corresponding IPsec SAs, the local device immediately discards the IPsec SA-encapsulated packets received from the remote device because the local device cannot find the corresponding IPsec SA. In addition, the local device sends a DELETE SA INFORMATIONAL message to the remote device by default. After the remote device receives the message, it immediately deletes the IPsec SA with the invalid SPI. If the remote device continues to send IPsec packets to the local device, the two devices will renegotiate to establish an IPsec SA. In this way, interrupted IPsec services can be restored in a timely manner.

However, if neither IKE SAs nor IPsec SAs exist on the local device, the local device cannot send a DELETE SA INFORMATIONAL message to the remote device. IPsec services will be interrupted for a long time until DPD detects that IPsec SAs are invalid or until the IPsec SA lifetime expires. To solve this problem, enable invalid SPI recovery so that the local device initiates IPsec SA renegotiation with the remote device to restore interrupted IPsec services in a timely manner.

Procedure

  1. Enter the system view.

    system-view

  2. Enable invalid SPI recovery.

    ipsec invalid-spi-recovery enable

    By default, invalid SPI recovery is disabled.
