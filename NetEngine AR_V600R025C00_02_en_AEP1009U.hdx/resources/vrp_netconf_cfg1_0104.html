Understanding PnP VLAN Auto-Negotiation

Background

If the DHCP server does not use the default VLAN 1 and an unconfigured device is connected, the device automatically uses VLAN 1 to obtain the NETCONF enabling status and iMaster NCE-Campus information from the DHCP server after being powered on and started. In this case, the device cannot obtain the NETCONF enabling status and iMaster NCE-Campus information, and cannot register with iMaster NCE-Campus. To solve this problem, PnP VLAN auto-negotiation is introduced:

There are two types of PnP VLANs: wired and wireless PnP VLANs. The device obtains the IP address of iMaster NCE-Campus and the IP address of itself through the wired PnP VLAN. If an AP is connected to a device, the device automatically changes the PVID of the interface connected to the AP to the wireless PnP VLAN ID. PnP VLAN negotiation involves both wired and wireless PnP VLANs. If only the wired PnP VLAN is configured and no wireless PnP VLAN is configured, the interface connected to the AP is added to the wired PnP VLAN. The priority of the PnP VLAN transmitted to the downstream device is as follows: Statically configured wireless PnP VLAN > Statically configured wired PnP VLAN > wireless PnP VLAN learned from the upstream device > Wired PnP VLAN learned from the upstream device.

Procedure

  • PnP VLAN access procedure

    As shown in Figure 1, the VLAN of the DHCP server is changed to another VLAN instead of the default one (VLAN 1). An unconfigured device (DeviceC) is connected to the network.

    Figure 1 Campus network diagram
    1. If DeviceA has NETCONF enabled and has registered with iMaster NCE-Campus, iMaster NCE-Campus delivers a PnP VLAN to DeviceA based on the preconfiguration. If DeviceA does not have NETCONF enabled, a PnP VLAN is manually configured on DeviceA using a command. DeviceA can communicate properly with the DHCP server through the wired PnP VLAN.
    2. DeviceC connects to the network and auto-negotiates with the upstream device (DeviceA) to obtain the PnP VLAN.
    3. DeviceC uses the negotiated wired PnP VLAN to obtain the NETCONF enabling status and iMaster NCE-Campus information from the DHCP server. This process implements plug-and-play.
    4. DeviceB identifies that the downstream device is an AP and changes the PVID of the interface connected to the AP to the wireless PnP VLAN.
    After devices managed by iMaster NCE-Campus support auto-negotiation of PnP VLANs, the advantages are as follows:
    • A new device can connect to the network through any interface of an upstream device, and the upstream device can identify the access interface and adds the interface to the PnP VLAN.
    • If an upstream device and a downstream device are connected through multiple links, they can auto-negotiate the multiple links as an Eth-Trunk interface and auto-negotiate the working mode of the Eth-Trunk as LACP.
  • Processing a PnP VLAN switchover

    As shown in Figure 2, when NETCONF is enabled on the upstream device, iMaster NCE-Campus modifies the PnP VLAN of the upstream device to trigger the downstream device to use the new PnP VLAN for re-registration. When the upstream device does not have NETCONF enabled, you can modify the PnP VLAN of the upstream device using a command to enable the downstream device to use the new PnP VLAN for re-registration.

    The upstream device's PnP VLAN and the management VLAN are two concepts. The two VLANs can be the same or different. The downstream device can register with iMaster NCE-Campus normally only when iMaster NCE-Campus communicates with the upstream device normally.

    When the upstream device has NETCONF enabled, changing the PnP VLAN enables only the downstream device but not the upstream device for registration. Whether the upstream device registers again depends on whether its management VLAN is changed.
