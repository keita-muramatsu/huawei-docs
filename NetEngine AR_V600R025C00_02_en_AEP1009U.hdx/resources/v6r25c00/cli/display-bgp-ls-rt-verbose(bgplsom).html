display bgp link-state unicast routing-table (All views)

Function

The display bgp link-state unicast routing-table command displays BGP-LS route information.

Format

display bgp link-state unicast routing-table [ peer { ipv4-address | ipv6-address } { received-routes | advertised-routes } ] bgp-ls-prefix

Parameters

Parameter Description Value
peer ipv4-address

Specifies an IPv4 peer address.

The value is in dotted decimal notation.
ipv6-address

Specifies an IPv6 peer address.

The value is a 32-digit hexadecimal string in format X:X:X:X:X:X:X:X.
received-routes

Displays BGP-LS routes received from the specified peer.

-
advertised-routes

Displays BGP-LS routes advertised to the specified peer.

-
bgp-ls-prefix

Specifies a BGP-LS route prefix.

The BGP-LS route prefix format is complex. To facilitate your query, run the display bgp link-state unicast routing-table command to check all BGP-LS routes, and copy the prefix of the route whose information is to be queried when specifying prefix.

Views

All views

Default Level

1: Monitoring level

Usage Guidelines

Usage Scenario

The display bgp link-state unicast routing-table command displays BGP-LS routing information. BGP-LS routes carry network topology information. BGP-LS routes are classified into node routes, link routes, prefix routes, TE Policy routes, and SRv6-SID routes and carry node, link, prefix, TE Policy, and SRv6-SID information, respectively. The five types of routes cooperate with each other to transmit topology information.

Precautions

Sub-TLVs contained in the Network Layer Reachability Information (NLRI) carried in BGP-LS routes need to be sorted in ascending order of Type values according to the protocol standard. If the sub-TLV contained in the message received from a non-Huawei device does not comply with the protocol standard, the message cannot be parsed and the corresponding specific route cannot be viewed.

BSID flag:

* D-Flag (0x8000): indicates the BSID data plane. If this flag is set, the value is a 16-byte SRv6 SID. If this flag is cleared, the value is a 4-byte SR/MPLS label.

* B-Flag (0x4000): When this flag is set, a BSID is assigned in the BSID field. When this flag is cleared, no BSID is assigned.

Flags

TE policy descriptor:

* E-Flag (0x80): If this flag is set, the endpoint address is an IPv6 address. If this flag is cleared, the endpoint address is an IPv4 address.

* O-Flag (0x40): If this flag is set, the initiator address is an IPv6 address. If this flag is cleared, the initiator address is an IPv4 address.

CP State:

* S-Flag (0x8000): If this flag is set, the candidate path is in the administratively closed state.

* A-Flag (0x4000): If this flag is set, the candidate path is an active path (for example, a path deployed on the forwarding plane).

* B-Flag (0x2000): If this flag is set, the candidate path is a backup path of an SR Policy (to protect the primary path).

* E-Flag (0x1000): If this flag is set, validity of the candidate path has been evaluated. (The headend evaluates the validity of the candidate path based on the priority.).

* V-Flag (0x0800): If this flag is set, the candidate path has at least one valid SID-List. When the E-Flag is cleared (for example, the candidate path has not been evaluated), this flag must be set to 0 by the initiator and ignored by the receiver.

* O-Flag (0x0400): If this flag is set, the candidate path has been instantiated based on the on-demand next-hop trigger of the local template. For details, see 8.5 of [I-D.ietf-spring-segment-routing-policy].

* D-Flag (0x0200): If this flag is set, the candidate path is delegated to a PCE or controller for computation.

* C-Flag (0x0100): If this flag is set, the candidate path is provided by the PCE or controller.

* I-Flag (0x0080): If this flag is set, the candidate path is discarded when it is invalid when no other active path is available for the SR Policy and the path is the optimal one among active candidate paths. For details, see 8.2 [I-D.ietf-spring-segment-routing-policy].
