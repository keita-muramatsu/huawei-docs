traffic-policy (interface view)

Function

The traffic-policy command applies a traffic policy to an interface.

The undo traffic-policy command deletes a traffic policy from an interface.

By default, no traffic policy is applied to an interface.

Format

traffic-policy policy-name { inbound | outbound } [ preprocess | firstprocess ]

undo traffic-policy policy-name inbound

undo traffic-policy policy-name outbound

Parameters

Parameter Description Value
policy-name

Specifies the name of a traffic policy.

The value is a string of 1 to 31 case-sensitive characters without spaces.
outbound

Applies a traffic policy to the outbound direction.

-
inbound

Applies a traffic policy to the inbound direction.

-
preprocess

Specifies the traffic policy as a preprocessing traffic policy.

-
firstprocess

Specifies the traffic policy as a preferential processing traffic policy.

-
undo

Cancels the current setting.

-

Views

10GE sub-interface view, 10GE interface view, 25GE interface view, 40GE interface view, Dialer interface view, Eth-Trunk interface view, GE sub-interface view, GE interface view, Multi-GE interface view, VLANIF interface view, Sub-interface view, Interface group view, Ethernet interface view, Ethernet sub-interface view

Default Level

2: Configuration level

Usage Guidelines

Usage Scenario

Packets can be classified based on Layer 2 information, Layer 3 information, or ACLs. To provide differentiated services for service flows, bind a traffic classifier and a traffic behavior to a created traffic policy and apply the traffic policy. You can run the traffic-policy command to apply a created traffic policy to an interface.

  • A common traffic policy, a preprocessing traffic policy, and a preferential processing traffic policy can be applied to the same direction of an interface. Their priorities in descending order of priority are as follows: preprocessing traffic policy > preferential processing traffic policy > common traffic policy. A traffic policy can be applied to different directions on different interfaces. If traffic matches the traffic classifier bound to a traffic behavior that defines the deny action in the preprocessing traffic policy, the traffic is discarded. Otherwise, the traffic is matched against traffic classifiers in the preferential processing traffic policy. If the traffic matches the traffic classifier bound to a traffic behavior that defines the deny action in the preferential processing traffic policy, the traffic is discarded. Otherwise, the traffic is matched against traffic classifiers in the common traffic policy. If the traffic matches a traffic classifier in any of the traffic policies, the traffic behavior defined in the traffic policy is performed for the traffic.
  • With the proliferation of users and service types on networks, it becomes ever-more critical to offer differentiated services to users. You can configure hierarchical scheduling in the inbound direction of a tunnel interface to differentiate both services and users, implementing refined QoS. You can specify the decap-process parameter to configure MQC for the decapsulation service on the physical interface where traffic enters the device, and then enable a decapsulation traffic policy on a tunnel interface. When traffic passes through the tunnel interface, the decapsulation traffic policy configured on the physical interface is executed. In this way, hierarchical scheduling is implemented on the tunnel interface.

Prerequisites

  • A traffic policy has been created using the traffic policy command, and traffic classifiers and traffic behaviors have been bound to the traffic policy.
  • If the decap-process parameter is specified, the qos car inbound decap-process command has been run in the interface view to configure the bandwidth limit for the decapsulation service in the inbound direction of the interface.
  • When a CBQ or HQoS policy is applied to a serial, MP-group, POS, or IP-Trunk interface, if the interface is down and the queue capability is disabled by default, the policy fails to be applied. If the interface is up and the queue capability is enabled by default, the policy is delivered normally.

Follow-up Procedure

After the traffic-policy inbound decap-process command is configured, run the traffic-policy decap-process enable command on a tunnel interface to enable the traffic policy decapsulation function on the tunnel interface.

Precautions

  • After a traffic policy is applied, it cannot be deleted directly. To delete a traffic policy that has been applied, run the undo traffic-policy command in the corresponding view to cancel the application of the traffic policy, and then run the undo traffic policy command in the system view to delete the traffic policy.
  • After a traffic policy is applied, you can modify the matching rules in the traffic classifier, ACL rules, actions in the traffic behavior, and binding between the traffic classifier and traffic behavior in the traffic policy. However, the modification may cause a failure to deliver the traffic policy. In this case, a message is displayed, indicating that the traffic policy fails to be delivered. If a traffic policy fails to be delivered, you can run the display traffic-policy applied-record command to check the cause of the delivery failure.
  • When a traffic policy is applied to an Eth-Trunk interface, if a member interface is updated, the traffic policy is delivered again. As a result, the applied traffic policy becomes invalid temporarily.
  • A traffic policy cannot match Layer 2 traffic.
  • When specifying the preprocess or firstprocess parameter, pay attention to the following points:
    • The traffic behavior in a preprocessing traffic policy supports only the statistic enable (traffic behavior view) and deny | permit commands.
    • The traffic behavior in a preferential processing traffic policy supports only the statistic enable (traffic behavior view), deny | permit, car (traffic behavior view), and remark dscp commands.
    • The following fields can be defined in preprocessing and preferential processing traffic policies: IPv4 address, IPv6 address, port number, protocol type, ToS, DSCP, fragment flag, TCP flag, VPN instance, application, and application group.
  • When specifying the decap-process parameter, pay attention to the following points:
    • The decap-process parameter is not supported in the 5G channelized interface view, Eth-Trunk interface view, and tunnel interface view.
    • The decap-process parameter is used at the management level. If the decap-process parameter is not specified, the command is used at the configuration level.
    • In traffic behaviors of the decapsulation traffic policy, only aggregated CAR can be configured. That is, the share parameter must be specified in the car command so that all the rules in traffic classifiers bound to the same traffic behavior share the CAR parameters.
    • When configuring traffic behaviors in the decapsulation traffic policy, you are advised to permit green and yellow packets and discard red packets. Otherwise, hierarchical scheduling may fail to be implemented.
    • To configure hierarchical scheduling on a tunnel interface, you must run all of the qos car inbound decap-process, traffic-policy inbound decap-process, and traffic-policy decap-process enable commands. Otherwise, hierarchical scheduling does not take effect.

Example

# Create a traffic policy p1, bind the created traffic classifier c1 and traffic behavior b1 to the traffic policy, and apply the traffic policy to the inbound direction on interface.
<HUAWEI> system-view
[HUAWEI] traffic classifier c1
[HUAWEI-classifier-c1] quit
[HUAWEI] traffic behavior b1
[HUAWEI-behavior-b1] quit
[HUAWEI] traffic policy p1
[HUAWEI-trafficpolicy-p1] classifier c1 behavior b1
[HUAWEI-trafficpolicy-p1] quit
[HUAWEI] interface 10GE 0/0/1
[HUAWEI-10GE0/0/1] traffic-policy p1 inbound
