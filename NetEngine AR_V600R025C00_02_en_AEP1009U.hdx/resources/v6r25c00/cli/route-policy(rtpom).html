route-policy

Function

The route-policy command creates a route-policy and displays the route-policy view.

The undo route-policy command deletes a created route-policy.

By default, no route-policy is created.

Format

route-policy route-policy-name matchMode node node

undo route-policy route-policy-name [ node node ]

Parameters

Parameter Description Value
route-policy-name

Specifies the name of the route-policy.

The value is a string of 1 to 200 case-sensitive characters without spaces. The character string can contain spaces if it is enclosed with double quotation marks (").
matchMode

Specifies the matching mode of the route-policy.

The value is an enumerated type:

  • permit: Specifies the matching mode of the route-policy as permit.
  • deny: Specifies the matching mode of the route-policy as deny.
node node

Specifies the index of the node in the route-policy.

The value is an integer ranging from 0 to 65535. When the route-policy is used to filter routes, the node with the smaller value is matched against first.

Views

System view

Default Level

2: Configuration level

Usage Guidelines

Usage Scenario

A route-policy is used to filter routes and set route attributes for the routes that pass the filtering. A route-policy can contain multiple nodes. One node can be configured with multiple if-match and apply clauses. The if-match clauses define matching rules for this node, and the apply clauses define behaviors for the routes that match the rules.

The relationship among if-match clauses that are based on different route attributes is AND in the same route-policy node. Specifically, a route is considered to match a node only if it matches all the if-match clauses of the node. The relationship among if-match clauses that are based on the same route attribute is OR in the same route-policy node. Specifically, a route is matched against the if-match clauses in order; if the route matches an if-match clause, the route is considered to match the route-policy and will not be matched against the rest if-match clauses. For example, node 10 has two if-match clauses: if-match community-filter 1 and if-match as-path-filter 1. The two if-match clauses are based on different route attributes. Therefore, the relationship between them is AND. Node 20 also has two if-match clauses: if-match community-filter 1 and if-match community-filter 2. The two if-match clauses are both based on the community attribute. Therefore, the relationship between them is OR. If no if-match clause is specified, all routes match this node.

The relationship between the nodes in a route-policy is "OR". That is, if a route matches one node in a route-policy, the route matches this route-policy. If a route does not match any node in a route-policy, the route fails to match this route-policy.

Generally, you are advised not to use the same route-policy to filter both IPv4 and IPv6 routes.

For example, if both IPv4 and IPv6 BGP peer relationships exist, you are advised to separate the route-policies configured for IPv4 peers from those configured for IPv6 peers. Detailed configurations are as follows:

#

bgp 65001

peer x.x.x.x as-number 65001

peer x::x as-number 65001

#

ipv4-family unicast

peer x.x.x.x enable

peer x.x.x.x route-policy policyV4 export

#

ipv6-family unicast

peer x.x.x.x enable

peer x::x route-policy policyV6 export

In this scenario, you are advised to configure one route-policy for IPv4 peer x.x.x.x and another route-policy for IPv6 peer x::x.

The following example describes the use of the same route-policy to filter both IPv4 and IPv6 routes.

Scenario 1: In a node in deny mode of a route-policy, some if-match clauses are used to filter IPv4 routes, and other if-match clauses are used to filter IPv6 routes.

#

route-policy policy1 deny node 10

if-match ip-prefix prefix-a

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 permit node 30

Explanation:

If the if-match clauses of a node are based on different attributes, a route matches the node only if the matching conditions specified in all the if-match clauses of the node are met.

By default:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a match the if-match clause and are denied by node 10. They are no longer matched against other nodes. Therefore, these routes cannot match the route-policy. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 30. Because no if-match clause is configured for IPv4 routes in node 30, which is in permit mode, all the IPv4 routes that do not match ip-prefix prefix-a are permitted by node 30.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv6 routes that match prefix-list prefix-a-v6 match the if-match clause and are denied by node 10. They are no longer matched against other nodes. Therefore, these routes cannot match the route-policy. The IPv6 routes that do not match prefix-list prefix-a-v6 are further matched against node 30. Because no if-match clause is configured for IPv6 routes in node 30, which is in permit mode, all the IPv6 routes that do not match prefix-list prefix-a-v6 are permitted by node 30.

By default, the IPv4 routes that match ip-prefix prefix-a and IPv6 routes that match prefix-list prefix-a-v6 are denied, and the other routes are permitted.

Scenario 1 (a): If node 20 is added to the route-policy to filter only IPv4 or IPv6 routes, unexpected results may occur.

For example, IPv4 routes need to be filtered in this scenario due to service changes. Therefore, node 20 is added and prefix-a-2 is used to filter IPv4 routes.

#

route-policy policy1 deny node 10

if-match ip-prefix prefix-a

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 deny node 20

if-match ip-prefix prefix-a-2

#

route-policy policy1 permit node 30

Explanation:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a match the if-match clause and are denied by node 10. They are no longer matched against other nodes. Therefore, these routes cannot match the route-policy. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 20. The IPv4 routes that match ip-prefix prefix-a-2 match the if-match clause and are denied. Node 30 is in permit mode. Therefore, the IPv4 routes that do not match ip-prefix prefix-a or ip-prefix prefix-a-2 are permitted.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv6 routes that match prefix-list prefix-a-v6 match the if-match clause and are denied by node 10. They are no longer matched against other nodes. Therefore, these routes cannot match the route-policy. The IPv6 routes that do not match prefix-list prefix-a-v6 are further matched against node 20. Because no if-match clause is configured for IPv6 routes in node 20, which is in deny mode, all the IPv6 routes that do not match prefix-list prefix-a-v6 are denied by node 20. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, no IPv6 route can match the route-policy.

By default, only the IPv4 routes that do not match ip-prefix prefix-a or ip-prefix prefix-a-2 are permitted, and the other IPv4 routes and all IPv6 routes are denied.

According to the analysis in scenario 1, the user intends to filter out some IPv4 routes (matching prefix-a-2) by adding a node to the original filter. However, it turns out that all IPv6 routes fail to pass the filtering of the route-policy.

Scenario 2: In a node in permit mode of a route-policy, one if-match clause is used to filter IPv4 routes, and another if-match clause is used to filter IPv6 routes.

#

route-policy policy1 permit node 10

if-match ip-prefix prefix-a

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 deny node 30

Explanation:

If the if-match clauses of a node are based on different attributes, a route matches the node only if the matching conditions specified in all the if-match clauses of the node are met.

By default:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a match the if-match clause and are permitted by node 10. Therefore, these routes directly match the route-policy. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 30. Because no if-match clause is configured for IPv4 routes in node 30, which is in deny mode, all the IPv4 routes that do not match ip-prefix prefix-a are denied by node 30.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv6 routes that match prefix-list prefix-a-v6 match the if-match clause and are permitted by node 10. Therefore, these routes directly match the route-policy. The IPv6 routes that do not match prefix-list prefix-a-v6 are further matched against node 30. Because no if-match clause is configured for IPv6 routes in node 30, which is in deny mode, all the IPv6 routes that do not match prefix-list prefix-a-v6 are denied by node 30.

By default, IPv4 routes that match ip-prefix prefix-a and IPv6 routes that match prefix-list prefix-a-v6 are permitted, and other routes are denied.

Scenario 2 (a): If node 20 is added to the route-policy to filter only IPv4 or IPv6 routes, unexpected results may occur.

For example, IPv6 routes need to be filtered in this scenario due to service changes. Therefore, node 20 is added and prefix-a-v6-2 is used to filter IPv6 routes.

#

route-policy policy1 permit node 10

if-match ip-prefix prefix-a

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 permit node 20

if-match ipv6 address prefix-list prefix-a-v6-2

#

route-policy policy1 deny node 30

Explanation:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a match the if-match clause and are permitted by node 10. Therefore, these routes directly match the route-policy. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 20. Because no if-match clause is configured for IPv4 routes in node 20, which is in permit mode, all the IPv4 routes that do not match ip-prefix prefix-a are permitted by node 20. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, all IPv4 routes match the route-policy.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv6 routes that match prefix-list prefix-a-v6 match the if-match clause and are permitted by node 10. Therefore, these routes directly match the route-policy. The IPv6 routes that do not match prefix-list prefix-a-v6 are further matched against node 20. The IPv6 routes that match prefix-list prefix-a-v6-2 match the if-match clause and are permitted. Node 30 is in deny mode. Therefore, the IPv6 routes that do not match prefix-list prefix-a-v6 or prefix-list prefix-a-v6-2 are denied.

By default, in this scenario, the IPv6 routes that do not match prefix-list prefix-a-v6 or prefix-list prefix-a-v6-2 are denied, and other IPv6 routes and all IPv4 routes are permitted.

According to the analysis in scenario 2, the user intends to permit some other IPv6 routes (matching prefix-a-v6-2) by adding a node to the original filter. However, it turns out that all IPv4 routes match the route-policy.

In the preceding scenario, the same route-policy is used to filter both IPv4 and IPv6 routes at the beginning, and the expected result can be obtained. However, if this configuration habit is retained for a long time, services may be interrupted due to improper use when services are changed.

In some scenarios, the same route-policy is used to filter both IPv4 and IPv6 routes. However, some nodes have only IPv4 if-match clauses, and other nodes have only IPv6 if-match clauses. As a result, unexpected results are more likely to occur. The following are examples:

Scenario 3: A route-policy is used to filter only IPv4 routes, but the route-policy is referenced by IPv6.

For example:

#

route-policy policy1 deny node 10

if-match ip-prefix prefix-a

#

route-policy policy1 permit node 30

Explanation:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a are denied. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 30 and permitted. No problem occurs in all IPv4 scenarios.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). Because node 10 (in deny mode) does not contain any if-match clause for IPv6 routes, all IPv6 routes are denied by node 10 by default. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, no IPv6 route can match the route-policy.

In conclusion, the IPv4 routes that do not match ip-prefix prefix-a are permitted, and the other IPv4 routes and all IPv6 routes are denied.

Scenario 4: A route-policy is used to filter only IPv6 routes, but the route-policy is referenced by IPv4.

For example:

#

route-policy policy1 deny node 20

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 permit node 30

Explanation:

a. In IPv6 scenarios, routes are matched against node 20 first according to the matching sequence (in ascending order). The IPv6 routes that match prefix-list prefix-a-v6 are denied. The IPv6 routes that do not match prefix-list prefix-a-v6 are matched against node 30 and are permitted. No problem occurs in all IPv6 scenarios.

b. In IPv4 scenarios, routes are matched against node 20 first according to the matching sequence (in ascending order). Because node 20 (in deny mode) does not contain any if-match clause for IPv4 routes, all IPv4 routes are denied by node 20 by default. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, no IPv4 route can match the route-policy.

In conclusion, the IPv6 routes that do not match prefix-list prefix-a-v6 are permitted, and the other IPv4 routes and all IPv6 routes are denied.

Scenario 5: In the same route-policy, some nodes are used to filter IPv4 routes, and other nodes are used to filter IPv6 routes. Some routes to be permitted are denied by the deny node in advance due to address family mismatch.

For example:

#

route-policy policy1 deny node 10

if-match ip-prefix prefix-a

#

route-policy policy1 deny node 20

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 permit node 30

Explanation:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a are denied. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 20. Because no if-match clause is configured for IPv4 routes in node 20, which is in deny mode, all the IPv4 routes that do not match ip-prefix prefix-a are denied by node 20. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, no IPv4 route can match the route-policy.

b. In the IPv6 scenario, routes are matched against the route-policy in sequence. Node 10 is matched first. Because node 10 (in deny mode) does not contain any if-match clause for IPv6 routes, all IPv6 routes are denied by node 10 by default. According to the one-time matching rule of the route-policy, node 20 and node 30 are not executed. As a result, no IPv6 route can match the route-policy.

In conclusion, all IPv4 or IPv6 routes are denied in this scenario.

Scenario 6: In the same route-policy, some nodes are used to filter IPv4 routes, and other nodes are used to filter IPv6 routes. Some routes to be denied are permitted by the permit node in advance due to address family mismatch.

For example:

#

route-policy policy1 permit node 10

if-match ip-prefix prefix-a

#

route-policy policy1 permit node 20

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 deny node 30

Explanation:

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes that match ip-prefix prefix-a are permitted. The IPv4 routes that do not match ip-prefix prefix-a are further matched against node 20. Because no if-match clause is configured for IPv4 routes in node 20, which is in permit mode, all the IPv4 routes that do not match ip-prefix prefix-a are permitted by node 20. According to the one-time matching rule of the route-policy, node 30 is not executed. As a result, all IPv4 routes match the route-policy.

b. In the IPv6 scenario, routes are matched against the route-policy in sequence. Node 10 is matched first. Because node 10 (in permit mode) does not contain any if-match clause for IPv6 routes, all IPv6 routes are permitted by node 10 by default. According to the one-time matching rule of the route-policy, node 20 and node 30 are not executed. As a result, all IPv6 routes match the route-policy.

In conclusion, all IPv4 or IPv6 routes are permitted in this scenario.

According to the preceding analysis, when the same route-policy is used to filter both IPv4 and IPv6 routes, unexpected results may occur due to the default matching rule of if-match clauses. Therefore, you are advised to separate the route-policies used to filter IPv4 routes from those used to filter IPv6 routes.

In some special service scenarios, if only one route-policy can be used, you are advised to run the route-policy address-family mismatch-deny command before running the route-policy command.

For example, in a BGP EVPN scenario, BGP EVPN peers can transmit both IPv4 and IPv6 routes through the same peer relationship. In this case, only one route-policy can be used.

In this scenario, to prevent service interruption caused by improper configurations, you are advised to use the following configuration methods:

#

route-policy policy1 permit node 10

if-match ip-prefix prefix-a

#

route-policy policy1 permit node 20

if-match ipv6 address prefix-list prefix-a-v6

#

route-policy policy1 deny node 30

#

route-policy policy1 address-family mismatch-deny

Explanation:

After the route-policy address-family mismatch-deny command is run, if the address family of a route does not match the address family specified in the if-match clause of the route-policy, the matching fails.

a. In IPv4 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). The IPv4 routes matching ip-prefix prefix-a match the if-match clause and are permitted. The IPv4 routes that do not match ip-prefix prefix-a are matched against node 20. Node 20 does not have any IPv4 route matching rule, and the route-policy address-family mismatch-deny command is run on the device. Therefore, these IPv4 routes fail to match node 20. Then, the IPv4 routes that do not match ip-prefix prefix-a are matched against node 30. Node 30 does not have any IPv4 route matching rule, and the route-policy address-family mismatch-deny command is run on the device. Therefore, these IPv4 routes fail to match node 30. In conclusion, the IPv4 routes that do not match ip-prefix prefix-a are denied by route-policy policy1.

b. In IPv6 scenarios, routes are matched against node 10 first according to the matching sequence (in ascending order). Node 10 does not have any matching rules for IPv6 routes. Moreover, because the route-policy address-family mismatch-deny command is run, these IPv6 routes fail to match node 10. All IPv6 routes are further matched against node 20. The IPv6 routes that match prefix-list prefix-a-v6 match the if-match clause and are permitted by node 20. Then, the IPv6 routes that do not match ip-prefix prefix-a-v6 are matched against node 30. Node 30 does not have any IPv6 route matching rule, and the route-policy address-family mismatch-deny command is run on the device. Therefore, these IPv6 routes fail to match node 30. In conclusion, the IPv6 routes that do not match ip-prefix prefix-a-v6 are denied by route-policy policy1.

The preceding analysis shows that routes can be accurately filtered in the BGP EVPN scenario based on the preceding configuration. To add IPv4 filtering conditions due to subsequent service expansion, you can add if-match clauses under node 10 or add IPv4 filtering nodes. To add IPv6 filtering conditions, add if-match clauses under node 20 or add IPv6 filtering nodes.

Precautions

You can run the display route-policy command to check the number of routes permitted and denied by the filter.

If a route-policy contains only ip-prefix-based filtering rules, these rules apply to IPv4 prefixes, not to IPv6 prefixes, and IPv6 prefixes match these rules by default. If IPv6 prefixes also need to be filtered, add an ipv6-prefix-based if-match clause. Similarly, if a route-policy contains only ipv6-prefix-based filtering rules, these rules apply to IPv6 prefixes, not to IPv4 prefixes, and IPv4 prefixes match these rules by default. If IPv4 prefixes also need to be filtered, add an ip-prefix-based if-match clause.

When a route-policy is used to control the advertisement or acceptance of BGP routes, the priority of the peer-specific configuration is higher than that of a peer group-specific configuration.

In the scenario where an if-match clause references a matching rule, if the referenced matching rule contains only the deny index, the current policy node is skipped and routes are matched against the next route-policy node.

A route-policy denies all unmatched routes by default. If more than one node is defined in a route-policy, at least one of the nodes must be in permit mode.

If a route-policy node is not configured with any if-match or goto clause, subsequent nodes with larger indexes cannot be executed. As a result, the configuration may be incorrect. Example:

route-policy test permit node 10

apply community 100

route-policy test permit node 20

apply community 200

In this case, node 20 cannot be executed.

If a route-policy is configured with multiple nodes with the same configuration, the configuration may be incorrect. Example:

route-policy test permit node 10

apply community 100

route-policy test permit node 20

apply community 100

The following if-match clauses may be used to filter both IPv4 and IPv6 routes in a route-policy: if-match clauses for prefix matching, nexthop matching, source matching, and ACL matching. The following uses prefix-based if-match clauses as an example to describe unexpected situations that may occur when a route-policy filters both IPv4 and IPv6 routes. The method of configuring other if-match clauses is similar to that of configuring prefix-based if-match clauses. The configuration principles are as follows:

  1. Generally, you are not advised to use the same route-policy to filter both IPv4 and IPv6 routes.
  2. In service scenarios where only one route-policy can be used, you are advised to run the route-policy address-family mismatch-deny command before running the route-policy command.

After a route-policy node is created, deleted, or configured, if all nodes in the route-policy are in permit mode and if-match is not configured, the route-policy is a permit-all policy. If a permit-all policy is configured and a route-policy node is added, this node cannot be executed. In addition, if a permit-all policy is applied, all routes pass the policy, which may cause problems such as overload.

After a route-policy node is created, deleted, or configured, if all nodes in the route-policy are in deny mode, the route-policy is a deny-all policy. If a deny-all policy is configured and a route-policy node is added, this node cannot be executed. In addition, if a deny-all policy is applied, all routes are denied by the policy, which may cause problems such as route unavailability.

A maximum of 65535 route-policies are supported.

A single route-policy supports a maximum of 65535 nodes.

All route-policies support a maximum of 65535 nodes.

Example

# Configure the route-policy named policy1 whose node number is 10 and matching mode is permit.
<HUAWEI> system-view
[HUAWEI] ip ip-prefix prefix-a index 10 permit 172.17.1.0 24
[HUAWEI] route-policy policy1 permit node 10
[HUAWEI-route-policy] if-match ip-prefix prefix-a
[HUAWEI-route-policy] apply cost 100
