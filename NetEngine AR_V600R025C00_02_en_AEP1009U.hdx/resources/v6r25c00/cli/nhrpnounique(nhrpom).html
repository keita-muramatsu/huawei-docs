nhrp registration no-unique

Function

The nhrp registration no-unique command configures a device to send NHRP packets with the no-unique flag, instructing the remote end to overwrite conflicting NHRP peer entries.

The undo nhrp registration no-unique command configures a device to send NHRP packets without the no-unique flag, instructing the remote end not to overwrite conflicting NHRP peer entries.

By default, NHRP packets without the no-unique flag are sent, so that new NHRP mapping entries do not override conflicting NHRP peer entries during NHRP registration.

Format

nhrp registration no-unique

undo nhrp registration no-unique

Parameters

None

Views

Tunnel interface view

Default Level

2: Configuration level

Usage Guidelines

Usage Scenario

This command can only be configured on spoke nodes. When a spoke node sends an NHRP Registration Reply packet to the hub node, whether this packet carries the no-unique flag determines whether the hub node can override the conflicting NHRP peer entries from this spoke node.

When a spoke node performs NHRP registration with the hub node, the hub node generates an NHRP peer entry for the spoke node. If the spoke node performs NHRP registration again after its public IP address changes, by default, the NHRP registration packet sent by this spoke node does not carry the no-unique flag. After receiving this packet, the hub node does not override the conflicting NHRP peer entry of this spoke node and rejects this NHRP registration. If the hub node needs to save the latest spoke node information and override the conflicting NHRP peer entries, run the nhrp registration no-unique command on the spoke node to enable the NHRP registration packets sent by this spoke node to carry the no-unique flag.

In scenarios where spoke nodes obtain their addresses dynamically (such as LTE scenarios), you are advised to run the nhrp registration no-unique command on spoke nodes. This allows them to send NHRP packets that carry the no-unique flag to instruct the hub node to overwrite conflicting NHRP peer entries. Without this, the spoke nodes cannot re-register with the hub node successfully.

Prerequisites

The following operations have been performed:

  • Run the interface tunnel command to create a tunnel interface and display the tunnel interface view.
  • Run the tunnel-protocol gre p2mp command to set the tunnel encapsulation mode to mGRE.

Configuration Impact

The following situations occur when the spoke re-registers with the hub after the public address of the spoke is changed:

  • If the nhrp registration no-unique command is used on the spoke, the device overrides existing NHRP peer entries with new NHRP peer entries.
  • If the nhrp registration no-unique command is not configured on a spoke node, new NHRP peer entries will not override existing NHRP peer entries on a hub node and new registration entries will be discarded. New registration entries can successfully register only when old NHRP peer entries are aged out.

Example

# Configure the device to send NHRP packets that carry the no-unique flag to instruct the peer end to overwrite conflicting NHRP peer entries.
<HUAWEI> system-view
[HUAWEI] nhrp enable
[HUAWEI] interface tunnel 0
[HUAWEI-Tunnel0] tunnel-protocol gre p2mp
[HUAWEI-Tunnel0] nhrp enable
[HUAWEI-Tunnel0] nhrp registration no-unique
