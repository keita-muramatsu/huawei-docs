radius-server support chargeable-user-identity

Function

The radius-server support chargeable-user-identity command configures the device to support the CUI attribute.

The undo radius-server support chargeable-user-identity command restores the default configuration.

By default, the device does not support the CUI attribute.

Format

radius-server support chargeable-user-identity

radius-server support chargeable-user-identity not-reject

undo radius-server support chargeable-user-identity

Parameters

Parameter Description Value
not-reject

Indicates that the device does not process the CUI attribute.

-

Views

RADIUS server template view

Default Level

3: Management level

Usage Guidelines

In the carrier network roaming charging scenario, the user name may be different in different network environments. Therefore, the user name cannot be used as the unique identifier for charging. In this case, the RADIUS CUI attribute defined in RFC can be used to solve this problem. The RADIUS authentication server can provide a unique CUI attribute for users as the charging identifier.

By default, RADIUS Access-Request packets sent by the device do not carry the CUI attribute. If the Access-Accept packet returned by the RADIUS server carries the CUI attribute, the device saves the CUI attribute and performs no other processing on the subsequent Accounting-Request (Start), Accounting-Request (Interim-update), and Accounting-Request (Stop) packets. The value is carried as it is.

After the radius-server support chargeable-user-identity [not-reject] command is run, the device sends RADIUS Access-Request packets with the CUI attribute set to Null.

  • If the Access-Accept packet returned by the RADIUS server contains the CUI attribute, the device saves the CUI attribute and sends subsequent accounting request packets (including Accounting-Request(Start), Accounting-Request(Interim-update), and Accounting-Request(Stop) packets). Carry the original in the middle; The UGW9811 includes the previously delivered CUI attribute in subsequent Access-Request packets triggered by re-authentication, authentication overwriting, or roaming.
  • If the Access-Accept packet returned by the RADIUS server does not carry the CUI attribute or the CUI attribute is null:
  • If not-reject is not specified, user authentication fails.
  • If not-reject is specified, the device ignores the CUI attribute and user authentication succeeds.

Example

# Configure the device to support the CUI attribute.
<HUAWEI> system-view
[HUAWEI] radius-server template test1
[HUAWEI-radius-test1] radius-server support chargeable-user-identity
