OSPFV3/4/OSPFV3_NSSA_TRANS_STATE_CHG

Message

OSPFV3/4/OSPFV3_NSSA_TRANS_STATE_CHG: The status of the NSSA translator changes. (RouterId=[RouterId], AreaId=[AreaId], NSSATranslatorState=[NSSATranslatorState], ProcessId=[ProcessId])

Description

The NSSA transition role may be changed because the status of the device changes between Enabled, Selected, and Disabled.

Parameters

Parameter Name Parameter Meaning

RouterId

Router ID of the device generating this trap.

AreaId

Area ID of the NSSA.

NSSATranslatorState

New NSSA translator state, which can be:

  • 1: ENABLED
  • 2: ELECTED
  • 3: DISABLED

ProcessId

OSPFv3 process ID.

Possible Causes

Cause 1: The translator-always option of the NSSA command was manually configured or deleted on an ABR in the NSSA.

Cause 2: A new router ID is configured on an ABR in the NSSA and the new router ID takes effect.

Cause 3: A new device is added to the NSSA or a device is removed from the NSSA.

Cause 4: A device in the backbone area or the NSSA restarts OSPFv3 or performs a master/slave main control board switchover, causing topology flapping in the area.

Cause 5: The ABR role of the local device changed.

Cause 6: The topology of the backbone area or the NSSA changes. As a result, the local device cannot route routes from the backbone area or the NSSA to another ABR with a larger router ID or with the translator-always option configured.

Procedure

1. If the nssa translator-always command was manually configured or deleted on the local device, run the display ospfv3 area command to check whether the translator state of the local device is correct.

  • If the nssa translator-always command was configured, run the display ospfv3 area command to check whether the NSSA translator state is always. If yes, go to Step 8. If no, go to Step 7.
  • If the nssa translator-always command was deleted, run the display ospfv3 area command to check the NSSA translator state. If the NSSA translator state is Disabled, go to Step 2. If the NSSA translator state is Elected, go to Step 8.

2. The nssa translator-always command may have been run on an ABR in the NSSA. You can run the display ospfv3 [ ] lsdb router command to check whether the Nt bit is carried in the Router-LSA sent by an ABR in the NSSA or check whether the nssa translator-always parameter has been configured for another ABR in the NSSA.

  • If the Nt bit is carried or the nssa translator-always parameter is configured for another ABR, go to Step 8.
  • If the Nt bit is not carried or the nssa translator-always parameter is not configured for another ABR, go to Step 3.

3. If a new router ID was configured for the local device and has taken effect, check whether the NSSA translator state of the local device is correct after the topology in the NSSA becomes stable.

  • If it is correct, go to Step 8.
  • If it is incorrect, go to Step 4.

4. If a new router ID was configured for another ABR in the NSSA, check the configuration of this ABR.

  • If the router ID of the ABR changed, check whether the new router ID is greater than the local router ID after the topology in the area becomes stable. If yes, go to Step 8. If no, go to Step 6.
  • If the ABR is correctly configured, go to Step 5.

5. If a new device was added to the NSSA:

  • If the added device is an ABR, check whether its router ID is greater than the local router ID after the topology in the area becomes stable. If yes, go to Step 8. If no, go to Step 6.
  • If the added device is not an ABR, go to Step 6.

6. Check whether the alarms OSPFV3_1.3.6.1.2.1.191.0.2 ospfv3NbrStateChange and OSPFV3_1.3.6.1.2.1.191.0.10 ifstatechange were generated on the local device and its neighbor.

  • If the preceding alarms were generated, deal with them according to the related handling procedure.
  • If the preceding alarms were not generated, go to Step 7.

7. Collect alarm and configuration information, and contact technical support engineers.

8. End.
