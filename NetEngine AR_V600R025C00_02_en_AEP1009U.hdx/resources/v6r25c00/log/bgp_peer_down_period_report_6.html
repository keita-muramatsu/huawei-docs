BGP/6/BGP_PEER_DOWN_PERIOD_REPORT

Message

BGP/6/BGP_PEER_DOWN_PERIOD_REPORT: Logs are recorded periodically after the BGP neighbor goes Down. (BgpIndex=[BgpIndex], InstanceId=[InstanceId], AddrFamilyAfi=[AddrFamilyAfi], AddrFamilySafi=[AddrFamilySafi], PeerAddrType=[PeerAddrType], PeerIpv4Ipv6Addr=[PeerIpv4Ipv6Addr], LocalIfIndex=[LocalIfIndex], LocalIfName=[LocalIfName], PeerLastError=[PeerLastError], PeerState=[PeerState], ReasonIndex=[ReasonIndex])

Description

Logs are periodically recorded after the BGP peer relationship is interrupted.

Parameters

Parameter Name Parameter Meaning

BgpIndex

Index of a BGP instance.

InstanceId

ID of a VPN instance.

AddrFamilyAfi

Address family:

  • 1: ipv4
  • 2: ipv6
  • 25: vpls
  • 196: l2vpn
  • 16388: link-state
  • 36879: rpd

AddrFamilySafi

Sub-address family:

  • 1: unicast
  • 2: multicast
  • 3: Unicast & multicast
  • 4: mpls
  • 5: mvpn
  • 65: vpls
  • 66: mdt
  • 70: evpn
  • 71: link-state
  • 73: srpolicy
  • 74: sdwan
  • 128: vpn
  • 129: vpnv4 multicast
  • 132: vpn orf
  • 133: flowv4
  • 134: flowvpn
  • 179: rpd
  • 245: tunnel-encap-ext
  • 255: mvrf

PeerAddrType

Address type of a peer.

PeerIpv4Ipv6Addr

Address of a peer. Only IPv6 addresses are reported in this alarm.

LocalIfIndex

Index of the local interface.

LocalIfName

Name of the local interface.

PeerLastError

Error code when the peer was disconnected last time.

The value of this parameter is displayed in the format of [ErrorCode][ErrorSubCode], where [ErrorCode] indicates the error code and [ErrorSubCode] indicates the error subcode. For example, 35, where 3 indicates an error code and 5 indicates an error subcode. For details about error codes, see "BGP Message Format" in BGP Fundamentals. If this parameter is set to 0, no error occurs.

PeerState

Status of the peer.

ReasonIndex

Index of the reason why the peer is disconnected.

  • 1: The peer relationship is torn down due to configurations.
  • 2: A Notification message is received.
  • 3: An error message is received.
  • 4: The Hold timer expires.
  • 5: The remote peer is unreachable.
  • 6: The directly connected interface is Down.
  • 7: The number of routes reaches the upper limit.
  • 8: The system memory is overloaded.

Possible Causes

Cause 1: The BGP peer relationship is disconnected due to BGP configurations.

Cause 2: BGP received a Notification message.

Cause 3: BGP received an error message.

Cause 4: The BGP hold timer expires.

Cause 5: The BGP remote end is unreachable.

Cause 6: The BGP directly connected interface is disconnected.

Cause 7: The number of BGP routes exceeds the upper limit.

Cause 8: The system memory is overloaded.

Procedure

Cause 1: Incorrect BGP configurations caused the peer relationship to be interrupted.

1. Check whether the interruption is caused by incorrect configurations.

  • If yes, go to Step 2.
  • If no, go to Step 3.

2. Delete the incorrect configurations to restore the connection.

3. Check whether the BGP connection is reset. Wait for a while and then check whether the connection can be re-established.

4. Collect log and configuration information, and contact technical support engineers.

Cause 2: A BGP Notification message was received.

1. Run the display bgp peer ip-address log-info command to check the Notification information about the BGP disconnection.

  • If the error code in the Notification message is 4, the BGP hold timer expires and no Keepalive message is received. In this case, go to Step 3.
  • If the error code in the Notification message is 5, the BGP FSM is faulty. In this case, go to Step 17.
  • If the error code in the Notification message is 6, the BGP connection is manually torn down. In this case, go to Step 2.

2. Run the display bgp peer ip-address log-info command to check whether the Notification is sent by the device that generates the alarm.

  • If yes, go to Step 3.
  • If no, go to Step 4.

3. Run the ping command to check whether the IP address of the BGP peer can be pinged.

  • If yes, go to Step 4.
  • If no, go to Step 5.

4. Check whether the CPU usage is too high.

  • If yes, go to Step 17.
  • If no, go to Step 6.

5. Run the display ip routing-table command to check whether the BGP peer address exists in the routing table.

  • If yes, go to Step 7.
  • If no, go to Step 8.

6. Run the display acl command to check whether an ACL is configured on the device to deny TCP port 179.

  • If yes, delete the ACL that denies TCP port 179.
  • If no, go to Step 9.

7. Run the display interface command to check whether the outbound interface of the route is up.

  • If yes, go to Step 17.
  • If no, go to Step 10.

8. Check the origin of the route with the BGP peer address.

  • If the route origin is OSPF, go to Step 11.
  • If the route origin is IS-IS, go to Step 12.

9. Check the BGP configuration to see whether a loopback interface is used to establish the BGP connection.

  • If yes, go to Step 13.
  • If no, go to Step 14.

10. Check whether the shutdown command is run on the interface.

  • If yes, run the undo shutdown command on the interface. - If the alarm persists, go to Step 13.
  • If no, go to Step 17.

11. Run the display ospf peer command to check whether the OSPF neighbor relationship is established.

  • If yes, go to Step 17.
  • If no, see the procedure for handling the alarm OSPF_1.3.6.1.2.1.14.16.2.2 ospfNbrStateChange.

12. Run the display isis peer command to check whether the IS-IS neighbor relationship is established.

  • If yes, go to Step 17.
  • If no, see the procedure for handling the alarm ISIS_1.3.6.1.3.37.2.0.17 isisAdjacencyChange.

13. Check whether a source address is specified for the BGP connection.

  • If yes, go to Step 14.
  • If no, run the peer connect-interface command to configure the source address used to initiate the BGP connection.

14. If the EBGP peer relationship is established and multiple hops exist between EBGP peers, check whether the peer ebgp-max-hop command is configured.

  • If yes, go to Step 15.
  • If no, run the peer ebgp-max-hop command.

15. If the peer valid-ttl-hops command is configured, check whether the TTL of the message received from the peer device is in the range of [255 – hops + 1, 255].

  • If yes, go to Step 16.
  • If no, run the peer valid-ttl-hops command to ensure that the TTL value of the message received from the peer device is in the range of [255 – hops + 1, 255].

16. Contact maintenance engineers of the peer device, and check whether BGP has been reset on the peer device, whether the peer device has been enabled in other address families on the local device, or whether BGP connection parameters have been set.

  • If any of these operations has been performed, wait for a while and then check whether the alarm is cleared.
  • If the alarm persists, go to Step 17.

17. Collect log and configuration information, and contact technical support engineers.

Cause 3: BGP received error messages.

1. Run the display bgp peer ip-address log-info command to check the Notification information about the BGP disconnection.

  • If the error code in the Notification message is 1, BGP received messages with incorrect headers. In this case, go to Step 2.
  • If the error code in the Notification message is 2, BGP received incorrect Open messages. In this case, go to Step 2.
  • If the error code in the Notification message is 3, BGP received incorrect Update messages. In this case, go to Step 2.

2. Collect log and configuration information, and contact technical support engineers.

Cause 6: The directly connected BGP interface was disconnected.

1. Check whether the shutdown command has been run on the interface.

  • If yes, run the undo shutdown command on the interface. - If the alarm persists, go to Step 2.
  • If no, go to Step 2.

2. Collect log and configuration information, and contact technical support engineers.

Cause 7: The number of BGP routes exceeded the upper limit.

1. Check whether the peer route-limit command is run and whether the number of existing routes exceeds the upper limit.

  • If yes, go to Step 2.
  • If no, go to Step 3.

2. Check whether the peer route-limit configuration is necessary.

  • If yes, reduce the number of routes to be less than the upper limit.
  • If no, run the undo peer route-limit command to cancel the configuration of the upper limit on the number of routes.

3. Collect log and configuration information, and contact technical support engineers.
