LDP_1.3.6.1.2.1.10.166.4.0.4 Session-Down-MIB

Trap Buffer Description

The LDP session status is Down. (PeerLsrId=[PeerLsrId], VrfName=[VrfName], SessionType=[SessionType], IfName=[IfName], SubReason=[SubReason], Reason=[Reason])

An LDP session went to Down or remained in the Down state.

Trap Buffer Parameters

Parameter Description

PeerLsrId

Peer LSR ID.

VrfName

VRF for an LDP session.

SessionType

LDP session type: - Local - Remote - Local and remote

IfName

Name of the physical interface.

SubReason

Detailed reason for the LDP session down event.

If an LDP session goes down because an error packet is received, the detailed error type is displayed. If an LDP session goes down because a Notify message is received, the detailed Notify type is displayed. Examples of typical error causes:

  • A packet with an incorrect LDP ID was received (1).
  • A packet with an incorrect version number was received (2).
  • A packet with an incorrect PDU length was received (3).
  • A packet with an incorrect message length was received (5).
  • A packet with an incorrect TLV was received (7).
  • A hello timeout notification message was received (9).
  • A shutdown notification message was received (10).
  • A keepalive timeout notification message was received (20).
  • IGP deleted RLFA IID (1056968430).

If an LDP session goes down because a socket error is received, the detailed error cause or error code is displayed. The following are examples of typical error causes:

  • TCP connection reset (54)
  • TCP connection timeout (60)

If an LDP session goes down because LDP packets fail to be sent or received, the detailed cause is displayed. The following are examples of typical causes:

  • A large number of LDP packets are not processed.
  • Failed to receive the packet.
  • Failed to send the packet.

If an LDP session goes down because LDP fails to set the socket option or LDP receives a socket close message, a detailed error code is displayed.

If the LDP session goes down due to other causes, the value of this field is 0.

Procedure

  • Cause 1: The LDP Hello hold timer expired.

    1. Run the display mpls ldp session <peer-id> command to check the session status. The value of <peer-id> in the command must be consistent with the value of the PeerLdpId field in the alarm information.

    • If the session status is Operational, go to Step 2.
    • If the session status is not Operational, go to Step 3.

    2. The session is in the Up state again. The fault may be caused by the intermittent blinking of the session. Services may have been interrupted. For further analysis based on the log information, go to Step 11.

    3. Run the ping -a <source-ip-address> -c < count > host command multiple times (more than 100) to check whether the link is normal and whether packets are dropped.

    • If so, go to Step 4.
    • If not, go to Step 5.

    4. If the link is unstable, the link is faulty, or the traffic is heavy. Check the link to ensure that the link is stable. Then, go to Step 8.

    5. Run the display mpls ldp interface command on both ends to check whether the interface status is normal based on the Status field.

    If the corresponding interface exists but is not in the Active state, go to Step 8.

    If the corresponding interface does not exist, go to Step 6.

    6. Run the display this command on the interface to check whether LDP is enabled.

    -If so, go to Step 11.

    -If not, go to Step 7.

    7. Run the mpls ldp command on the interface. Go to Step 8.

    8. Run the display this command on the interface to check whether the interface is shut down.

    • If so, go to Step 9.
    • If not, go to Step 11.

    9. Run the undo shutdown command on the interface. Go to Step 10.

    10. Check whether the session is Up.

    • If so, no further action is required.
    • If not, go to Step 11.

    11. Collect alarm, log, and configuration information, and contact technical support personnel.

The value of <peer-id> in the command must be consistent with the value of the PeerLdpId field in the alarm information. The command output must contain the TransportAddress field. Run the display ip routing-table <ip-address> command to check whether information about the route to the peer exists. Check whether the IGP route is correctly configured. If OSPF is used as an IGP, run the display current-configuration configuration ospf command in the OSPF view to check whether OSPF has advertised the routes destined for the addresses of loopback interfaces and corresponding interfaces. If IS-IS is used as an IGP, run the display this command in the loopback interface view and the corresponding interface view to check whether IS-IS is enabled. - If IS-IS is enabled, go to Step 6. - If IS-IS is not enabled, go to Step 5. 5. Restore the routing protocol configurations and check whether the configurations are normal. - If the configurations are normal, go to Step 3. - If the configurations are not normal, go to Step 14. 6. Check whether the session is in the Up state. - If the session is in the Up state, the procedure ends. - If the session is still Down, go to Step 14. 14.
