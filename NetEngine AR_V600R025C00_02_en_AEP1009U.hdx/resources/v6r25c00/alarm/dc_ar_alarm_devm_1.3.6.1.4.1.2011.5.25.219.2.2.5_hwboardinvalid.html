Procedure

  • Cause 1: The power supplied to the board is insufficient.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 6: The EPLD logic of the board failed.

    1. Check whether the faulty board is the active board.

    • If yes, perform the active/standby switchover when the standby board is normal.
    • If not, go to Step 2.

    2. Power off and then power on the faulty board. If the faulty board cannot be registered or the fault persists after the board is registered, replace the faulty board.

  • Cause 7: The in-position board type conflicts with the pre-configured board type.

    1. Delete the pre-configured board configuration in the position.

    2. Remove the board.

    3. Clear the offline configuration of the slot.

  • Cause 8: The clock signals of the board were incorrect.

    1. Check whether the faulty board is reset or powered off and whether services are running properly.

    • If the board is not reset or powered off and services are running properly, go to step 4.
    • If the board is reset or powered off, or services are abnormal, go to step 2.

    2. Power off the faulty board and then power it on.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 3.

    3. Replace the faulty board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 4.

    4. Contact technical support personnel.

    5. End.

  • Cause 9: The board does not support some configurations and cannot register.

    The current system does not support the board. Remove the board.

  • Cause 10: The board does not match the device.

    The current chassis does not support the board. Remove the board.

  • Cause 11: The FPGA local bus self-check failed.

    1. If the faulty board is not the active MPU, go to step 3.

    2. If the standby MPU is normal, run the slave switchover command in the system view to perform an active/standby switchover, and then go to step 1.

    3. Power off and then power on the faulty board.

    4. If the fault persists, replace the faulty board.

  • Cause 12: The SD5K communication failed.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 13: The board obtained abnormal signals from the master and slave MPUs.

    1. Check whether the two MPUs are properly installed. If not, install them properly and check whether the fault is rectified.

    • If the fault is rectified, go to Step 4.
    • If the fault persists, go to Step 2.

    2. If no service is running on the faulty board, perform the following operations in sequence: If the fault is rectified, go to step 4. Otherwise, go to step 3.

    • If the board is not properly installed, install the faulty board properly.
    • If the backplane has bent pins, do not insert a new board into the faulty slot and contact technical support personnel.
    • If the board connector is faulty, replace the board.

    3. If services are running on the faulty board or the fault persists, contact technical support personnel.

    4. End.

  • Cause 14: The device hardware verification failed.

    Reset the board and check whether the fault is rectified. If the fault persists, replace the board.

  • Cause 19: TCAM chip failed.

    1. Check whether the faulty board is reset or powered off and whether services are running properly.

    • If the board is not reset or powered off and services are running properly, go to step 4.
    • If the board is reset or powered off, or services are abnormal, go to step 2.

    2. Power off the faulty board and then power it on.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 3.

    3. Replace the faulty board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 4.

    4. Contact technical support personnel.

    5. End.

  • Cause 20: The FPGA entry of the board may be faulty.

    1. Check whether the faulty board is reset or powered off and whether services are running properly.

    • If the board is not reset or powered off and services are running properly, go to step 4.
    • If the board is reset or powered off, or services are abnormal, go to step 2.

    2. Power off the faulty board and then power it on.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 3.

    3. Replace the faulty board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 4.

    4. Contact technical support personnel.

    5. End.

  • Cause 21: The PCIE of the board was faulty.

    1. Check whether the faulty board is reset or powered off and whether services are running properly.

    • If the board is not reset or powered off and services are running properly, go to step 4.
    • If the board is reset or powered off, or services are abnormal, go to step 2.

    2. Power off the faulty board and then power it on.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 3.

    3. Replace the faulty board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 4.

    4. Contact technical support personnel.

    5. End.

  • Cause 22: The board is not installed properly.

    1. Check whether the line card is properly installed. If not, install the line card properly and check whether the fault is rectified. If the alarm persists, go to step 2.

    2. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 23: The PCIE link of the FPGA and slave CXP is faulty.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 24: Board burnt due to high PoE power.

    Collect alarm and log information and contact Huawei technical support personnel.

  • Cause 26: The master or slave ACT signal of the MPU board is abnormal.

    1. Check whether other boards have low voltage alarms or power-related alarms. If yes, clear the alarms first.

    2. Remove and reinstall the current slave MPU. Check whether the slave MPU is properly installed, whether there are bent pins, and whether the board connector is faulty. Go to step 4.

    3. If the device is reset, remove the other MPU and check whether it is properly installed, whether there are bent pins, and whether the board connector is faulty. Then, go to step 4.

    4. If the board is not properly installed, install the faulty board properly.

    5. If the backplane has bent pins, do not insert a new board into the faulty slot and contact technical support personnel.

    6. If only the connector of the faulty board is faulty, replace the board. Then, go to step 8.

    7. If the slave MPU is not registered or the alarm persists, contact the technical support personnel.

    8. End.

  • Cause 33: The board was not registered.

    Collect alarm, log, and configuration information, and contact technical support.

  • Cause 35: Memory Of The Board Failed.

    1. If the faulty board is not reset or powered off and services are running properly, go to Step 4. Otherwise, go to Step 2.

    2. Power off and then power on the faulty board.

    3. If the board cannot be registered or the alarm cannot be cleared after the board is registered, replace the faulty board.

    4. If the alarm persists, collect alarm, log, and configuration information, and contact technical support personnel.

    5. End.

  • Cause 42: A board of this type is already registered in the chassis.

    Remove the board.

  • Cause 66: The board failed to register after three registration attempts.

    Collect alarm, log, and configuration information, and contact technical support.

  • Cause 67: A board was powered off. Possible causes include: The board was manually powered off; the current version does not support this board; the board temperature was too high; the board was not registered for a long period of time; the board was not working normally.

    1. Replace the board and check whether the alarm is cleared. If the alarm persists, go to step 2.

    2. Collect alarm, log, and configuration information, and contact technical support.

  • Cause 68: The board was powered on.

    Power on the board.

  • Cause 69: The FPGA of the board failed.

    1. Run the EntPhysicalName command to determine the slot number of the faulty board. The first digit after fpga indicates the FPGA chip number, and the second digit indicates the slot number of the board. For example, EntPhysicalName=fpga1 3 indicates that FPGA1 in slot 3 is faulty.

    2. If the faulty board cannot be registered after being restarted or the alarm cannot be cleared after the board is registered, replace the faulty board.

    3. If the faulty board is not restarted or powered off and services are running properly, contact technical support personnel.

  • Cause 70: The board does not match the slot.

    The current slot does not support the board. Remove the board. The SIC-4GET-V2 can be installed only in an even-numbered slot.

  • Cause 80: The power supply self-check failed.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 85: The smi serial of the board is abnormal.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 98: The EPLD logic of the board failed.

    1. If the faulty board is not the active control board, go to step 3.

    2. If the slave MPU is normal, perform an active/standby switchover in the system view. Then, go to step 1.

    3. If the faulty board is registered, run the upgrade mpu/lpu/sfu <slotid> startup firmware command in the user view to upgrade the CPlD. Then, go to step 5.

    4. If the faulty board is not registered, power off and then power on the faulty board.

    5. If the faulty board cannot be registered or the fault persists after the board is registered, replace the faulty board.

  • Cause 99: The FPGA local bus self-check failed.

    Collect alarm, log, and configuration information, and contact technical support.

  • Cause 123: The board voltage exceeded the major alarm threshold.

    1. Collect trap, log, and configuration information, and contact technical support.

  • Cause 124: The board voltage fell below the major alarm threshold.

    1. Collect trap, log, and configuration information, and contact technical support.

  • Cause 125: The board voltage exceeds the fatal alarm threshold.

    1. Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 126: The board voltage fell below the fatal alarm threshold.

    1. Collect trap, log, and configuration information, and contact technical support.

  • Cause 127: The board is incompatible with the software version.

    Collect alarm, log, and configuration information, and contact technical support.

  • Cause 128: Different SFUs were installed in the same chassis.

    1. Run the clear inactive-configuration command to clear the offline configuration.

    2. Remove and then insert the faulty board or power on the faulty board. Then, check whether the fault is rectified.

    • If the fault is rectified, go to Step 4.
    • If the fault persists, go to Step 3.

    3. Collect alarm, log, and configuration information, and contact technical support personnel.

    4. End

  • Cause 130: The card is incompatible with board.

    Remove the subcard and insert a subcard that is compatible with the board type.

  • Cause 131: The water detection cable detected leakage.

    Collect alarm, log, and configuration information, and contact technical support personnel.

  • Cause 132742: The presence signals of the board were incorrect.

    1. Check whether the faulty board is reset or powered off and whether services are running properly.

    • If the board is not reset or powered off and services are running properly, go to step 4.
    • If the board is reset or powered off, or services are abnormal, go to step 2.

    2. Power off the faulty board, remove and then insert the board, and then power on the board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 3.

    3. Replace the faulty board.

    • If the board is registered successfully and the fault is rectified, go to step 5.
    • If the board cannot be registered or the alarm persists after the board is registered, go to step 4.

    4. Collect alarm, log, and configuration information, and contact technical support engineers.

    5. End.
