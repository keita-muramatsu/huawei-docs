(Optional) Configuring PPP Negotiation Parameters

Prerequisites

Before configuring PPP negotiation parameters on an interface, you have completed the following task:

  • Configure PPP as the link layer protocol of the interface.

Context

A PPP link is established between two communicating devices through negotiation. After the physical link between the two devices goes up, the devices enter the Establish phase, during which the two devices perform LCP negotiation. After LCP negotiation succeeds, if a network layer protocol has been configured, the devices perform NCP negotiation on network layer packet attributes and types.

Procedure

  1. Enter the system view.

    system-view

  2. Enter the interface view.

    interface interface-type interface-number

  3. Configure PPP negotiation parameters. For details, see Table 1.

    Table 1 Configuring PPP negotiation parameters

    Negotiation Parameter

    Command

    Description

    PPP MRU

    ppp mru-negotiate ipv4

    This command configures PPP MRU negotiation on an interface. If MTUs are configured on the interfaces at both ends of the link, enable PPP MRU negotiation so that the MTUs on the interfaces are negotiated to be the same. This ensures proper data transmission. During PPP MRU negotiation, if the interfaces have different MTUs, the smaller MTU will be used as the MTU of the PPP link.

    Negotiation timeout period

    ppp timer negotiate seconds

    This command configures the PPP negotiation timeout period. During LCP negotiation, the local device sends an LCP negotiation packet to the remote device. If the local device does not receive a reply packet from the remote device within the specified negotiation timeout period, the local device resends an LCP negotiation packet.

    NOTE:

    After the configuration, run the shutdown command followed by the undo shutdown command in the interface view for the configuration to take effect.

    DNS server address

    ppp ipcp dns { primary-dns-address [ secondary-dns-address ] | admit-any }

    ppp ipcp dns request

    The two devices can negotiate the DNS server address during IPCP negotiation. The local device can provide the DNS server address for the remote device or accept the DNS server address assigned by the remote device. In this way, the two devices can both resolve domain names through the assigned DNS server.

    • The ppp ipcp dns { primary-dns-address [ secondary-dns-address ] | admit-any } command configures the local device to assign a DNS server address to the remote device. Alternatively, run the ppp ipcp dns admit-any command to enable the local device to accept any DNS server address assigned by the remote device.
    • The ppp ipcp dns request command configures the local device to request the DNS server address specified by the remote device.
    NOTE:

    After running the ppp ipcp dns command, run the shutdown command followed by the undo shutdown command in the interface view for the configuration to take effect.

    After running the ppp ipcp dns request command, run the shutdown command followed by the undo shutdown command in the interface view for the configuration to take effect.

    PPP magic number check

    ppp magic-number check

    During data transmission over links, if an incorrect link interconnection relationship is detected, the devices will adjust the relationship. However, after the adjustment is complete, the interfaces at both ends are unaware of the adjustment. Consequently, LCP renegotiation is not triggered, causing link establishment to fail. With PPP magic number check, when the local device finds that the magic number carried in the Echo Reply message from the remote device is inconsistent with that learned before, the local device will consider it as an error. After error statistics on an interface reach a specific threshold, the interface goes down, triggering an LCP renegotiation.

    The PPP magic number check function enables an interface to promptly be aware of the link status change.

    NOTE:

    After the configuration, run the shutdown command followed by the undo shutdown command or run the restart command in the interface view for the configuration to take effect.

    Prohibiting the local device from adding the peer host route to the local routing table of direct routes

    ppp peer hostroute-suppress

    To avoid incorrect routing information in the local routing table, you can run this command to prohibit the local device from adding the peer host route to the local routing table of direct routes.

    NOTE:

    After the configuration, run the shutdown command followed by the undo shutdown command or run the restart command in the interface view for the configuration to take effect.

    Default route

    ppp ipcp default-route

    This command configures a default route pointing to the interface where IPCP negotiation is successful. The default route has all 0s as the destination address and mask. When a device is connected to another device using PPP, you can configure a default route to specify the default outbound interface for packets.

    NOTE:

    After the configuration, run the undo pppoe-client dialer command followed by the pppoe-client dialer command in the interface view to restart the dialer interface for the configuration to take effect.

    OSICP and MPLSCP

    ppp { osicp | mplscp } { enable | disable }

    When the default OSICP and MPLSCP configurations differ on devices that are to communicate, run the ppp osicp mplscp command to ensure consistent configurations on both devices.

    • If OSICP and MPLSCP on the remote device go up without negotiation, you need to configure OSICP and MPLSCP on the local device to go up without negotiation by running the ppp { osicp | mplscp } disable command on the local device.
    • If OSICP and MPLSCP on the remote device go up only after negotiation, you need to enable OSICP and MPLSCP negotiation on the local device by running the ppp { osicp | mplscp } enable command on the local device.

    Keepalive time

    keepalive count number

    timer hold interval

    The keepalive count number command configures the Keepalive count during link detection.

    The timer hold interval command configures the polling interval.

    These parameters are used to set the Keepalive time of a link for link status monitoring. You can set a polling interval and Keepalive count to determine whether the link status is normal.

    • Keepalive count

      If the local device does not receive a Keepalive packet from the remote device over the link within a specified polling interval, the Keepalive count increments by 1. If the local device still does not receive a Keepalive packet after a specified Keepalive count is reached, the device considers the link faulty and sets the link status to down.

    • Polling interval

      The polling interval of an interface is the interval at which the interface sends a Keepalive packet. When PPP is specified as the link layer protocol on the interface, the interface sends a Keepalive packet to the remote interface at the specified polling interval. If the interface does not receive a Keepalive packet from the remote interface after five consecutive polling intervals, the interface considers the remote interface faulty and sets the link status to down. In situations with significant network delay or congestion, you can increase the polling interval to reduce network flapping.

    The Keepalive time equals the polling interval multiplied by the Keepalive count. If the Keepalive time is too short and the network delay is long or congestion is severe, network flapping may occur. If the Keepalive time is too long, link faults may not be detected in a timely manner. Therefore, set a proper polling interval and Keepalive count based on the site requirements.
